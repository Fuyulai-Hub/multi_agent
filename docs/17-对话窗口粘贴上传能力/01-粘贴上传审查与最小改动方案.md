# 01 · 对话窗口粘贴上传（现状审查 + 最小改动方案）

> 本文档对应的改造**已实施并验证**，实验记录见 §6；未实施项在 §5 标注「可选增强（未实现）」。

## 1. 结论

**审查结论**：现有两条上传链路（需求文档 `/api/upload` → `requirement_path` 文件通道；对话附图 `/api/upload_image` → `images` 数组）契约清晰，后端校验 / 抽取 / 落盘 / 入流水线职责单一，**与预期行为的偏差全部集中在前端入口层——对话窗口完全不支持粘贴**（截图、复制的文件只能通过「上传需求文档 / 上传图片」按钮走文件选择器）。

**改造结论**：粘贴只是新增一个「文件来源」。前端在 `#new-requirement` 上增加一个 `paste` 监听器，把剪贴板文件按「图片 / 文档」分类后**转交既有两条上传通道**，校验、落盘、抽取、入流水线全部复用原链路——**后端零改动**（`frontend/server.py` / `mas/sources.py` / `mas/leader.py` 一行未动）。净增代码约 70 行，全部在 `frontend/app.js`，另有 `index.html` 两处提示文案；整体可回滚。

**验证结论**：粘贴分发逻辑 18/18 通过（真实加载 app.js + DOM 桩）；真实 server 子进程端到端 15/15 通过（含带图运行验收 pass）；全量 unittest 275 条与基线一致（改动前后均 OK）。

## 2. 现状审查（已核实的代码事实）

### 2.1 既有上传链路（两条通道，互不回归）

```text
通道 A（需求文档）：
  按钮 #upload-doc → FileReader base64 → POST /api/upload
    → sources.save_upload（UPLOAD_SUFFIXES 白名单 / ≤10MB / 文件名净化 / 落盘 workspace/uploads/）
    → 返回 {path, name, kind, ...} → state.upload
  发送时 /api/run 带 requirement_path → start_run → Leader.run(path, as_text=False)
    → load_requirement → sources.extract_text 三级路由（stdlib / MCP / 明确失败）
    → run_dir/input/requirement.md + requirement_source(source="file")

通道 B（对话附图）：
  按钮 #upload-image → FileReader base64 → POST /api/upload_image
    → sources.save_upload(allowed_suffixes=IMAGE_SUFFIXES, max_bytes=5MB)，kind 恒为 "image"
    → 返回 {path, ...} → state.images（含 dataUrl 供缩略图）
  发送时 /api/run 带 images=[paths] → start_run → Leader.run(..., images=...)
    → sources.prepare_images（后缀 / 单张大小 / 张数 ≤4 校验，复制到 run_dir/input/images/）
    → requirement_source.images 元数据（mime/bytes/相对路径，不存 base64）
    → requirement_images_attached 事件；读图由 llm.vision.enabled（默认 false）把门
```

| 事实 | 位置 |
|---|---|
| `/api/upload` 与 `/api/upload_image` 白名单隔离（文档路由拒图片、图片路由拒文档） | `frontend/server.py:444-449, 512-550`；`mas/sources.py:66, 377-431` |
| `/api/run` 的 `requirement` 与 `requirement_path` 二选一；`images` 只做类型校验 | `frontend/server.py:475-496` |
| `images` 仅附图：只有图片、没有文字/文档时 400「图片为附图，需与需求文字/文档一同发送」 | `frontend/server.py:481-483` |
| `start_run` 两条通道都透传 `images` 给 `Leader.run` | `frontend/server.py:349-354` |
| 前端上传约束常量与后端对齐（后缀表 / 5MB / 4 张 / 10MB） | `frontend/app.js:19-24` |

### 2.2 与预期行为的偏差清单

| # | 偏差 | 位置（核实值） | 性质 | 处置 |
|---|---|---|---|---|
| D1 | **对话窗口无 `paste` 监听**：`#new-requirement` 只处理 Enter / Shift+Enter；粘贴截图或复制的文件时 textarea 无默认动作，图片被静默丢弃，用户零反馈 | `frontend/app.js:652-658`（keydown），无 paste | 功能缺口（本次主目标） | 新增 paste handler（§4） |
| D2 | 剪贴板文件的 `name` 可能为空（截图、部分复制途径）；原按钮路径按 `file.name.split(".").pop()` 推后缀，空 name 会得到 `"."` 被拒，且后端 `_safe_name("")` 直接抛「文件名非法」 | `frontend/app.js` 原 upload-image 后缀推导；`mas/sources.py:365-374` | 粘贴场景边界（按钮路径不会触发，因为文件选择器必有文件名） | `pastedFileName()` 按 MIME 补名（§4） |
| D3 | 个别浏览器 `clipboardData.files` 为空但 `items` 里有文件项 | — | 兼容边界 | `clipboardFiles()` items 兜底（§4） |
| D4 | 重复选择**同一个**文档文件不触发 `change`（`#upload-doc` 未重置 input value），上传失败后重选同一文件无反应 | `frontend/app.js` 原 `#upload-doc` handler（对比 `#upload-image` 有 `ev.target.value = ""`） | 既有小缺陷（与粘贴无关，审查发现） | 顺手修复 1 行，与图片输入行为对齐 |
| D5 | 纯文本粘贴必须放行：若 paste handler 无条件 `preventDefault`，用户连粘贴文字都被阻断 | — | 回归风险点（改造自身引入） | `clipboardData` 无文件即 `return`，不阻止默认行为 |

**以下两项「看似偏差、实为有意设计」，本次保持不动**：

1. **只粘贴图片、无文字/文档时发送被拒**（前端守卫 + 后端 400 双重保证）。依据 `16-…/01-图片输入.md` §边界：图片是需求附图，单独不构成可执行需求。粘贴与按钮上传在此语义上保持一致。
2. **粘贴图片的「读图」仍由 `llm.vision.enabled`（默认 false）把门**。端点 multimodal 兼容性未探测前不谎称读图；能力形态为「缩略图展示 + 流水线存档 + 事件留痕」。本项不改变该默认值。

## 3. 方案设计

### 3.1 数据流

```text
用户在 #new-requirement 按 Ctrl+V
        │
        ▼
paste handler（app.js 新增，约 44 行）
        │  clipboardFiles(clipboardData)：files 为主路径，items 兜底；无文件 → 放行默认粘贴（纯文本）
        ▼
   逐个文件分类：MIME 或后缀任一指向图片 → 附图通道；否则 → 文档通道
        │
        ├─ 图片 → uploadImageFile(file, pastedFileName(file,"png"))
        │            → POST /api/upload_image（既有路由，零改动）
        │            → state.images + renderImageTray()（缩略图托盘，可移除）
        │
        └─ 文档 → uploadDocFile(file, pastedFileName(file,""))
                     → POST /api/upload（既有路由，零改动）
                     → state.upload（发送时走 requirement_path 文件通道）
        │
        ▼
   用户点「发送需求」→ /api/run（requirement / requirement_path 二选一 + images）
        → 与按钮上传**完全同一条后端链路**：save_upload → Leader.run → extract_text / prepare_images
        → run_dir/input/images/ + requirement_source.images + requirement_images_attached 事件
```

### 3.2 接入位置与模块边界

| 层 | 位置 | 职责边界 |
|---|---|---|
| 文件来源（新） | `app.js` paste handler | 只做「取文件 → 分类 → 补名 → 转交」；不碰 HTTP 契约、不做后端已有的校验 |
| 上传接收（既有） | `frontend/server.py` `/api/upload`、`/api/upload_image` | **零改动**；白名单/大小/净化仍是单一事实来源 |
| 暂存与抽取（既有） | `mas/sources.py` `save_upload` / `extract_text` / `prepare_images` | **零改动** |
| 流水线（既有） | `mas/leader.py` `Leader.run(images=…)` | **零改动** |

**边界原则：粘贴不制造新通道。** 粘贴产生的 HTTP 调用与按钮上传逐字节同构（同一 URL、同一 payload 字段），因此所有既有防护（后缀白名单、10MB/5MB 上限、文件名净化、落盘 resolve 校验、张数截断告警）对粘贴自动生效，无需重复实现。

## 4. 关键实现细节

### 4.1 抽出的两个上传函数（按钮与粘贴共用）

```js
async function uploadDocFile(file, nameOverride) {
  const name = nameOverride || file.name;      // 粘贴场景：剪贴板 name 可能为空
  if (file.size > 10 * 1024 * 1024) { setUploadName("文件超过 10MB 上限", "error"); return false; }
  setUploadName(`正在上传 ${name} ……`, "running");
  try {
    const content_base64 = await fileToBase64(file);
    const res = await fetch("/api/upload", { /* filename: name, content_base64 */ });
    const data = await res.json();
    if (!res.ok) { state.upload = null; setUploadName(data.error || "上传失败", "error"); return false; }
    state.upload = { path: data.path, name: data.name };
    setUploadName(`已选择：${data.name}（${data.kind}，发送时将替代输入框内容）`, "done");
    return true;
  } catch (err) { state.upload = null; setUploadName(`上传失败：${err.message}`, "error"); return false; }
}
```

`uploadImageFile` 同构：后缀白名单（按 `name` 推）→ 单张 5MB → 张数 ≤4 → `POST /api/upload_image` → 成功 push 进 `state.images` 返回 `true`。**校验顺序与错误文案与改造前逐字一致。**

### 4.2 剪贴板取文件与补名

```js
function clipboardFiles(data) {
  const direct = Array.from(data.files || []);
  if (direct.length) return direct;
  return Array.from(data.items || [])          // 兜底：files 为空但 items 有文件项
    .filter((item) => item.kind === "file")
    .map((item) => item.getAsFile()).filter(Boolean);
}

function pastedFileName(file, fallbackExt) {
  if (file.name && /\.[A-Za-z0-9]+$/.test(file.name)) return file.name;   // 正常名原样用
  const ext = ((file.type || "").split("/")[1] || fallbackExt || "").replace(/[^a-z0-9]/gi, "");
  return ext ? `pasted-${Date.now()}.${ext}` : `pasted-${Date.now()}`;
}
```

设计要点：
- **图片通道**：Chromium 截图粘贴给 `name="image.png"` + `type="image/png"`，正常名直接复用；无名时按 MIME 补 `pasted-<ts>.png`，保证 `IMAGE_SUFFIXES` 命中。
- **文档通道**：从资源管理器复制的文件带真实文件名；无名时按 MIME 补 `pasted-<ts>.markdown` 等；两者都缺时得到无后缀名，**由后端明确拒绝**（`不支持的文件后缀 (无后缀)`）——明确失败而非静默，符合项目「不静默、不伪造」的一贯立场。
- 落盘名带 `upload_id` 前缀（`save_upload` 既有行为），多次粘贴同名文件不会互相覆盖。

### 4.3 paste handler：分类、转交、托盘刷新

```js
$("#new-requirement").addEventListener("paste", async (ev) => {
  const files = clipboardFiles(ev.clipboardData);
  if (!files.length) return;                 // D5：纯文本粘贴放行默认行为
  ev.preventDefault();
  let imagesAdded = 0;
  for (const file of files) {
    const isImage = (file.type || "").startsWith("image/")
      || IMAGE_SUFFIXES.includes("." + (file.name.split(".").pop() || "").toLowerCase());
    const ok = isImage
      ? await uploadImageFile(file, pastedFileName(file, "png"))
      : await uploadDocFile(file, pastedFileName(file, ""));
    if (ok && isImage) imagesAdded += 1;
  }
  renderImageTray();                          // 粘贴的图片与按钮路径一样进托盘（可见、可移除）
  if (imagesAdded) setUploadName(`已选择 ${state.images.length} 张附图（随需求一起发送，可点 ✕ 移除）`, "done");
});
```

- **分类用 MIME 优先、后缀兜底**：剪贴板截图常只有 MIME 可靠；复制的文档文件则两者都有。
- **`renderImageTray()` 无条件调用**（幂等：无图时隐藏托盘），保证粘贴与按钮两条路径的视觉反馈一致；文档上传的「已选择」状态由 `uploadDocFile` 自行设置，不被覆盖。
- 一次粘贴混合「图 + 文档」时两条通道各归其位（自动化用例 12 覆盖）。
