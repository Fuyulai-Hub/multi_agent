## 2. 三步方案的可行性核实

| 用户方案 | 核实结果 | 落地方式 |
| --- | --- | --- |
| ① inputs（name/type/required/default）映射成 function schema，注册进 ToolRunner | **成立**。`Skill.meta["inputs"]` 字段已齐；`ToolRunner.register_local`（`mas/toolrunner.py:80`）就是为「本地执行器」预留的入口（web_search 同款模式），无需改 ToolRunner 本体 | 新增 `build_tool_schema()`：inputs → `properties` / `required` / JSON Schema `default`；`type` 取 string/integer/number/boolean/object/array，未知回落 string |
| ② 模型 tools/call → sandbox 执行 `scripts/*.py` → stdout 回灌 | **成立，但有两处必须新增的设计**（原方案未覆盖）：<br>**(a) 参数协议**——模型 arguments 如何到达脚本，需要定一个约定；<br>**(b) 沙箱 root**——`Sandbox` 的路径边界以 root 为界（`sandbox.py:148`），技能目录不在 run 目录内，直接用 run 的沙箱会「路径越界」 | (a) 入参以**单个 JSON**（`sys.argv[1]`）传入，框架侧做「白名单过滤 + required 校验 + default 填充」；<br>(b) 以**技能目录为 root 新建独立 Sandbox**（与既有 `_smoke_skill` 冒烟同一模式，`skills.py` 内既有先例） |
| ③ steps 非脚本部分只能是文本约束 | **判断成立**。「完成技术选型」这类意图性步骤无法变成调用，保留 `render_for_prompt` 文本注入轨；两轨独立开关、可并存 | 未动文本轨。`tool.script` 声明 = 进入可执行轨；未声明 = 仅文本轨 |

补充说明（白名单约束，方案已提到、实现遵循）：沙箱命令白名单 `python/python3/py/node`
（`config/system.yaml` + `sandbox.py:280`），因此技能脚本的执行器固定为
「`config.runtime.python` + 脚本相对路径」，脚本本身用 Python 写（node 脚本同理可挂，
本批技能不涉及）。

## 4. 数据流与参数协议

```text
装配（run 启动时一次）：Leader._build_tool_runner()          mas/leader.py
  ├─ llm.tools_enabled=true  → MCP tools/list + web_search（既有）
  └─ skills.enabled && skills.tools_enabled=true → _register_skill_tools()
       对每个声明了 tool.script 的技能：
         build_tool_schema(skill) → 注册 skill_<id> 到 ToolRunner.register_local
         执行器闭包 = run_skill_script(skill, arguments, config, events)
       未声明 tool.script 的技能不注册（继续走文本注入轨）

调用闭环（intake 节点，既有机制零改动）：
  base._tool_schemas（tools_nodes 白名单，默认 ["intake"]）
    → tools 随请求下发（与 response_format 互斥，既有）
    → 模型返回 tool_calls{skill_contract_schema_guard{contract_spec, payload, node_id}}
    → run_skill_script：
        ① 参数白名单过滤（只透传 inputs 声明字段）+ required 校验 + default 填充；
           缺必填 → 不执行脚本，错误作为 tool 消息回灌（模型可自纠）
        ② Sandbox(root=技能目录, cwd=技能目录) 执行 [python, scripts/guard.py, <JSON>]
        ③ 返回 {ok, exit_code, duration_ms, stdout, stderr} → json.dumps 回灌
    → 模型基于 stdout 续跑（轮数上限 llm.tool_max_rounds）
  留痕：tool_calls_requested / skill_tool_executed / sandbox_exec 事件 + llm_traces.jsonl
```

脚本侧约定（写 SKILL.md 与技能脚本时必须遵守）：

1. 入参读 `sys.argv[1]`（JSON 对象），字段名与 SKILL.md `inputs` 一致；
2. 结果打印到 stdout（框架原样回灌），JSON 为佳；
3. 退出码 0 = 脚本自身执行成功，业务结论（如校验 fatal）放在 stdout 里表达；
4. 脚本定位为**只读**：沙箱 root=技能目录意味着技术上可写技能目录，约定不写、
   不产生持久副作用（需要输出文件的能力不在本期范围）。

`tool` 字段规范（front-matter 可选）：

```yaml
tool:
  script: scripts/guard.py    # 必需：相对技能目录的脚本路径；声明了才注册为工具
  description: ""             # 可选：工具描述（默认取 skill.description + when_to_use）
```

运行：`python tests/live_skill_call.py`　→　`workspace/runs/live-skill-20261016-234919`
（真实装配路径 `Leader._build_tool_runner` + 真实 `ProductAgent.act` + 真实端点 + 真实沙箱）

| 环节 | 证据 |
| --- | --- |
| 工具注册 | `skill_tool_registered`：tool=`skill_contract_schema_guard`，inputs=[contract_spec, node_id, payload] |
| 模型决策 | 第 1 轮 finish_reason=`tool_calls`；`tool_calls_requested.calls[0]` 参数完整（contract_spec.fields 两项 / 客户样例 payload / node_id=intake） |
| 沙箱执行 | `sandbox_exec`：`python scripts/guard.py {"contract_spec": {...}, ...}` exit=0；`skill_tool_executed`：588ms、stdout 242 字符 |
| 回灌消费 | 第 2 轮 finish_reason=`stop`、9173 字符；background 中逐字引用报告原文（checked/missing/type_mismatch/skipped/repaired/fatal 六键齐全）并据此声明「判定可放行」 |
| 双轨并存 | `skill_matched`（spec-scope-guard 文本注入 1177 字符）与 `tool_calls_requested` 同一次运行中各自生效 |

一个值得留意的实现细节（防御性设计的正反馈）：模型按 schema 把 `contract_spec`
构造成 `{"fields": [...]}`（inputs 声明 type=object 的自然推断）；`guard.py` 的
`_load_fields` 同时兼容「列表」与「含 fields 的对象」两种形态，因此首轮即命中、无需重试。

## 6. 边界与不做

- **只能经沙箱白名单解释器**执行（python/python3/py/node）；shell 一律拒绝（既有硬约束）；
- **技能脚本以技能目录为 root**：路径越界被拒；技术上可写技能目录，约定只读（§4-4）；
- **steps 的意图性描述永远是文本轨**，本方案不试图把自然语言步骤编译成调用；
- **单次工具调用的轮数上限**沿用 `llm.tool_max_rounds`（本测试内存调为 3）；多技能协作
  依赖模型多轮自主组合，不做框架级编排；
- **响应体大小**：stdout 单次截断 20000 字符（同模块常量），tool 消息再经
  `tool_result_max_chars`（4000）全局截断，双层防刷屏；
- **默认关闭**：`skills.enabled=false` / `skills.tools_enabled=false` 时整条链路不装配，
  默认路径与原实现逐字节一致。

## 8. 启用方式

```yaml
# config/system.yaml
runtime:
  skills:
    enabled: true          # 技能系统总开关（文本注入轨同时开启）
    tools_enabled: true    # 技能工具（本功能）
llm:
  tools_nodes: ["intake"]  # 哪些节点下发工具（默认仅 intake；tools 与 json_mode 互斥）
```

前置：目标技能在 SKILL.md 声明 `tool.script` 且脚本存在（`python -m mas skill show <id>`
可查看可调用工具行；脚本缺失时注册端发 `skill_tool_skipped` 告警并跳过该技能）。
