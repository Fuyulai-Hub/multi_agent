# Part 1｜精简版简历描述（可直接粘贴）

## 配置驱动的多 Agent 软件交付流水线系统（MAS）

**技术栈**：`Python 3` / `Multi-Agent System` / `Agent Orchestration` / `Leader-Worker` / `配置驱动 Configuration-Driven` / `YAML Profile 深合并` / `黑板模式 Blackboard` / `消息总线 Message Bus` / `请求-应答协商` / `分层记忆 L1/L2/L3` / `自学习闭环` / `事件溯源 Event Sourcing` / `JSONL 事件日志` / `可观测性 Observability` / `AST 静态分析` / `白名单安全求值` / `沙箱执行 subprocess` / `质量门禁 Quality Gate` / `回退与重试` / `优雅降级` / `Prompt 工程` / `结构化输出契约` / `Function Calling Tool Use` / `MCP (stdio/sse)` / `零依赖设计` / `unittest`

> 独立设计并落地的 LLM 多 Agent 交付系统：Leader 统一调度 5 个角色 Agent，把「需求评估 → 方案设计 →
> 编码实现 → 代码审查 → 业务测试 → 缺陷修复 → 验收门禁 → 报告归档」全链路自动化，并用事件日志驱动的
> 三级经验库构建可证伪的自学习闭环；核心 12,428 行 Python，**第三方依赖仅 PyYAML**，287 个自测用例全通过。

- **设计配置驱动的 Leader 调度内核**：用 YAML 声明 8 节点流水线状态机（节点/角色/流转/门禁/回退策略），配合 Profile 深合并与「裁剪节点后自动重接流转边」，使流程拓扑变更零代码改动——`strict` 插入方案评审节点（8→9）、`lean` 裁剪审查节点（8→7，门禁 10→5 条）均只需一个 YAML 文件；配置加载期一次性校验引用可达性与门禁表达式合法性，把故障前置到启动阶段。
- **实现「黑板 + 消息总线」解耦的多 Agent 协作机制**：角色间零直接调用，产物写入版本化共享黑板（`v*.json` + `latest` + sha256），按感知矩阵按需读取上游上下文；消息总线支持广播与 `correlation_id` 关联的请求-应答协商，未闭环的需求歧义直接作为门禁项阻塞验收，全部通讯落盘可审计。
- **落地 AST 白名单安全求值的证据式质量门禁**：替代模型自评打分——基于 `ast.NodeVisitor` 白名单求值器（禁用导入/赋值/lambda/非白名单函数，实测拦截 `__import__`、`eval`、`open`）判定 10 条门禁表达式，叠加基于真实 `ast` 的静态审查（12 条规则）；不通过则按 per-node 回退策略退回修复，并用全局回退上限与最大步数兜底防死循环。
- **构建三级经验库自学习闭环并验证其有效性**：从事件日志规则化提炼 5 类经验，按「相关性 0.45 + 置信度 0.25 + 频次 0.15 + 新鲜度 0.15」加权检索，受分层 + 全局 token 双重预算约束注入 Prompt；经验携带机器可读 `action_key` 被确定性执行体真实消费。**实测同一需求连续三轮：11 步/5 缺陷 → 7 步/0 缺陷 → 7 步/0 缺陷**，第二轮起缺陷不再复现。
- **实现五层沙箱化代码执行**：路径越界拦截、命令白名单（拒绝 `cmd`/`bash`/`powershell` 等 shell 解释器）、剔除含 `KEY/TOKEN/SECRET` 的环境变量防凭据泄露、POSIX rlimit 资源限制（CPU 300s/内存 1GB/进程 128）、AST 检测外连依赖与子进程白名单绕过；执行前静态体检把「环境缺工具链」「测试套件自身缺陷」与真实交付物缺陷区分开，避免回退预算被无效返工耗尽。

## V2｜确认效果由经验库驱动（排巧合）

只看步数下降不足以证明因果，因此核对了完整因果链，四环相扣：

1. 第一轮确实注入了缺陷 —— `round1/artifacts/code_manifest/v1.json`：
   ```json
   "defects_injected": [{"op": "calc_shipping", "fp_id": "FP-03",
     "note": "续重步数用 int() 截断而非向上取整，且遗漏新疆/西藏偏远地区加收"}]
   ```
2. 该缺陷被事件日志提炼成经验 —— action_key = `guard_calc_shipping__boundary`（置信度 0.90 / 触发 `bug_found`）
3. 第二轮 `implement` 节点的 Prompt **确实注入了这条经验**（`prompts/implement#1-developer-044441.md` 原文）：
   ```text
   - (置信度 0.90 / 命中 3 / 触发 bug_found) 功能点 FP-03 出现边界缺陷：
     AssertionError: Decimal('15.00') != Decimal('20.00')
     动作: 实现 FP-03 时显式覆盖边界输入，并保留回归用例
     标识: guard_calc_shipping__boundary
   ```
4. 第二轮 `code_manifest` 的 `defects_injected` = **`[]`** —— 同一缺陷不复现。

> 结论：**自学习闭环是真实因果链，不是「第二次碰巧写对了」**。

# Part 3｜诚实边界（面试时被追问请主动说明）

## ⚠️ 边界 1：MCP / Function Calling 已实现，但当前未接入生产服务

验证时发现的客观事实，不容粉饰：

```text
$ python -m mas mcp list
未配置 MCP 服务（配置文件：config/mcp.yaml）     # 该文件内容就是 servers: []
system.yaml:47  tools_enabled: false            # function calling 默认关闭
```

准确表述应为：
> **实现了** MCP 客户端（stdio 长驻子进程 + SSE）、五阶段诊断、`tools/list → ToolRunner → 结果回传 → 续跑`
> 的完整 function calling 闭环，并用真实子进程 + 287 个单测覆盖；
> **但仓库自带的 `config/mcp.yaml` 为空（`servers: []`），未接入任何真实第三方 MCP 服务，
> 且 `tools_enabled: false` 默认关闭**，默认链路走的是「结构化输出契约 JSON + 确定性 Python 工具执行」。

**不要**在简历里写「集成了 XX 个 MCP 工具」「生产环境使用 function calling」。

## ⚠️ 边界 2：端到端通过率不可简化引用（务必看口径）

全量 38 次运行（`workspace/knowledge/metrics.jsonl`）的真实分布：

| 口径 | 通过 | 说明 |

要点：
- **C++ 需求（`cpp_smart_pointer`）的 1/4 通过是设计内结果**：沙箱只能执行 Python，非 Python 交付物
  被 `_verification_gap` 判定为「验证口径缺口」并如实判失败。这不是缺陷，是刻意不谎报及格。

- 离线确定性 Provider（`provider: offline`）下稳定性显著更高，本次三轮验证 3/3 通过。

## ⚠️ 边界 3：不要声称「高并发 / 分布式」

Leader 是单进程同步 `while` 循环（`leader.py:233`）；运行时引用已改为参数显式传递以支持同一 Leader
实例被复用，但**同进程内仍不能并行两个 run**。跨进程安全靠 `msvcrt`/`fcntl` 文件锁保证，是「并发安全」，
不是「并发执行」。

## ⚠️ 边界 4：沙箱无网络隔离

`network_import` 规则只是让高危外连依赖**可见**供 reviewer 拦截，不是隔离——标准库没有跨平台网络命名空间
方案。Windows 下 rlimit 也自动跳过并降级。这两点已在代码注释与 finding 消息里写明。

## ⚠️ 边界 5：经验库数据会随运行增长，引用时请注明时间点

截至本次验证：`workspace/knowledge/experience.jsonl` 122 条（L1 90 / L2 2 / L3 30），累计命中 1,857 次，
