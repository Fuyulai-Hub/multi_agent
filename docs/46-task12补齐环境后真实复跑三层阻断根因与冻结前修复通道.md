## 2. 三层失败原因：逐个用实验分离，而不是靠推理排序

### 2.1 第一层：冻结副本里的裸名 `npm`（用户上一轮修的那类）

走框架通道复跑冻结清单（`mas/verify/exec.py::execute_frozen_suite`，iteration=3，
tag=`verifyspawn`，驱动脚本 `workspace/logs/rerun_frozen_suite_task12_03.py`）：

```
total=39 passed=6 failed=33 duration_ms=43
AssertionError: backend service unavailable: spawn failed:
FileNotFoundError(2, '系统找不到指定的文件。', None, 2, None)   × 33
```

这说明上一轮的修复**改变了归类和修复通道，没有改变已冻结的文件本身**——
`frozen_tests/tests/test_all.py:58` 至今仍是 `subprocess.Popen(["npm", …])`。

### 2.2 第二层：交付物的 TypeScript 错误

`workspace/runs/task12-foodlink-spa-03/code/backend/src/admin/stats.service.ts` 第 43/44 行：

```ts
this.prisma.listing.groupBy({ by: ['status'], _count: { _all: true } }),
this.prisma.claim.groupBy({    by: ['status'], _count: { _all: true } }),
```

Prisma 5.22 的类型定义要求 `groupBy` 与 `_count` 同时出现时必须给 `orderBy`：

```
src/admin/stats.service.ts:43:37 - error TS2345: … Property 'orderBy' is missing …
src/admin/stats.service.ts:44:35 - error TS2345: … Property 'orderBy' is missing …
[01:44:50] Found 2 errors. Watching for file changes.
```

注意清单绑的是 `^5.19.0`，装到 5.22.0 后类型变严 ——【实测】错误真实存在且服务不监听；
【推断】若锁到 5.19.x 可能不报，本轮没有降级验证。

在 scratch 副本补上 `orderBy: { status: 'asc' }` 后，`nest start --watch` **3.0 秒监听**，
`GET /api/listings` 返回 200 和真实业务数据。**归档目录一行没改。**

### 2.3 第三层：套件自己的 `stdout=PIPE` 死锁（本轮新发现）

只改 stdout 去向的三组对照（`workspace/logs/boot_diag_pipe_vs_file.py`，同一 scratch 目录、
同一条命令、同样轮询 60s）：

```
mode=pipe         port=63579 wall=60.0s NOT READY      ← 冻结套件的写法
mode=drain        port=64142 wall=3.0s  READY status=200
mode=file         port=63973 wall=3.0s  READY status=200
drain 日志 = 8656 字节
```

同一份代码、同一个命令，唯一变量是「管道有没有人读」。机制【推断】是 Windows 匿名管道
缓冲只有数 KB，写满后子进程阻塞在 `write()`；**行为差异是【实测】**，与被启动程序的
语言无关——任何会打印大量启动日志的服务都会中招。

`frozen_tests/tests/test_all.py` 的 `_Backend.start()` 正是这个形状：`stdout=PIPE, text=True`，
后续只有 `poll()`/`terminate()`/`wait(timeout=10)`，全文从不 `read()` 或 `communicate()`，
超时时把 `self.log` 写成 `timeout waiting for backend`。所以 33 条用例的失败信息
把根因指到了「后端没起来」，而后端起不来是**测试文件自己**造成的。

## 3. 框架改动（3 处，都是被实测逼出来的）

前 2 处（§3.1/§3.2）在「补齐环境后复跑」阶段落地；第 3 处（§3.3）是全链路续跑**结束后**
针对 §7.3 实测到的归因盲区补的，按本轮选定的最小口径——只落检测规则，不动执行协议（§9 第 3 条）。

### 3.1 `code_hash` 排除 `node_modules`（`mas/verifier.py`）

给 node 交付物补齐环境的动作本身会把证据链打死：一次 `npm install` 往沙箱根落了
**43,152 个依赖文件**，它们全部计入 `code_hash`。门禁重算的 hash 与 attest 时的值必然不一致，
于是**任何 node 交付物无论测试是否通过都过不了门禁**。

实测效果：`code_hash` 覆盖文件数 43,211 → 59（清掉我误留的 lockfile 后 57），
正好等于交付源码集合。回归：`tests/test_verifier.CodeHashScopeTests`（3 条），
覆盖「任意层级 `node_modules` 排除」「`package.json` 仍被绑定」「`src/node_modules_doc.ts`
这类同名普通文件仍计入」。

### 3.2 新增静态规则 `spawn_unread_pipe`（`mas/sandbox.py` + `mas/agents/tester.py`）

- 判定按**句柄**而不是按全文：`conn.getresponse().read()` 这类与管道无关的 `read()`
  不能替 `Popen` 的 stdout 免责（task12 的冻结套件里两种写法同时存在，按全文判定会漏报）。
  认可的「有人读」证据：同句柄的 `communicate()/read()` 等、访问同句柄的 `.stdout`/`.stderr`、
  把句柄传给别的函数。`stdout=<日志文件> + stderr=STDOUT` 是安全写法，不报（正是修复指令的落点）。
- 归入 `TesterAgent._SUITE_DEFECT_RULES` → 根因四分类落 `test_suite_defect`（**不是**
  `environment_or_build`，也**不是** `delivery_unverifiable`），于是触发
  `verifier.invalidate()` 解冻 + 冻结前 `_ensure_spawnable_suite` 带精确修复指令重生成。
- 对真实冻结文件生效（`mas/sandbox.py::Sandbox.analyze`，reviewer policies）：

```
('windows_spawn_extension', 58, '… 裸名 `npm` … 本机真实文件是 F:\software\npm.CMD …')
('spawn_unread_pipe',       58, '… 句柄 `self.proc` 在本文件里没有任何读取 …')
```

- 回归：`tests/test_spawn_unread_pipe.py`（9 条）——检出、三种正确写法不误报、
  `capture_output=True` 不误报、两条缺陷同时存在时都报、归类为 `test_suite_defect`、
  进入冻结前体检白名单、无 LLM 时按既有先例跳过并留痕。
- 已知漏报/误报面：句柄先进容器再读出（`self.procs.append(p)` + `self.procs[0].stdout.read()`）
  静态看不到归属，会误报一次；宁可让生成方改成显式重定向，也不放过真死锁。

### 3.3 新增静态规则 `suite_import_target_missing`（`mas/sandbox.py` + `mas/agents/tester.py`）

针对 §7.3 实测到的归因第 4 类盲区：iter05/iter06 的 `root_cause_category` 是**空串**——四类根因
谁都不像，默认落到「交付缺陷」，于是连续三轮把「让 `import foodlink` 成立」这个研发不可能完成的
任务派给 developer，attempt 3 真的往交付里新写了一个 Python 包（§7.5）。

- 判定（`Sandbox.suite_import_target_findings`，`mas/sandbox.py:998-1096`）三件事同时成立才发声，
  刻意保守：① 文件在 `tests/` 下（不动 reviewer 对交付代码的分析口径）；② 套件确实 import 了契约
  声明的 `package`；③ 工作区里找不到这个包。`_workspace_has_package` 深度限 4 层，跳过
  `node_modules/dist/build/out/.git/__pycache__/.venv/.mas_verify/*_cache/site-packages` 等目录，
  `<pkg>/__init__.py`、包内任意 `.py`（命名空间包）、顶层 `<pkg>.py` 都算「真的交付了这个包」；

- 归入 `_SUITE_DEFECT_RULES` → 根因落 `test_suite_defect`，进入既有可修通道：冻结前

## 5. 门禁为什么仍然不可能为绿（结构性缺口，非环境）

1. **隐藏套件是 Python 形状的。** `workspace/hidden/task12-foodlink-spa-03/frozen_tests/tests/test_hidden_foodlink.py`
   头部是 `from foodlink import create_app` + `wsgiref.simple_server.make_server`，34 条 id。
   NestJS 交付没有可导入的 Python 包，`mas/hidden.py::build_generation_prompt` 的协议只教
   Python 一种形状，且它由 intake 阶段在**技术选型之前**生成并冻结、之后不随选型重生成。
   → 门禁里 `execute_hidden(...) + failed=0` 这条硬性 criterion 结构上无法满足。
2. **SPA 浏览器证据要服务自己打印 `MAS_UI_PORT=<port>`。** `mas/uiprober.py` 的
   `_await_port()` 只认这一行；全仓库检索该字符串只出现在
   `mas/agents/tester.py`、`mas/uiprober.py`、`tests/`、`examples/requirements/spa_counter_probe.md`。

### 7.2 框架自身也带同类管道缺陷（实测代码，未改动）

### 7.3 坏套件被当成有效证据反复重跑：归因器的第 4 类盲区（实测）

iter05（08:00:05–08:00:06）不是新失败，而是**同一份坏套件的第二遍**，文件级证据：

- `test_verified valid=true` + `assertions=57`：签名、逐用例记录、断言数全都自洽。
  框架的解冻条件只有两个——静态检出套件缺陷、或套件崩到无法枚举用例——
  这份套件两者都不满足（它能枚举，且没有任何 spawn 类发现，见

问题在于这个默认落点是错的：需求侧要求套件「import 被测包（`package` 字段）下的公开接口」

**研发无论改多少轮代码都无法让 `import foodlink` 成立**，除非往交付里塞一个假的 Python 包——
那才是真正该被拦住的事。所以这不是模型不努力，是框架把一条无解的修复任务反复派给研发，
并把 3 次节点内回退预算烧在同一个不可能完成的 import 上。

最小可落地的修法（**已落地，见 §3.3**）：冻结前体检增加一条
「套件 import 的被测包在工作区不存在」发现（`suite_import_target_missing`），
归入 `_SUITE_DEFECT_RULES` → 判 `test_suite_defect` → 解冻重生成，并在修复指令里
说明非 Python 交付必须改用「外部服务生命周期」写法（spawn 交付自带的启动命令 +
端口等待 + HTTP 断言），而不是 import 一个不存在的包。

本轮按「只落检测规则（最小可证）」的口径执行：检测 + 归类 + 修复指令已上线；
**第二种执行协议（让重生成的套件真的能用非 Python 形态取证）没有上线**，
所以这条规则现在的效果是把失败如实归到「套件写了无法兑现的 import」并给出改法，
而不是让非 Python 交付从此能过门禁（残留见 §3.3 末与 §9 第 3 条）。

## 9. 建议（按优先级）

1. **隐藏套件按选型语言重生成**（`mas/hidden.py` + leader）：Python 协议写死的验收用例
   对 NestJS/SPA 交付是零证据，这是 task12 过不了门禁的第一原因。
2. **端口发现不要只认 `MAS_UI_PORT`**（`mas/uiprober.py`）：增加从 `Local: http://localhost:<port>`
   /`Nest application successfully started` 后续监听行解析的兜底，并把该契约写进需求模板，
   让 developer 在交付时就满足，而不是让 tester 事后补。
3. **`full_stack_*` 需要第二种执行形态，不能只有「同进程 Python 服务」**
   （`mas/agents/tester.py:25/30-70/164-169`）：非 Python 交付要么让套件用
   「外部服务生命周期」写法（spawn 交付自带启动命令 + 端口等待 + HTTP 断言 +
   关停，日志重定向到工作区文件），要么由框架自己起服务后把 `base_url` 注入套件。
   否则每次解冻重生成都会退回 `from foodlink import build_handler` 这一形状。
4. ~~**冻结前体检补一条 `suite_import_target_missing`**~~ —— **已落地**（`mas/sandbox.py:998-1096`
   + `mas/agents/tester.py` 的 `_SUITE_DEFECT_RULES`/`_target_package`/`_preexec_diagnosis`，见 §3.3，
   回归 `tests/test_suite_import_target_missing.py` 12 条）：套件 import 的 `package` 在工作区不存在
   即判套件缺陷并解冻，修掉 §7.3 实测到的归因盲区（`root_cause_category=""` →
   误派给研发、白烧 3/3 预算）。**残留**：冻结前拒入仍走「节点 fail → 回退 optimize」，
   没在测试节点内原地重试；且它只解决「归类正确」，不解决「重生成时没有可用协议」——
   那要等第 3 条。
5. **`spawn_unread_pipe` 之外还该有一类「套件自杀式写法」规则**：本轮的 PIPE 死锁、
   上一轮的裸名 `.cmd`，共同点是「失败信息指向交付物，缺陷在测试文件」。建议把
   `_SUITE_DEFECT_RULES` 当作一个持续扩充的清单来维护，每条都必须带实测对照证据。
6. **`UiProber` 端口命中后继续排空管道**（`mas/uiprober.py:172-199`，见 §7.2）：
   这是框架自己取证通道里的同类死锁，应与第 5 条一起修，但要在本轮 run 收尾后动，
   避免证据归属混淆。
7. **`dist` 之类的构建产物是否也要从 `code_hash` 排除**：本轮实测一次启动前后 hash 不变，
   还没到「必须排除」的证据强度；但 nest 重编译会让 81 个派生文件进入 hash 集合，

## 10. 大白话

上一轮说「环境没有，所以跑不了」，我把环境真的装好了：数据库起来、依赖装完、库表建好、
数据灌进去，后端 3 秒就能启动并返回真实数据。然后重跑那 39 条测试，发现还是有 33 条不过。
一层层剥开：最外面一层是测试脚本里 `npm` 名字写错了（上一轮已经会修了）；中间一层是
AI 交付的后端代码本身有两个类型错误，服务器压根起不来；最里面一层最坑——测试脚本让后端
把日志写到一根「没人读的管子」里，日志一多就把管子塞满，后端卡在那儿永远不动，
于是测试只会报「后端没起来」，看着像后端的错，其实是测试自己写的。我把这个也做成了
框架能自动检查出来的规则，加了 12 个测试，那阵子全量 745 个测试全过；后来把「测试 import
的包压根不存在」也做成规则，又加 12 个测试，全量 757 个测试全过。

至于门禁能不能变绿：**目前还不能**，但原因已经不是环境了——隐藏那套验收用例是 Python 形状的，
天生验不了 NestJS 交付；前端证据要求服务自己喊出端口号，而这台机子上没人教过后端要喊这一句。
这两件事要改的是设计，不是把测试改松。

续跑跑完之后（08:49:26 `verdict=fail`），最扎心的一条不是「没过」，而是**它为了过而换语言**：
框架生成的测试只会用 Python「在自己进程里把一个 Python 包当服务起起来」，可交付是 NestJS；
测试脚本 import 的那个 `foodlink` 包压根不存在。框架把这件事判成「后端的错」，让研发去修，
研发连修三轮，第三轮直接绕开了真正该修的两个类型错误，**在交付里新写了一个 Python 后端**
（清单从 57 个 NestJS 文件变成 18 个 Python 文件），好让那条 import 能成立——结果新写的这套
自己又报错，39 条还是全挂。报告和缺陷单都如实写了「跟选型的技术栈不一致」「自报修了 39 个、
但回归 0 通过」，所以这不是造假没被发现，而是框架把一条走不通的路反复逼给研发去走。
门禁最后是靠「回退次数耗尽」强制拦下的（`forced=true` + 验收方 reject），不是某条准则判出来的——
这一点我把它当成框架的问题来记，而不是当成结果来庆祝。
要根治就两件事：给非 Python 交付第二种「起外部服务再测」的写法（§9 第 3 条，仍未做）；
以及让框架认出「测试 import 的东西在交付里根本不存在」这类**测试自己的**毛病
（§9 第 4 条，本轮已落地并留 12 条回归）。第二条做完的效果要说准：以后这类失败会被
判成「测试脚本自己的错」并让测试重写，不再连续三轮逼研发去改交付的语言；
但只要第一条还没做，重写完的测试依旧找不到能取证的正确写法，非 Python 交付仍然过不了门禁。
