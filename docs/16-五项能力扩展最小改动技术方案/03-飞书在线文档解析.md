# 03 · 飞书在线文档解析（飞书文档作为需求输入）

> 行号基准：2026-10-15 逐行核实。未核实项标注「待验证」。

## 1. 结论

**新建 `mas/sources.py` 输入适配层，在 `Leader.run()` 入口把飞书 URL 解析成 `(title, text)`，
汇入现有 `load_requirement()` 的返回签名——下游零改动。**
项目内目前**没有任何飞书代码**（全仓 grep `feishu/lark` 零命中）；WorkBuddy 宿主侧的飞书 connector
是插件进程，本项目 Python 进程调不到，必须**自发自收**（stdlib urllib 直连飞书 OpenAPI，保持零依赖）。
凭据走 `${VAR}` 环境变量展开（复用 `mas/mcp.py:75` 的 `expand_env`，不重写），
配置放新文件 `config/inputs.yaml`（照抄 `mcp.yaml` 的按需加载模式，**零改 `config.py`**）。

## 2. 现状核实（已核实的代码事实）

| 事实 | 位置 |
|---|---|
| 需求输入只有两种：`--text` 文字 / 文件路径；都不是则报 ConfigError | `mas/config.py:738-748` `load_requirement` |
| `Leader.run` 的输入段已有现成的 ConfigError 处理通道（失败 → run_summary verdict=fail + 事件） | `mas/leader.py:131-140` |
| 全仓无 feishu/lark 任何代码 | grep 零命中 |
| `${VAR}` 展开 + 「变量未设置即报错并指出变量名」已实现 | `mas/mcp.py:75-82` |
| 配置文件按需加载模式（`config/mcp.yaml` 由 `mcp.py:91` 直读，不经 `load_config` 的 bundle 白名单） | `mas/mcp.py:87-99`；`mas/config.py:602-611` |
| `load_config` 的 bundle 只收 `system/llm/runtime/files/flow/collaboration/learning/roles` 七个键——**新顶层配置段会被静默丢弃** | `mas/config.py:602-611` |

**结论：新配置必须走「独立 yaml + 按需加载」或「塞进已有段」两条路之一，不能直接加顶层键。**

## 3. 方案设计

### 3.1 数据流

```text
CLI: python -m mas run -r "https://xxx.feishu.cn/docx/AbCdEf..."    前端: 输入框粘飞书链接
        │
        ▼
Leader.run() 输入段                       mas/leader.py:131
        │  sources.classify_source(value)  ← L1 规则判定（确定性）
        │    命中 feishu.cn / larksuite.com 域名 + /docx/|/docs/|/wiki/ 路径 → "feishu"
        ▼
sources.fetch_feishu_document(url, creds)          mas/sources.py
        ① POST /open-apis/auth/v3/tenant_access_token/internal   {app_id, app_secret}
             → tenant_access_token（进程内缓存至过期前 60s）
        ② wiki 链接先 GET /open-apis/wiki/v2/spaces/get_node?token=<wiki_token>
             → obj_token + obj_type；非 docx 类型如实报错（sheet/幻灯片等不支持）
        ③ GET /open-apis/docx/v1/documents/{document_id}/raw_content
             → 纯文本正文
        ▼
(title, text) 以与 load_requirement() 完全一致的签名返回   mas/config.py:738
        ▼
run_dir/input/requirement.md 落盘 + requirement_source 发布（source 标记为 "feishu"）   leader.py:141-147
        ▼
intake → requirement_spec → 下游全部零改动
```

### 3.2 接入位置与模块边界

| 层 | 位置 | 职责 |
|---|---|---|
| 源分类（L1 规则） | `mas/sources.py:classify_source` | 确定性：只认域名+路径形状，不联网 |
| 抓取 | `mas/sources.py:fetch_feishu_document` | 三个 HTTP 调用 + token 缓存 + 错误翻译 |
| 入口挂载 | `mas/leader.py:131-147` | 识别 → 抓取 → 失败走既有 ConfigError 通道 |
| 凭据 | `config/inputs.yaml` + `expand_env` 复用 | 不落明文 |
| 留痕 | `events.emit("input_source_fetched", ...)` | doc_id/obj_type/title/chars |

**边界原则：飞书只影响「text 从哪来」，不影响 text 之后的一切。**
`requirement_source.source` 字段从 `"file"|"text"` 扩为 `"file"|"text"|"feishu"`，
该字段目前只作记录用途（grep 确认无门禁/分支依赖），扩值安全。

### 3.3 文件级改动清单

| 文件 | 位置 | 改动 | 估算行数 |
|---|---|---|---|
| `mas/sources.py` | 新文件（P0 建骨架，P2 填飞书） | `classify_source` / `fetch_feishu_document` / token 缓存 / URL 解析（docx_id、wiki_token）/ 错误翻译（code+msg → 中文可读） | ~150 |
| `mas/leader.py` | `run`（131-147） | 识别飞书 URL → 抓取 → `(title, text)` 汇入现有落盘与发布逻辑；发 `input_source_fetched` 事件 | ~12 |
| `config/inputs.yaml` | 新文件 | `feishu: {enabled, api_base, app_id: "${FEISHU_APP_ID}", app_secret: "${FEISHU_APP_SECRET}", timeout_s: 15}`；`api_base` 默认 `https://open.feishu.cn`，国际版 Lark 填 `https://open.larksuite.com` | ~15 |
| `.gitignore` | — | 确认 `config/inputs.yaml` 若含明文凭据需忽略；推荐只放 `${VAR}` 引用则可不忽略（与 mcp.yaml 同策略） | 0 |

`load_requirement()`（`config.py:738`）**不改**——飞书在 Leader 入口已完成「URL → text」，不必入侵它。

### 3.4 对现有流程的影响

- 非飞书 URL（文件路径/文字/其他 http 链接）行为不变：`classify_source` 不命中即走原路。
- 飞书抓取失败（无凭据/403/404/超时）→ 走 `leader.py:136-140` 既有 ConfigError 通道，
  run 以 verdict=fail 结束并带明确错误信息，**不拖垮其他输入模式**。
- 网络依赖：离线/HPC 环境本来也拉不了飞书，失败即如实失败。

### 3.5 实现风险

| 风险 | 等级 | mitigations |
|---|---|---|
| **raw_content 只返回纯文本**：飞书文档里的表格（变空格拼接）、图片（丢失）、代码块（丢失语言标记） | 高 | 一期接受（需求文档以文字为主）；表格保真列为二期 blocks 递归拉取，方案预留 `fetch_mode: raw_content\|blocks` 配置位 |
| 飞书应用权限不足（docx:readonly scope 未开）→ 403 | 中 | 错误信息带 code/msg 原文；探测脚本先验证权限再谈默认开 |
| wiki 链接需要先解析 node，且可能指向非 docx 对象 | 中 | 非 docx 如实报错并说明支持范围 |
| app_secret 泄露 | 中 | 只走 `${VAR}` + 环境变量；`inputs.yaml` 模板只放占位符；事件与日志不打印 secret |
| API 字段名/行为与文档不符（待验证） | 中 | §3.6 探测脚本先跑通再写实现；实现里对 `code != 0` 一律报错不猜 |

### 3.6 验证方式

**凭据与 API 探测（P2 第一步，先于实现）**：

```bash
export FEISHU_APP_ID=cli_xxx FEISHU_APP_SECRET=yyy
python - <<'PY'
import json, os, urllib.request
# ① tenant_access_token
req = urllib.request.Request("https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal",
    data=json.dumps({"app_id": os.environ["FEISHU_APP_ID"],
                     "app_secret": os.environ["FEISHU_APP_SECRET"]}).encode(),
    headers={"Content-Type": "application/json"}, method="POST")
tok = json.loads(urllib.request.urlopen(req, timeout=15).read())["tenant_access_token"]
# ② raw_content（把 <doc_id> 换成真实文档 id）
doc = urllib.request.Request(
    "https://open.feishu.cn/open-apis/docx/v1/documents/<doc_id>/raw_content",
    headers={"Authorization": f"Bearer {tok}"})
body = json.loads(urllib.request.urlopen(doc, timeout=15).read())
print("code:", body.get("code"), "| content chars:", len((body.get("data") or {}).get("content") or ""))
PY
```

**单测**（tests/test_sources.py）：本地 HTTP 桩按序返回 token → raw_content，
断言 `fetch_feishu_document` 的 title/text/doc_id 提取与错误翻译（桩模式参照 `tests/fake_mcp_server.py`）。

**端到端**：`python -m mas run -r "https://<tenant>.feishu.cn/docx/<doc_id>"`，
检查 `input/requirement.md` 正文、`requirement_source` 的 `source="feishu"`、事件流里的 `input_source_fetched`。

### 3.7 验收标准

1. 探测脚本跑通（真实 app + 真实文档），结论（含表格丢失程度）记录到本文档「实验记录」节；
2. 无凭据环境下运行飞书 URL：明确报错「缺少 FEISHU_APP_ID/FEISHU_APP_SECRET」，不影响其他输入模式；
3. 单测覆盖 token 失败 / 403 / 404 / 非 docx 对象四条错误路径。
