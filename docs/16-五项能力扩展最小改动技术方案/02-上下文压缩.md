# 02 · 上下文压缩（Prompt 上下文治理）

> 行号基准：2026-10-15 逐行核实。未核实项标注「待验证」。

## 1. 结论

**现有「压缩」只有一处：`blackboard.brief()` 的无结构硬截断（超长直接切字符串，JSON 被切坏）。**
最小方案是新建 `mas/compress.py` 做**结构化规则压缩**，挂在 `BaseAgent.perceive` 内、`brief()` 之前；
外加 tool 结果的统一截断（约 12 行）。LLM 摘要压缩列为可选第二步，**默认关闭**
（每一次新增 LLM 调用都是新增一份 300s 网关超时风险，这是本项目最硬的约束）。
默认 `runtime.context_compression.enabled=false`，行为与现状一致。

## 2. 现状核实（已核实的代码事实）

| 事实 | 位置 |
|---|---|
| 感知段压缩 = `brief()` 硬截断：`payload[:max_chars] + "...(截断, 共 N 字符)"`，JSON 中间切坏 | `mas/blackboard.py:180-193` |
| 单产物预算来自 `runtime.prompt_artifact_max_chars`（当前 10000），历史上 900 会把 12 功能点的规格截到只剩 3 个 FP 片段 | `mas/agents/base.py:229-232`；`config/system.yaml:91` |
| **没有「跨节点对话历史」需要压缩**：每个节点都是单轮 `generate`，无多轮消息历史 | `mas/llm.py:139-159`；`mas/agents/base.py:104-142` |
| 经验注入已有成熟的 token 预算机制（分层 budget + 总量 budget + 超预算跳过）——**现成的参照实现** | `mas/experience.py:316-380`；`config/learning.yaml:16-36,65-71` |
| function calling 的 `extra_messages`（tool 结果）**无任何截断**，`tool_max_rounds=2` 时两轮工具结果可无限增长 | `mas/agents/base.py:120-141` |
| `_estimate_tokens` 只做估算展示，不参与裁剪 | `mas/prompts.py:209-216` |
| `TRACE_LIMIT` 只截断落盘的 trace，不影响发给模型的 prompt | `mas/agents/base.py:163,185-186` |

**结论：上下文压缩的真正对象是三段——感知段（artifact brief）、经验注入段（已有预算）、tool 结果段（无预算）。
最小改动只需要补第一段的结构化和第三段的截断。**

## 3. 方案设计

### 3.1 数据流

```text
BaseAgent.perceive()                        mas/agents/base.py:226
    found, missing = blackboard.require(names)
        │
        ▼  【新增】compress.found_artifacts(found, budget)   ← enabled=false 时原样返回
    mas/compress.py:
        按 artifact 名分派压缩策略（白名单制，未知名保持现状硬截断）：
          requirement_spec → 保 FP 的 id/title/rules/category/acceptance；超预算丢 samples/parameters
          test_report      → 保 summary/coverage counts；丢逐条明细
          review_report    → 保 verdict/blocking 计数与 blocking_items；丢 findings 明细
          bug_reports      → 保 open 计数与 open items；丢 closed
        │
        ▼
blackboard.brief(compressed, max_chars_per_item)     base.py:232（不变）
        │
        ▼
prompt 感知段（结构完整、可被 LLM 正确解析的 JSON 片段）
```

tool 结果截断（同一阶段）：

```text
base.py:140  extra_messages.extend(runner.execute(calls))
        │
        ▼  【新增】truncate_tool_results(messages, max_chars=runtime.tool_result_max_chars)
        头尾保留（前 60% + 后 40%），中间标注「省略 N 字符」
```

### 3.2 接入位置与模块边界

| 层 | 位置 | 边界 |
|---|---|---|
| 压缩策略 | `mas/compress.py`（新） | 纯函数 + 策略表；**不 import LLM**（第一步），可单测 |
| 挂载 | `mas/agents/base.py:226-234` `perceive` | 唯一调用点，五个角色 Agent 统一生效 |
| tool 截断 | `mas/agents/base.py:140` 后 | 只在 tools 开启时生效 |
| LLM 摘要（可选） | `compress.py` 内 + `ctx.llm` | 默认关；开启时 task_kind="compress"，落盘 prompts/ 留痕 |

**边界原则：压缩只改「进 prompt 的内容」，绝不改黑板上的 artifact 数据。**
门禁求值走 `blackboard.snapshot()`（`leader.py:418`），与压缩完全隔离——压缩出错不可能刷绿门禁。

### 3.3 文件级改动清单

| 文件 | 位置 | 改动 | 估算行数 |
|---|---|---|---|
| `mas/compress.py` | 新文件 | 策略表 + `found_artifacts()` + `truncate_tool_results()` + 压缩统计返回（before/after 字符数） | ~120 |
| `mas/agents/base.py` | `perceive`（226-234） | 调 `compress.found_artifacts`；发 `context_compressed` 事件（含 before/after） | 10 |
| `mas/agents/base.py` | `_generate_with_tools`（140 后） | tool 结果截断 | 4 |
| `config/system.yaml` | `runtime:` 段 | `context_compression: {enabled:false, per_item_chars:10000, total_chars:32000, llm_summary:false}` + `tool_result_max_chars: 4000` | 7 |
| `mas/compress.py`（可选第二步） | LLM 摘要 | `llm_summary=true` 时对仍超预算的 artifact 调一次 LLM 生成摘要；失败回落规则压缩 | ~40 |

### 3.4 对现有流程的影响

- **默认零影响**：`enabled=false` 时 `found_artifacts` 恒等返回，`tool_result_max_chars` 对无 tools 的运行不触发。
- 开启后只改变 prompt 感知段文本；artifact、门禁、事件流（除新增的 `context_compressed`）均不变。
- 收益可量化：同一需求开启前后，prompt 文件中「功能点 id 出现数」「JSON 可解析性」直接可 diff。

### 3.5 实现风险

| 风险 | 等级 | mitigations |
|---|---|---|
| 压缩丢关键信息 → 下游节点质量下降（如丢了某 FP 的 rules，实现漏规则） | **高** | 白名单制：只压已知 artifact；spec 的 FP id/title/rules 永不丢；用 §3.6 的 12FP 实验定量对比后再开 |
| 策略表与 schema 演进脱节（新增 artifact 类型忘了加策略） | 中 | 未知名保持现状硬截断 + `context_compressed` 事件里记录未压缩项，可审计 |
| LLM 摘要引入新的失败模式（超时/空摘要/摘要失真） | 中（仅开启后） | 默认关；开启时摘要失败必须回落规则压缩，且事件留痕 |
| 双预算（per_item 与 total）交互复杂 | 低 | 先按 per_item 压，再按 total 优先级裁剪（spec > solution_design > review/test 明细），优先级写进配置 |

### 3.6 验证方式

**12 功能点对比实验**（P4 核心，直接复用历史教训场景）：

1. 构造/选用一个 12 功能点的需求文档（记忆中的 attempt03 场景：900 字符预算会把 12 FP 截到 3 个片段）；
2. 关闭压缩跑一次 → 记录 `prompts/` 中各 FP id 出现次数、prompt 字符数、门禁结果；
3. 开启压缩（同样预算）跑一次 → 同样记录；
4. 通过标准：开启后 FP id 覆盖数**不低于**关闭时、prompt 更短或相当、验收结论不变差。

**单测**（tests/test_compress.py）：
- `requirement_spec` 压缩后 JSON 仍可解析、FP id/title/rules 全保留、samples 被丢；
- 预算 0 / 负数 / artifact 为 null 或标量时不抛异常；
- `truncate_tool_results` 头尾保留语义。

**回归**：`python -m unittest discover -s tests`（重点看 `tests/test_token_budget.py` 是否被压缩改动波及）。

### 3.7 验收标准

1. 默认关闭时，任取一次历史运行的 prompt 文件与开启配置前的版本逐字节一致；
2. 12FP 实验通过标准达成，数据写入 `docs/16-五项能力扩展最小改动技术方案/02-上下文压缩.md` 的「实验记录」节；
3. `context_compressed` 事件在开启后每次 perceive 均出现，字段含 before/after 字符数。

## 实验记录（2026-10-15 本机实测）

**§3.6 的 12 功能点对比实验**（构造方式：示例 `order_pricing_service.md` 的 7 个 FP 块 + 复制 FP-01..FP-05
为 FP-08..FP-12，offline provider，`per_item_chars=10000 / total_chars=32000`）：

| 配置 | 验收 | 步数 | prompt 文件数 | prompt 总字符 | 出现的 FP id 数 |
|---|---|---|---|---|---|
| 关闭压缩 | 未通过 | 17 | 19 | 459537 | 12 |
| 开启压缩 | 未通过 | 17 | 19 | **389733** | 12 |

- 通过标准：FP id 覆盖 **12 ≥ 12（满足）**；prompt 字符 **389733 ≤ 459537（满足，约 -15.2%）**；
  验收结论 **未通过 == 未通过（不变差，满足）**。
- 说明（如实）：两轮均为「未通过」，原因是该人工构造文档里复制出的 FP-08..FP-12 与 FP-01..FP-05 映射到
  **同一个算子**，测试覆盖率按 FP id 去重统计时无法覆盖后 5 个 id —— 这与压缩无关。因此本实验证明的是
  「压缩不降低 FP 覆盖、显著缩短 prompt、不改变结论」，**不是**一次通过态的对照。

**其余验收项**：
1. 默认（`enabled=false`）时 `found_artifacts` 恒等返回、`tool_result_max_chars` 默认 0 不截断，
   存量 260 条 unittest 全绿（含 `test_token_budget` / `test_pipeline`），默认路径与改造前一致；
2. `context_compressed` 事件在开启后每次 perceive 均出现，实测单次运行 7 条，字段含 before/after 字符数；
3. 压缩只改 Prompt 文本，不改黑板 artifact：真实运行 acceptance gate 仍判 `passed=true`；
4. `tests/test_compress.py` 覆盖：spec 保 id/title/rules、丢 samples/parameters；预算 0/负数/null/标量不抛异常；
   test_report/review_report/bug_reports 策略；`truncate_tool_results` 头尾语义与关闭恒等。
