# 01 · 图片输入（多模态需求输入）

> 行号基准：2026-10-15 逐行核实。未核实项标注「待验证」。

## 1. 结论

**图片作为需求附件进入 intake 一个节点，改动集中在 `llm.py` 的 payload 组装处（约 35 行）与 `leader.py` 的输入段（约 15 行）。**
下游节点感知的是 `requirement_spec`（纯文本），天然不接触图片，模块边界由现有数据流自动保证。
默认 `llm.vision.enabled=false` 且无图片传入时，`_build_payload` 输出与现状**逐字节一致**。

## 2. 现状核实（已核实的代码事实）

| 事实 | 位置 |
|---|---|
| `requirement_source` artifact 只有 `{title, text, source, chars, run_id}`，无附件字段 | `mas/leader.py:142-147` |
| `ProductAgent.build_context` 只取 `source.get("text")` | `mas/agents/product.py:55-65` |
| `_build_payload` 的 messages 恒为 `[system, user]` 两条纯文本 | `mas/llm.py:258-261` |
| `generate()` 收到 `context` 但只转给 offline provider，**没有传进** `_build_payload` | `mas/llm.py:139-159`（openai 分支 `llm.py:152`） |
| offline provider 完全不走 HTTP，图片对它无意义 | `mas/llm.py:162-175` |
| 4xx 错误在 `_post_with_retry` 直接抛 `AgentError`（不重试），冒泡到 `act()` 变节点失败 | `mas/llm.py:446-447`；`mas/agents/base.py:86-92` |
| CLI 与前端均无图片入口 | `mas/cli.py:405-414`；`frontend/server.py:450-467` |

## 3. 方案设计

### 3.1 数据流

```text
CLI --image a.png --image b.jpg                前端（P1 的 /api/upload 之后可选扩展）
        │
        ▼
Leader.run(..., images=[Path])      mas/leader.py:89（新增关键字参数，默认 None）
        │  校验：后缀白名单 {.png,.jpg,.jpeg,.webp,.gif} + 单张 ≤ 5MB
        ▼
复制到 run_dir/input/images/<name>；发布 requirement_source 时增加字段：
    "images": [{"name","path"(相对 run_dir),"mime","bytes"}]     leader.py:142-147
        ▼
ProductAgent.build_context 把 images 放进 context      product.py:55-65
        ▼
prompts.py 的 user prompt 追加一段「附图 N 张（路径…）」说明（留痕，人可审查）   prompts.py:180 附近
        ▼
LLMClient.generate(context=...) → _build_payload(bundle, context=...)   llm.py:152/250
        当 context["images"] 非空且 llm.vision.enabled：
        user.content = [
            {"type":"text","text":bundle.user},
            {"type":"image_url","image_url":{"url":"data:<mime>;base64,<...>"}},  # 从 run_dir 拼路径读文件
            ...
        ]
        ▼
400 且错误详情含 image/multimodal/vision 字样 → 去图重发一次（degraded=True + 事件留痕）
```

### 3.2 接入位置与模块边界

| 层 | 位置 | 职责边界 |
|---|---|---|
| 输入采集 | `Leader.run` + CLI `--image` | 只做校验与落盘，不碰 LLM |
| 数据承载 | `requirement_source.images` | 存元数据与相对路径，**不存 base64**（避免 artifact 膨胀） |
| Prompt 留痕 | `prompts.py` | 只加文字说明，不改契约字段 |
| 多模态组装 | `llm.py:_build_payload` | 唯一知道「怎么把图片变成 API parts」的地方；读文件+base64 在此完成 |
| 降级 | `llm.py:_generate_openai` | 端点不支持时去图重发，节点不失败 |

**边界原则：图片只进 intake。** 其他节点的 `perception` 拿的是 `requirement_spec`，看不到图片——
不需要给每个 agent 加「忽略图片」的逻辑。

### 3.4 对现有流程的影响

- **默认零影响**：`vision.enabled=false` 或无图片时，payload 结构与现在一致；offline provider 路径不变。
- 开启后仅 **intake 一次生成**的 payload 结构变化；下游全部节点不变。
- `_generate_openai` 的去图重试只在「带图且 400」时触发，不影响无图路径。

### 3.5 实现风险

| 风险 | 等级 |  mitigations |
|---|---|---|
| **端点不接受 image_url parts（待验证）** | 高 | 见 §3.6 探测；400 降级路径保证「最坏退化成无图运行 + 事件告警」，节点不失败 |
| 图片 base64 使 payload 暴涨，可能触发网关/模型输入上限 | 中 | 单张 5MB 上限 + 张数上限（建议 ≤4，Leader 校验时截断并告警）；探测阶段同时验证大图行为 |
| data URI 与部分端点的 `image_url` 字段格式差异（有的要裸 base64） | 中 | 格式集中在 `_build_payload` 一处，探测后按端点调整；配置项 `vision.url_style: data_uri\|raw_base64` 预留 |
| 图片含敏感信息随 prompt 外发 | 低 | 上传即明示（前端提示 + 事件留痕）；不额外处理 |

### 3.6 验证方式

**端点兼容性探测（P3 第一步，必须先做）**：

```bash
# 最小 multimodal 请求：一张 1x1 png + 一句问话，max_tokens=16，流式
python - <<'PY'
import base64, json, urllib.request
png = base64.b64decode("iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR42mP8z8BQDwAEhQGAhKmMIQAAAABJRU5ErkJggg==")
body = {"model": "DeepSeek", "stream": True, "max_tokens": 16,
        "messages": [{"role": "user", "content": [
            {"type": "text", "text": "describe"},
            {"type": "image_url", "image_url": {"url": "data:image/png;base64," + base64.b64encode(png).decode()}}]}]}
req = urllib.request.Request("https://api.chat.csu.edu.cn/v1/chat/completions",
    data=json.dumps(body).encode(), method="POST",
    headers={"Content-Type": "application/json", "Authorization": "Bearer <KEY>"})
try:
    with urllib.request.urlopen(req, timeout=120) as r:
        print("HTTP", r.status, r.headers.get("Content-Type"))
except urllib.error.HTTPError as e:
    print("HTTP", e.code, e.read().decode()[:400])
PY
```

判定：200 且能读到 SSE → 端点支持，`vision.enabled` 可开；400 且 detail 提及 image/multimodal → 端点不支持，
能力降级为「图片存档 + 文字说明」，**不允许为了让门禁通过而谎称读图**。

**单测**（tests/test_vision.py）：
- `_build_payload` 在 images 非空 + enabled 时产出 parts 结构（桩 Generation 不断网）；
- 400 + "image" detail → 去图重发一次且 `degraded=True`；
- 无图 / disabled 时 payload 与改动前一致（快照断言）。

**端到端**：`python -m mas run -r examples/requirements/order_pricing_service.md --image <真实截图>`，
检查 `run_dir/input/images/` 落盘、`requirement_source` v1.json 的 images 字段、`llm_traces.jsonl` 的 degraded 标记。

### 3.7 验收标准

1. 探测结论写入本文档（支持/不支持/部分支持），`vision.enabled` 按结论设默认值；
2. 不支持的端点下，带图运行**验收结论与无图运行一致**（不谎报、不失败）；
3. `python -m unittest discover -s tests` 全绿，offline demo 不受影响。

## 实验记录（补充 2026-10-16：前端对话窗口图片上传）

**缺口分析**：流水线侧（`Leader.run(images=)` / `prepare_images` / 多模态 payload）在 10-15 已落地，
但 HTTP 与 UI 层没接通——`/api/upload` 的白名单（`UPLOAD_SUFFIXES`）不含图片后缀，
`/api/run` 没有 images 字段，对话窗口没有选择/展示图片的组件。

**最小改动（5 处，全部可单独回滚）**：

| 文件 | 改动 | 必要性 / 对现有功能的影响 |
|---|---|---|
| `mas/sources.py` | `save_upload` 增加 `allowed_suffixes` / `max_bytes` 覆盖参数 | 图片上传复用同一套校验与落盘；不传参数时契约逐字节不变（需求文档路径零影响） |
| `frontend/server.py` | 新增 `POST /api/upload_image`（白名单=`IMAGE_SUFFIXES`、单张 5MB，落盘 `workspace/uploads/`，`kind` 恒为 `"image"`） | 与 `/api/upload` 白名单隔离，两条通道互不回归 |
| `frontend/server.py` | `start_run` 增加 `images` 透传 `Leader.run(images=...)`；`/api/run` 校验 images 为字符串数组（400 明示） | 附件必须到达流水线；后缀/大小/张数语义仍由 `prepare_images` 单一负责 |
| `frontend/index.html` / `app.js` / `style.css` | composer 增加「上传图片」按钮（多选）+ 缩略图托盘（可移除）；消息气泡内缩略图展示（点击新标签页放大）；发送时 `images=[paths]` 随需求提交 | 对话窗口「选择→上传→发送→展示」闭环；`state.images` 与既有 `state.upload`（文档）并列，互不干扰 |
| `tests/test_upload.py` | +15 条：覆盖参数（图片放行/默认仍拒/大小/穿越名）、`upload_image` 路由（合法/文档后缀/超限/空文件名）、未知路由 404、`/api/run` 的 images 校验、`start_run` 透传（Leader 打桩，不触网） | 新链路覆盖 + 旧契约回归 |

**边界（有意设计）**：图片是**附图**——单独发图片不构成可执行需求，`/api/run` 仍要求文字或文档
（错误信息已明示）；读图能力仍由 `llm.vision.enabled`（默认 false）把门，本项不改变该默认值，
「对话中展示」= 客户端缩略图 + 流水线存档 + 事件留痕，不谎称读图。

**实测（2026-10-16，真实 server 子进程 + offline provider，17 项检查全过）**：
上传 PNG 200（`kind=image`）/ `.md` 400；`/api/upload` 逐项不变（md 200、png 400）；
`/api/run` 带文字+图片 → 122 条事件、`requirement_images_attached` 在场、
`requirement_source.images` 元数据正确（mime/bytes/相对路径，无 base64）、
图片复制进 `run_dir/input/images/`、验收 pass；`/` 与 `/app.js` 返回带新 UI 的资源。
全量 unittest **275 条全绿**（原 260 + 15）。

**顺带发现的既有缺陷（本次未改，记录备修）**：`runtime.verbose` 默认开启时 server 会把每条事件
echo 到 stdout；若 server 以「无人读取的管道」启动（如被服务管理器捕获输出），缓冲区写满后
`print` 永久阻塞，运行静默卡在报告阶段（faulthandler 栈定位在 `events.py` 的 echo）。
处置：启动 server 时将 stdout 重定向到文件，或对该场景关闭 `runtime.verbose`。
