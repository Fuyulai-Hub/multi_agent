# 04 · 文档上传（前端上传需求文档）

> 行号基准：2026-10-15 逐行核实。未核实项标注「待验证」。
> **解析层选型已升级**：docx 及 PDF/pptx/xlsx 等格式的解析采用「stdlib 默认 → MCP 增强 → 明确失败」
> 三级路由，评估依据与配置示例见同目录 `06-MCP文档解析接入评估.md`，本文档已按该结论修订。

## 1. 结论

**前端加一个 `POST /api/upload`（JSON + base64，绕开 multipart 解析），落盘到 `workspace/uploads/`，
再让现有的 `/api/run` 带上 `requirement_path` 走 Leader 已有的文件通道——两段式时序，不动 run 生命周期。**
`.md/.txt/.markdown/.csv/.json` 与 `.docx` 用 stdlib 直接处理（零依赖默认路径）；
**PDF/pptx/xlsx 等改为「MCP 可选支持」**：配置了文档解析 MCP 服务（如 markitdown-mcp）即可解析，
未配置则如实报错（详见 06 文档）——不引第三方 pip 依赖进主项目。

## 2. 现状核实（已核实的代码事实）

| 事实 | 位置 |
|---|---|
| `POST /api/run` 只解析 JSON body，取 `requirement` 字符串 | `frontend/server.py:418-424,450-467` |
| `start_run()` 固定 `as_text=True`，前端只能传文字 | `frontend/server.py:335` |
| CLI 已有文件通道：`load_requirement` 按路径读文件（utf-8） | `mas/config.py:738-748` |
| 前端发送逻辑：读 textarea → JSON POST → 清空输入框 | `frontend/app.js:554-582` |
| `Leader.run` 会把需求原文落盘 `run_dir/input/requirement.md` 并发布 `requirement_source`（source="file"） | `mas/leader.py:141-147` |
| Python 3.13 已移除 `cgi` 模块，stdlib 解析 multipart 需手写 email parser——不最小 | 运行时事实 |

**结论：上传的落点不在「新造一条输入链」，而是「让前端也能用上 CLI 早就有的文件通道」。**

## 3. 方案设计

### 3.1 数据流（两段式）

```text
第一段：上传（建 run 之前）
前端 FileReader 读文件 → base64
        │  POST /api/upload {filename, content_base64}
        ▼
frontend/server.py do_POST 新增分支           server.py:413
        校验：后缀白名单 / 解码后 ≤10MB / 文件名净化（Path(name).name + 去控制字符）
        落盘 workspace/uploads/<upload_id>__<safe_name>
        ▼
返回 {upload_id, path, name, kind, chars}

第二段：发起运行
前端 POST /api/run {..., requirement_path: "<上一步返回的 path>"}
        ▼
start_run(..., requirement_path)               server.py:301
        │  requirement_path 非空 → Leader.run(path, as_text=False)（走文件通道）
        ▼
Leader.run → load_requirement(path)            config.py:738
        │  sources.extract_text(path) 三级路由（详见 06 文档 §4.1）：
        │    L1 stdlib：.md/.txt/.csv/.json 直读；.docx 用 zipfile+ElementTree 抽取
        │    L2 MCP   ：后缀命中 inputs.yaml 的 document_parse.formats → MCPClient.call_tool 抽 content 文本
        │    L3 失败  ：都不支持 → ConfigError 如实报错
        │  （抽取在 Leader 落盘 input/requirement.md 前完成；不入侵 load_requirement，config.py 零改）
        ▼
input/requirement.md（抽取后的文本）+ requirement_source(source="file") → intake
```

> 为什么 base64 JSON 而不是 multipart：Python 3.13 没有 `cgi`，手写 multipart parser 约 80 行且易错；
> base64 JSON 前后端各 10 行，代价是体积 +33%（10MB 文件约 13.3MB，本地回环可接受）。

### 3.2 接入位置与模块边界

| 层 | 位置 | 边界 |
|---|---|---|
| 上传接收 | `frontend/server.py` `do_POST` + 新函数 `save_upload()` | 只做校验+落盘，不启动任何运行 |
| 文档抽取 | `mas/sources.py:extract_text`（P0 与飞书共用文件） | 三级路由（stdlib / MCP / 明确失败）；MCP 部分是框架直调 `MCPClient.call_tool`，不走模型 function calling（理由见 06 文档 §4.2）；失败抛 `ConfigError` |
| 运行串联 | `frontend/server.py:start_run` + `Leader.run` 调用处 | `requirement_path` 为空时行为与现状逐字节一致 |
| 前端 | `index.html` 加 `<input type="file">` + `app.js` 上传/带参逻辑 | 不上传时 UI 行为不变 |

**边界原则：上传目录（`workspace/uploads/`）与运行目录（`workspace/runs/<id>/`）分离**，
上传是「暂存」，run 启动时才读入；过期暂存文件的清理列为后续项（最小方案不自动删，UI 可见）。

### 3.4 对现有流程的影响

- 不上传文件时，前端与后端行为与现状**逐字节一致**（`requirement_path` 缺省为空）。
- 上传后走的是 CLI 同款文件通道，`requirement_source.source="file"`，下游无感知。
- 抽取（stdlib 或 MCP）在 Leader 落盘前完成，`input/requirement.md` 始终是 UTF-8 纯文本。
- MCP 解析是**框架侧行为**：offline provider 同样可用，与 `llm.tools_enabled` 无关
  （不走模型 function calling，不触发 json_mode 冲突，详见 06 文档 §4.2）。

### 3.5 实现风险

| 风险 | 等级 | mitigations |
|---|---|---|
| docx 抽取丢失结构（表格拼成空格、文本框/页眉页脚丢失、图片丢失） | 高 | 如实标注：抽取结果头部加一行「本文档由自动抽取，表格与图片可能丢失」；保真度用真实 docx 验证后记录 |
| 文件名路径穿越（`../../etc/x`）写越界 | 高 | `Path(name).name` 取 basename + 拒绝含 `..`/绝对路径/控制字符 + 落盘前 resolve 校验在 uploads 目录内 |
| 大文件打爆内存/磁盘 | 中 | 10MB 硬上限（base64 解码后判定）；超限 400 |
| **PDF 在未配置 MCP 解析服务时不可用** | 中 | 上传放行（白名单包含 pdf）但运行时明确报错「格式 .pdf 需要配置文档解析 MCP 服务（见 docs/16 06 文档）」；配置后即可用。**不再走「前端直接拒绝」**——拒绝与不可解析是两件事，前者剥夺了用户配置后重试的权利 |
| **MCP 解析发生在沙箱子进程之外**（`_StdioTransport` 直起进程，Windows 无 rlimit；上传 PDF 是不可信输入） | 高 | 缓解：格式白名单 + 大小上限；文档如实告知；彻底方案（parse server 也走 sandbox）需改传输层启动路径，明确不做，列为后续项（详见 06 文档 §6） |
| MCP server 契约不统一（有的返回输出文件路径而非文本 content） | 高 | 选型必须过 `python -m mas mcp check docparse --call convert_file --params '{...}'` 冒烟；适配层只契约化「返回文本 content」的 server（详见 06 文档 §6） |
| uploads 目录无限增长 | 低 | 一期不自动清（UI 可见、体积小）；二期加「按 mtime > 7 天清理」并先行告警 |

### 3.6 验证方式

**单测**（tests/test_sources.py / tests/test_upload.py）：
- `extract_text` 路由：手工构造最小 docx（zipfile 打包含 `word/document.xml`，含段落+表格），断言文本顺序与分段；路由表断言（pdf→MCP、md→stdlib、.psd→明确失败）；
- MCP 路径：fake parse server 桩（范本 `tests/fake_mcp_server.py`）覆盖正常 markdown / `isError=true` / 超时三条路径；
- `save_upload`：合法 .md / 越界文件名 / 超限 / 非法后缀 / 空文件五条用例。

**端到端**：前端分别传一个 .md 和一个真实 .docx → 检查 `workspace/uploads/` 落盘、
`runs/<id>/input/requirement.md` 内容、intake 产出的 spec 功能点数与原文一致。
PDF 端到端（需先按 06 文档 §7 完成选型冒烟）：未配置 docparse → 明确报错；配置后 → 抽取文本进 intake。

**攻击面手工用例**：
```bash
# 路径穿越（应被净化或拒绝）
curl -X POST localhost:8000/api/upload -H 'Content-Type: application/json' \
  -d '{"filename":"../../evil.md","content_base64":"aGk="}'
# MCP 解析服务选型冒烟（接入前置条件）
python -m mas mcp check docparse --call convert_file --params '{"file_path": "C:/path/real.pdf"}'
```

### 3.7 验收标准

1. 白名单内后缀可上传并跑通 intake；白名单外/超限/穿越名全部 400 且错误信息可读；
2. docx 抽取保真度结论（表格/图片丢失情况）记录到本文档「实验记录」节；
3. 不上传文件的既有前端流程零变化（diff app.js 改动确认分支互斥）；
4. MCP 路由：未配置 docparse 时 pdf 明确报错且不影响其他格式；配置后真实 pdf 跑通 intake，
   抽取字符数记入 06 文档「实验记录」节；
5. 默认配置（无 docparse）下全量 unittest + offline demo 与现状一致。
