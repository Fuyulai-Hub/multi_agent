# 前后端交付能力：意图路由 + A/B 档实施方案

> 本文所有结论均以 2026-10-15 逐行核实的代码为准，行号可直接定位。
> 未核实的内容一律标注为「待验证」，不作为方案依据。

---

## 1. 结论先行：A 与 B 不是覆盖关系

**判定：A 是必经基座，B 是叠加在基座之上的第二条证据通道。做了 B 不能免除 A，反而必须先有 A。**

逐项拆解 A 档的四个补丁，看 B 档是否需要它：

| A 档补丁 | B 档是否仍需 | 依据 |
|---|---|---|
| ① 网络模块按意图豁免 | **仍需，且更刚需** | B 档后端依旧是 Python 服务，`sandbox.py:542-555` 照样产出 `network_import` major finding，门禁 `review_report.blocking == 0` 照样可能被拦 |
| ② `_verification_gap` 判定修正 | **仍需，且更易踩坑** | `tester.py:425` 用 `"python" in language.lower()` 判定。B 档选型写成 `"TypeScript + React"` 就 gap=1、测试节点判 fail；写成 `"React + Python"` 则侥幸通过——判定依赖字符串巧合，两种形态都不可靠 |
| ③ import 约束（模块级不启动服务） | **仍需** | `developer.py:175` 的 `import {package}` 自检对后端包恒定生效 |
| ④ 端口管理 | **仍需，且要求更高** | A 档是「同进程自起自停」；B 档浏览器是**外部进程**，服务必须在测试进程之外存活 → A 档的端口约定是 B 的前置，但 B 还要额外新增「跨进程服务生命周期」 |
| 前端静态证据 | 必要性下降但**不会自动解决** | `sandbox.py:431` `_analyzable` 只认 `.py`，B 档补的是运行时证据，静态维度依旧空白 |

反向也要说清楚：**B 不会让 A 的「服务端渲染」形态变得多余。**
浏览器通道的成本（环境依赖、flaky、依赖 LLM 是否发起工具调用）远高于一次进程内 HTTP 请求。
对「只做后端」和轻量全栈需求启用浏览器是过度杀伤。所以 A 是默认路径，B 是按意图启用的增强路径。

一句话概括三者关系：

```
backend_only（现状）  ── 不改任何行为
        │
        ├── full_stack_ssr  ── 走 A 档：网络豁免 + 端口 + 判定修正 + import 约束 + 前端静态证据
        │
        └── full_stack_spa  ── 在 A 档之上再叠加 B 档：浏览器证据通道 + UI 用例汇入 cases
```

## 2. 现状核实：决定方案形态的三个硬事实

### 2.1 profile 在启动期决定，不能运行时切换

`config.py:579-623`：`load_config(config_dir, profile)` 读 `system.yaml` 的 `default_profile` 或 CLI 传入值，
profile 文件可覆盖 `flow`（`config.py:549` 支持 `skip: true` 摘除节点）。
但**意图只有等 intake 节点跑完才知道**，此时 profile 早已加载完毕。
→ **不能靠「按意图选 profile」来做流程拓扑分叉。**

### 2.2 flow.transitions 是固定映射，无条件路由

`flow.yaml:20` 等处形如 `transitions: { pass: solution, fail: halt }`，只有 pass/fail 两条边。
→ **不能按意图改流程拓扑**（除非改造 transitions 支持 expr，代价大且收益低）。

### 2.3 门禁表达式天然支持意图分支，但有一个陷阱

`leader.py:408-411`：`snapshot = ctx.blackboard.snapshot()`，criteria 的 expr 在**全量黑板快照**上求值，
可直接访问 `requirement_spec`。`expr.py` 支持 `==` / `!=` / `and` / `or`。
→ 门禁层做意图分支是**零代码**的。

**但陷阱在这里**：`expr.py:170-174` 的 `visit_BoolOp` 是

```python
values = [self.visit(value) for value in node.values]   # 先求全部值，再 all/any
```

**`or` 不是短路求值。** 若写成

```yaml
expr: "requirement_spec.delivery_shape != 'full_stack_spa' or ui_evidence.failed_asserts == 0"
```

当 `ui_evidence` 这个 artifact 不存在时，`_lookup` 抛 `_MissingField` → `evaluate` 返回
`ExprResult(ok=False)` → 该条 criterion `passed=False`，**即使当前是 backend_only 也会被判失败**。

影响面：现有全部历史任务的 spec 都没有 `delivery_shape`、也从未发布过 `ui_evidence`。
任何新增的门禁表达式只要引用了可能缺失的字段，就会让老任务验收失败。

**对策（必须同时做两条）**：

1. `requirement_spec` 落黑板前由框架注入默认值 `delivery_shape = "backend_only"`，
   保证字段恒定存在（`backend_only` 是安全默认值——它完全不改变现有行为）；
2. tester 节点在任何形态下都发布 `ui_evidence` artifact，
   `backend_only` / `full_stack_ssr` 时发布 `{enabled: false, failed_asserts: 0, asserts: []}`。

可选改进：让 `expr.py` 的 `BoolOp` 短路求值。`any/all` 的最终结果不变，
变化只是「左值已能确定结果时不再报字段缺失」。这属于通用改进，建议单独立项、单独回归，不与本方案捆绑。

## 3. 意图识别设计

### 3.1 字段定义

在 `requirement_spec` 中新增一个字段，三值枚举：

```yaml
delivery_shape: backend_only | full_stack_ssr | full_stack_spa
```

| 取值 | 含义 | 证据通道 | 现状 |
|---|---|---|---|
| `backend_only` | 纯后端（库 / CLI / 服务），无前端产物 | Python 测试 | 已支持，行为零变更 |
| `full_stack_ssr` | 前后端一起，服务端渲染 HTML | Python 测试断言响应体 | A 档目标 |
| `full_stack_spa` | 前后端一起，浏览器前端 | Python 测试 + 浏览器断言 | B 档目标，预留 |

### 3.2 三层识别（不把判定权全交给 LLM）

| 层 | 位置 | 性质 | 产出 |
|---|---|---|---|
| L1 规则预分类 | 新建 `mas/intent.py`，`classify_delivery_shape(text)` | **确定性**，纯关键词/句式 | `intent_hint` + 命中证据 |
| L2 LLM 判定 | `product` 节点（`mas/agents/product.py`）契约新增字段 | 概率性 | `delivery_shape` |
| L3 框架校验 | intake 节点 `apply` 内，发布前 | **确定性** | 非法值兜底 + 事件告警 |

**L1 规则层要点**（放进 `mas/intent.py`，不依赖任何 LLM）：

- 显式句式优先：`只做后端 / 仅后端 / 不需要前端 / 后端即可` → `backend_only`；
  `前后端 / 包含页面 / 要界面 / 前端也要` → `full_stack_*`。
- 无显式声明时走特征词：`接口 / SDK / 库 / 命令行 / CLI / 算法` → 偏 `backend_only`；
  `页面 / 前端 / 界面 / 浏览器 / 点击 / 表单 / UI / 网页` → 偏 `full_stack_*`。
- 冲突或全部未命中 → 返回 `unknown`，交由 L2 定夺，并在事件里记录命中词。
- L1 **只产提示不产结论**，不覆盖 L2。

**L2 契约改动**（`product.py:24-42` 的 contracts）：

```jsonc
"delivery_shape": "backend_only | full_stack_ssr | full_stack_spa",
"delivery_shape_reason": "一句话说明为什么归到该形态（写入 open_questions 以备追溯）"
```

prompt（`config/roles/product.yaml:23-27`）补充一条 guideline：
「前后端需求必须把每个前端功能点写成**可断言的产出**（服务端渲染出来的响应文本，或浏览器可观测的 DOM/文案），
写不出可断言产出的交互不得列为功能点。」

> 这条 guideline 是 A 档「把前端 FP 重述为服务端可断言行为」的**合法化位置**。
> 关键区别：F23 是在测试节点偷偷改写需求；本方案要求在 intake 阶段显式声明并留下原文，
> 产物确实能跑、断言确实指向真实响应体。这是工程降级，不是伪造证据。

**L3 校验**：`delivery_shape` 不在三值内 → 置为 `backend_only` + emit `intent_fallback` 事件（severity=warning）。
安全默认取 `backend_only` 的理由：现有已验证能力全在这个形态下，兜底不改变任何既有行为。

### 3.3 意图影响到的四处（一张表对齐）

| 环节 | `backend_only` | `full_stack_ssr` | `full_stack_spa` |
|---|---|---|---|
| 网络模块 finding | 维持 major（现状） | 降为 info | 降为 info |
| `_verification_gap` | 要求 language 含 python | 要求存在 Python 可验证通道 | 要求浏览器通道已接入，否则 gap=1 如实报失败 |
| 前端产物静态检查 | 不适用 | 启用（模板占位符/资源引用） | 启用 |
| 测试执行协议 | 现状 | 追加「进程内起服务 + 端口 0 + shutdown」约束 | 追加「跨进程服务生命周期」约束 |
| 门禁表达式 | 现状 8 条 | 现状 8 条 | 现状 8 条 + UI 断言条目 |

## 4. A 档：四处补丁的文件级改动

### 补丁 1 — 网络模块按意图豁免

**改动点不在 `sandbox.py`，在 `reviewer`。**
原因：`sandbox.analyze(files, policies)`（`sandbox.py:389`）签名里没有 spec，拿不到意图；
而 `reviewer` 手上有 `perception.spec`。

- `reviewer.py:43`（`build_context` 的 `task.node_id == "review"` 分支）
- `reviewer.py:82`（`build_prompt` 里的第二次 `analyze`）

**两处都要改。** 只改一处，`build_prompt` 仍会把 major finding 塞进 prompt，LLM 照样拦截。

改动形态（统一抽成一个方法，两处复用）：

```python
def _relax_network_findings(self, findings, spec):
    shape = str((spec or {}).get("delivery_shape") or "backend_only")
    if shape == "backend_only":
        return findings, []
    relaxed = []
    for item in findings:
        if item.rule == "network_import":
            item.severity = "info"
            relaxed.append(item.to_dict())
    return findings, relaxed   # relaxed 单独写进事件，保留审计痕迹
```

配套：在 `reviewer.yaml` 的 prompt guideline 里写明「`delivery_shape` 非 `backend_only` 时，
`network_import` 已由框架降为 info，审查时不得据此判阻塞」。

> 为什么不用「把 `reviewer.yaml:61` 的 `network_import` 直接改成 info」：
> 那样是全局关闭，`backend_only` 任务失去「高危外连可见」能力，与 `sandbox.py:27` 注释的原始意图冲突。

### 补丁 2 — `_verification_gap` 判定修正

现状（`tester.py:417-433`）：只看 `language` 字符串是否含 `python`。

改为按「交付形态所需验证手段是否都在可执行集合内」判定：

```python
def _verification_gap(self, solution_design, spec):
    shape = str((spec or {}).get("delivery_shape") or "backend_only")
    language = str(((solution_design or {}).get("tech_choice") or {}).get("language", "")).strip()
    if shape in ("backend_only", "full_stack_ssr"):
        # 验证通道 = Python；不要求 language 字符串里恰好含 "python"
        return {... "gap": 0 ...}
    if shape == "full_stack_spa":
        # 浏览器通道未接入时如实报缺口，不允许假通过
        return {... "gap": 1, "note": "full_stack_spa 需要浏览器证据通道，当前未接入（见 B 档前置项）"}
    # 未声明形态：退回原字符串判定，保持既有行为
    ...
```

要点：`backend_only` / `full_stack_ssr` 不再依赖 `"python" in language` 这个字符串巧合；
`full_stack_spa` 在 B 档未完成时**明确报失败**，而不是退化成「Python 测试全过就放行」。

### 补丁 3 — import 约束（模块级不得启动服务）

现状：`developer.py:175` 跑 `python -c "import {package}"`。若 LLM 写出模块级
`HTTPServer(...).serve_forever()`，import 自检会被挂住直到 180s 超时（`system.yaml:67`）。

两层防护：

1. **契约/prompt 约束**（`config/roles/developer.yaml`）：
   「Web 服务的监听必须在 `if __name__ == "__main__":` 或显式 `start()` 函数内，
   模块级只允许定义 handler 与 app 工厂。」
2. **静态 rule**（`sandbox.py` 的 `_analyze_file` 内新增，AST 可判定）：
   `web_service_lifecycle` —— 检出模块级（非函数/if-main 内）的 `serve_forever` / `Thread(...start())` 调用，
   severity 走 `severity_map`（建议 major，仅在 `full_stack_*` 下启用）。

> 只做第 1 条也能用，但依赖 LLM 自觉；第 2 条把约束变成确定性检查，与项目既有风格
> （`sandbox_command_bypass`、`json_not_imported` 都是同一思路）一致。

### 补丁 4 — 执行协议：端口与服务生命周期

现状：`tester.py:118-143` 的 `execution_protocol` 只描述 unittest + marker 回传，
没有任何关于起服务的约定。LLM 自由发挥时必然出现固定端口、`serve_forever` 不退出的写法。

在 `execution_protocol.requirements` 追加（`full_stack_*` 生效）：

- 服务必须绑 `("127.0.0.1", 0)`，端口由 `server.server_address[1]` 读取，**禁止字面量端口**；
- 在 `threading.Thread(target=server.serve_forever, daemon=True)` 中启动；
- 每个用例结束调 `server.shutdown()` + `server.server_close()`（建议 `addCleanup`）；
- 请求侧只能用 `urllib.request` 访问 `127.0.0.1`，禁止任何外部域名；
- 断言对象必须是**响应体文本**（如 `assert "购物车: 2 件" in body`），不得断言 HTML 外观。

配套静态 rule（AST，仅 `full_stack_*` 启用）：
`web_port_literal`（端口为字面量非 0）、`web_service_not_daemon`（线程非 daemon）。
这两条 + 补丁 3 的 `web_service_lifecycle` 共同把「起服务」从靠 prompt 变成靠检查。

### 补丁 5 — 前端静态证据（补第 4 件事的实现形态）

现状：`sandbox.py:431` `_analyzable` 只认 `.py`；HTML/CSS/JS 落盘后（`developer.py:132` 不限制后缀）
进得了 manifest（`sandbox.py:179-212` 的 `code_stats` 支持非 .py），但**没有任何质量证据**。

新增独立检查 `analyze_web_assets(files)`（不要塞进 Python AST 分析器，两者不是一类东西）：

| rule | 检查内容 | 建议 severity |
|---|---|---|
| `html_placeholder_unresolved` | 模板里残留未替换的 `{{ }}` / `{}` 占位符 | major |
| `html_asset_missing` | `link/script` 引用的相对路径文件不存在 | major |
| `html_tag_unclosed` | 常见标签未闭合（`<div>` / `<form>` 等） | minor |
| `js_syntax_error` | 无 node 环境下**只能做括号配平**等弱检查，明确标注为弱证据 | info |

**如实说明边界**：没有 node 就没有真正的 JS 语法/语义检查，`js_syntax_error` 只能是括号配平这类弱信号，
必须在 finding message 里写明「非完整语法检查」，否则就是制造假证据。

## 5. B 档：两件前置，以及它对 A 的依赖

### 前置 1 — 工具结果落 artifact

现状（`base.py:122-142`）：MCP 工具调用闭环存在，
但 `base.py:140` 的 `runner.execute(...)` 结果只进 `extra_messages`（回喂给 LLM 的会话消息），
**不进黑板、不进 artifact** → `leader.py:408` 的快照取不到 → 门禁表达式**永远读不到浏览器证据**。

改动：tester 节点在工具回传后，把每次调用的工具名、入参、返回摘要、截图路径
收集成 `ui_evidence` artifact 并 publish：

```jsonc
{
  "enabled": true,
  "channel": "mcp:playwright",
  "asserts": [{"fp_id": "FP-03", "category": "functional", "name": "...", "status": "passed", "message": ""}],
  "failed_asserts": 0,
  "screenshots": ["test_runs/iter01/ui/FP-03.png"],
  "console_errors": []
}
```

**注意**：工具调用由 LLM 发起（`tool_max_rounds` 默认 2，`base.py:119`），
框架无法保证它一定调用。这是 B 档最大的不确定性，方案里必须承认：
`ui_evidence.enabled == true` 但 `asserts` 为空时，应判为**证据不足**，而不是判通过。

### 前置 2 — UI 用例汇入 cases（否则覆盖率门禁过不了）

现状（`tester.py:498-512`）：`rate = 去重 fp_id 数 / fp_total`，
且 `flow.yaml:85-90` 要求 functional / exception / boundary **三类各 ≥ 1.0**。
`cases` 只来自 marker 回传的 unittest 结果。

→ 只加 `ui_evidence.failed_asserts == 0` 这一条门禁**解决不了覆盖率**：
前端 FP 依旧进 `fp_total`，三类依旧要为它各凑出一条带 `fp_id` 的用例。

推荐做法：**把 UI 断言转成同构 cases 条目汇入 `parsed["cases"]`**，
字段与现有 case 完全一致（`test` / `class` / `fp_id` / `category` / `status` / `message`）。
这样 `_coverage`、`_track_bugs`、缺陷闭环全部复用，**门禁零改动**。

替代做法（不推荐）：按层拆分 `fp_total`（前端 FP 单独算覆盖率）。
需要改 `_coverage` 的分母来源，且会让「覆盖完整」这个语义变得含糊。

### B 档对 A 档的依赖（不可跳过）

- 后端仍需补丁 1（网络豁免）；
- 仍需补丁 2（`full_stack_spa` 若走原判定，写 `"TypeScript + React"` 直接 gap=1）；
- 仍需补丁 3（import 自检）；
- 仍需补丁 4 的端口约定，并**额外**新增跨进程生命周期：
  浏览器是外部进程，服务不能只活在测试进程内。建议形态：
  测试脚本起服务 → 把端口写入约定文件（如 `.ui_port`）→ 浏览器 MCP 读取 → 结束后关停。
  这部分是 B 档独有，A 档不涉及。
- `base.py:96-102` `_tool_schemas` 全量下发、**无角色隔离**（developer 也能开浏览器），
  B 档应补按角色/节点的工具授权。

## 6. 门禁表达式片段（可直接贴进 profile）

```yaml
# config/profiles/web.yaml（新建，或并入 strict.yaml）
flow:
  nodes:
    acceptance:
      gate:
        criteria:
          # ... 原有 8 条保持不变 ...
          - id: "UI 断言无失败（仅 SPA 形态要求）"
            expr: "requirement_spec.delivery_shape != 'full_stack_spa' or ui_evidence.failed_asserts == 0"
          - id: "UI 证据非空（SPA 形态下不得证据不足）"
            expr: "requirement_spec.delivery_shape != 'full_stack_spa' or len(ui_evidence.asserts) > 0"
```

**两条前置条件必须同时满足，否则上面两条会让所有老任务验收失败**：

1. `requirement_spec.delivery_shape` 由框架注入默认值 `backend_only`（第 3.2 节 L3）；
2. `ui_evidence` 在任何形态下都被发布，非 SPA 时为 `{enabled: false, failed_asserts: 0, asserts: []}`。

## 7. 分阶段实施计划

| Phase | 内容 | 改动文件 | 预估 |

## 8. 量化验收标准

| # | 标准 | 判定方式 |
|---|---|---|
| 1 | `backend_only` 任务行为零变更 | 同一需求在改动前后跑两次，gate 8 条结果与回退次数一致 |
| 2 | 意图识别确定性兜底生效 | 造 3 条非法 `delivery_shape` 输入，全部落到 `backend_only` 且 events.jsonl 有 `intent_fallback` |
| 3 | 网络豁免只在该豁免时生效 | `backend_only` 需求里写 `import socket` → 仍报 major；`full_stack_ssr` 需求里写 `import http.server` → 降为 info |
| 4 | 端口约束被静态检出 | 测试文件写固定端口 → 出现 `web_port_literal` finding；改 `0` 后消失 |
| 5 | SSR 端到端通过 | 一个「带页面的购物车」需求，门禁 8 条全绿，且 `test_report.executions` 里有真实 exit_code=0 记录 |
| 6 | 前端 FP 有真实断言 | 该需求的 `test_report.coverage.functional.rate == 1.0`，且抽查用例的断言对象确实是响应体文本 |
| 7 | 前端静态证据非空 | HTML 里留未替换占位符 → 出现 `html_placeholder_unresolved` |
| 8 | B 档未完成时如实失败 | `full_stack_spa` + 未接浏览器 → `verification.gap == 1`，门禁判失败，**不得出现假通过** |
| 9 | 老任务不回归 | 改动后重跑 2 个历史 task 目录，验收结论与改动前一致 |

第 8 条是本方案的诚实性底线：它确保「预留 B 档形态」不会变成一个能骗过门禁的空壳。

## 9. 明确不做的事（避免范围失控）

- **不做流程拓扑分叉**：`flow.transitions` 保持 pass/fail 两条边，不新增按意图的路由节点
  （第 2.1 / 2.2 节已论证：profile 启动期固定 + transitions 无条件路由，改造代价大收益低）。
- **不做真部署（原 C 档）**：它改变的是系统定位而非工程量，建议退化为 B 档下的一个 MCP server。
- **不在没有 node 的环境声称做了 JS 语法检查**：只有括号配平这类弱信号，message 里必须写明强度。
- **不把 `network_import` 全局改成 info**：那会剥夺 `backend_only` 任务的高危外连可见性。
- **不在本方案内改 `expr.py` 的 `BoolOp` 语义**：短路求值是通用改进，建议单独立项单独回归。
