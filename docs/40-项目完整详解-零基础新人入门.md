## 1. 这个项目是什么（大白话版）

### 一句话

**用 5 个各司其职的 AI"员工"，模拟一家小型软件公司的完整交付流程：接到需求 → 出方案 → 写代码 → 测试 → 审查 → 验收出报告——全程自动，且有一整套防止 AI"作弊偷懒"的制度。**

### 一个比喻

想象你开了一家只有一个人的"软件公司"，雇了 5 个 AI 员工：

| 员工 | 干什么 | 类比真实公司里的 |
| --- | --- | --- |
| 产品 Agent | 把需求文档拆成功能点和验收标准 | 产品经理 |
| 研发 Agent | 出技术方案、写代码、修 bug | 程序员 |
| 测试 Agent | 独立设计测试用例、真实执行测试 | 测试工程师 |
| 评审 Agent | 静态分析代码、核对需求覆盖、签署验收意见 | 代码评审员 / QA 负责人 |
| 报告 Agent | 汇总所有证据，出验收报告 | 项目经理 |

还有一个" Leader（调度器）"——它不是员工，更像**项目经理 + 流程审批系统**：决定现在该谁干活、干活结果不通过该退给谁、退几次之后放弃。

### 它解决的真实痛点

直接让大模型"帮我写个功能"，你会遇到三个问题：

1. **模型会说谎**：它可能声称"我测试过了，全部通过"，实际上根本没跑测试；
2. **产出不可验收**：你拿到一堆代码，不知道它到底实现了需求的哪几条、覆盖没覆盖边界情况；
3. **不吸取教训**：同一个错误，换一次对话它再犯一遍。

这个项目的回答是：**不靠"提示模型请诚实"，靠制度（代码强制执行的规则）**——

- 测试的**执行权收归框架**：AI 只能"生成测试代码"，跑测试的是框架自己（见 [6.3 防作弊体系](#63-防作弊体系本项目最核心的设计)）；
- 每份测试、每份契约、每份证据都带 **HMAC 签名**（可以理解为"防伪钢印"），改一个字节就验签失败；
- 还有**一套 AI 看不到的"隐藏考卷"**（隐藏用例），门禁独立执行，专门抓"照着实现写测试"的糊弄行为；
- **验收结论只有一个来源**：门禁节点的裁决产物，其他任何 Agent（包括报告 Agent）都改不了。

### 两个关键数字（2026-10-26 实测）

- `python -m unittest discover -s tests` → **Ran 661 tests ... OK**（165 秒，无跳过、无失败）；
- 离线模式端到端运行一次（含注入缺陷、回退修复、审查、隐藏用例门禁）约 **5 秒**；接真实大模型（DeepSeek）运行一次完整流程约 **62 分钟**（见 `workspace/runs/20261026-024610-997b/timeline.md`）。

## 2. 开始之前：先懂 12 个名词

这些名词在文档和代码里到处都是，先用大白话讲清楚：

| 名词 | 大白话解释 | 在本项目里的体现 |
| --- | --- | --- |
| **LLM**（大语言模型） | 就是"ChatGPT 那样的模型"，给它一段文字它回一段文字 | 项目接了两种：`offline`（内置的假模型，行为固定可复现）和 `openai_compatible`（任何兼容 OpenAI 接口的真模型，当前配 DeepSeek） |
| **Agent** | 能"看材料 → 想一想 → 干活 → 交结果"的一轮封装。本项目里一个 Agent = 一段 Python 类 + 一份角色提示词 | `mas/agents/` 下 5 个类，每个角色的"人设"在 `config/roles/*.yaml` |
| **Prompt** | 发给大模型的完整"考题"，包含角色说明、任务、参考材料、输出格式要求 | 每次调用都存档在 `workspace/runs/<run_id>/prompts/`，可直接打开看 |
| **产物（artifact）** | Agent 干完活交出来的结构化成果（JSON 文件），如"需求规格"、"测试报告" | 存在 `workspace/runs/<run_id>/artifacts/<产物名>/v1.json、v2.json...`，**带版本号**，改过几版一清二楚 |
| **黑板（blackboard）** | 全体 Agent 共享的"公告板"：谁干完活就把产物贴上去，谁接活前先来读相关材料 | `mas/blackboard.py`；每个角色"必须读哪些材料"由配置里的**感知矩阵**决定 |
| **消息总线（bus）** | Agent 之间传"便条"的管道（本项目禁止 Agent 私聊，所有通讯都留痕） | `mas/bus.py`；所有便条落盘 `messages.jsonl` |
| **事件日志（events.jsonl）** | 流水线的"行车记录仪"：每一步动作（开始干活、发布产物、门禁判定、回退……）都按顺序记一行 JSON | `mas/events.py`。**整个系统以它为唯一事实来源**——事后统计、经验提炼、前端展示全从它来 |
| **门禁（gate）** | 流程里的"质检站"：一组布尔表达式 + 一堆框架强制检查，全过才放行 | `config/flow.yaml` 里 `kind: gate` 的节点；判定代码在 `mas/leader.py` 的 `_run_gate` |
| **沙箱（sandbox）** | 一个受控的隔离环境，专门用来"真实运行"AI 生成的代码，防止它乱来 | `mas/sandbox.py`：限定只能用 python 命令、剥离密钥类环境变量、可选 Docker 容器隔离 |
| **HMAC 签名** | 一种"防伪钢印"：用密钥对文件内容算出的校验值，内容改一个字节签名就对不上 | 测试清单、需求契约、验证证据都有签名（`mas/verifier.py`、`mas/contract.py`） |
| **ReAct 循环** | 让 Agent 能"想一步 → 用个工具 → 看结果 → 再想"的多轮工作方式，而不是一次性作答 | `mas/agents/base.py` 的 `_generate_with_react`，默认最多 4 步 |
| **YAML** | 一种缩进表示层级的配置文件格式（比 JSON 好读），本项目所有"流程/角色/学习规则"都用它描述 | `config/` 目录下所有 `.yaml` |

## 3. 全景架构：一张图看懂

```text
                 ┌──────────────────────────────────────────────────┐
                 │                    入口层                          │
                 │   CLI（python -m mas run/demo/...）               │
                 │   前端面板（frontend/server.py，浏览器操作）        │
                 └──────────────────────┬───────────────────────────┘
                                        │ 发起一次运行（run）
                 ┌──────────────────────▼───────────────────────────┐
                 │              Leader 调度器（mas/leader.py）        │
                 │   状态机循环：取下一个节点 → 造任务 → 派活 →         │
                 │   按结果走 pass/fail 分支 → 回退/重试/升级 → 记账    │
                 └──┬───────────────┬───────────────┬───────────────┘
                    │ 派活/收产物     │ 判门禁         │ 记账/复盘
        ┌───────────▼──────┐ ┌──────▼───────┐ ┌─────▼─────────────┐
        │  五个角色 Agent    │ │  门禁引擎      │ │  报告与经验        │
        │  product/develop/ │ │  flow.yaml    │ │  experience.py    │
        │  tester/reviewer/ │ │  criteria 表达式│ │  （自学习闭环）     │
        │  reporter         │ │  + 5 组硬校验  │ │                   │
        └───────────┬──────┘ └──────┬───────┘ └─────┬─────────────┘
                    │               │               │
     ┌──────────────▼───────────────▼───────────────▼─────────────┐
     │                        协作基础设施                           │
     │  黑板（版本化产物） │ 消息总线（留痕通讯） │ 事件日志（唯一事实）  │
     └──────────────┬─────────────────────────────────────────────┘
                    │
     ┌──────────────▼─────────────────────────────────────────────┐
     │                        底层支撑                              │
     │  LLM 客户端（offline / openai_compatible）                   │
     │  沙箱（真实执行代码+AST 静态分析） │ 验证器（冻结+签名+复算）      │
     │  可选：MySQL/Redis 双写 │ Redis 消息队列+worker │ 技能/MCP/搜索 │
     └────────────────────────────────────────────────────────────┘
```

三个理解要点：

1. **Agent 之间从不直接对话**。研发不会"打电话"给测试说"我写完了"。研发把产物贴到黑板、发一条广播，测试接活时自己来黑板读。所有交互都有留痕，事后可审计。
2. **Leader 是唯一流程权威，门禁是唯一验收权威**。Agent 只管"干好自己的活并交产物"，流程走向、回退几次、最终过不过，都由 Leader 按配置和门禁裁决。
3. **几乎所有"规则"都在配置文件里**，不在代码里。想加一个"方案评审"环节？写一份 YAML Profile 就行，不用改代码（见第 7 节）。

## 4. 一次运行的完整旅程（跟着真实运行走一遍）

下面跟着一次**真实发生过的运行**走完全流程。运行 ID：`20261026-040431-eb6e`（离线模式，需求是《订单金额计算与校验服务》）。所有引用的文件都在 `workspace/runs/20261026-040431-eb6e/` 下，你可以边读边打开。

> 想看"接真实大模型"的运行，看 `workspace/runs/20261026-024610-997b/`（DeepSeek，62 分钟，151 个事件），结构完全一样。

### 第 0 步：发起运行

你在终端敲下：

```bash
python -m mas run -r examples/requirements/order_pricing_service.md
```

`mas/cli.py` 解析参数 → `Leader.run()`（`mas/leader.py` 的 `run` 方法）开始工作：

1. 创建运行目录 `workspace/runs/20261026-040431-eb6e/`，下设 `artifacts/ code/ prompts/ test_runs/ reports/ ...`；
2. 实例化全部基础设施：事件日志、消息总线、黑板、沙箱、经验库、LLM 客户端；
3. 把需求原文读进来，作为第一个产物 `requirement_source` 贴上黑板（时间线第一行可见：`artifact_published | 需求输入（2476 字符）`）；
4. 顺手探测本机环境（有没有 node、能不能起浏览器），产出 `env_probe`——这样后面定方案时就不会"定出一个本机验证不了的交付形态"。

### 第 1 步：intake —— 产品 Agent 拆需求（并埋下两颗"防作弊钉子"）

产品 Agent 接到任务，先按**感知矩阵**从黑板读 `requirement_source`，把材料组装成一份 Prompt 发给 LLM，拿到结构化 JSON：

- **7 个功能点**（FP-01 金额解析、FP-02 会员折扣、FP-03 运费计算……），每个功能点带验收标准；
- **4 条总验收标准**（如 AC-02：功能/异常/边界三类用例覆盖率 100%）；
- **交付形态判定**：这份需求只要后端库（backend_only），不是全栈网站。

但这一步真正的价值是两件"防作弊"动作（这是全项目最精妙的设计，画重点）：

**钉子一：需求契约冻结。** 产品 Agent 把需求正文确定性切分成 51 条条款（C-01、C-02……），要求后面每个功能点都必须标注"我来自哪几条条款、原文引文是什么"，没被任何功能点覆盖的条款必须显式声明"范围外+理由"。然后整份契约用 HMAC 签名，落盘到 `contract/requirement_contract.json`。**从此以后需求不能改**——门禁会重新验签，发现规格在冻结后被改动，直接判不通过。

**钉子二：隐藏用例提前生成。** 此刻还没有任何代码。系统单独调用一次 LLM，**只给它看冻结契约**（不给方案、不给代码、不给可见测试），让它生成一套测试（本次 74 条），存到 **run 工作区之外**的 `workspace/hidden/20261026-040431-eb6e/`，同样签名冻结。因为生成时看不到实现，这套测试天然不可能"照着实现写"；到验收时由框架独立执行，专门抓"实现和需求不符但可见测试没测出来"的情况。

### 第 2 步：solution —— 研发 Agent 出技术方案

研发 Agent 读 `requirement_spec` + `env_probe`，产出 `solution_design`：选型"标准库 Decimal + 正则（零第三方依赖）"，列出 3 个候选方案对比、2 个模块、3 项风险、功能点覆盖 7/7。

时间线证据：`artifact_published | 选型『标准库 Decimal + 正则（零第三方依赖）』，候选 3 个，风险 3 项`。

### 第 3 步：implement —— 研发 Agent 写代码

研发 Agent 写出真实可运行的 Python 包 `order_pricing/`（本次 2 个文件、171 行），发布产物 `code_manifest`（代码清单：每个功能点映射到哪个文件的哪个符号，如 `order_pricing/core.py::parse_amount`）和 `implementation_summary`。

代码真实落在 `code/order_pricing/core.py`——现在就可以打开看，`python -c "from order_pricing import parse_amount"` 也能直接 import（在 code 目录下执行）。

> 离线模式这里有个教学彩蛋：配置了 `inject_first_pass_defect: true`，首轮会**故意注入一个典型缺陷**（运费计算"续重按 int 截断而不是向上取整"+漏算偏远地区加收），用来演示后面的缺陷闭环。经验库里若有对应的"守护经验"，则不再注入——这让自学习效果可以被量化（见 6.4）。

### 第 4 步：test —— 测试 Agent 独立测试

测试 Agent 的独立性写在角色配置里：**"用例必须来自需求契约，禁止读取研发实现代码反推期望值"**（`config/roles/tester.yaml`）。它的工作流：

1. **生成**：按契约给每个功能点设计功能/异常/边界三类用例（本次 74 条），写入 `code/tests/test_order_pricing.py`；
2. **冻结**：框架立刻对测试文件计算 SHA-256、复制一份到 run 目录下的 `frozen_tests/`，枚举出所有测试用例 ID，HMAC 签名生成 `test_manifest.json`。从此测试文件被"钢印封存"；
3. **真实执行**：注意，**跑测试的不是测试 Agent，是框架的执行器**（`mas/verify/runner.py`）。它只执行冻结清单里登记过的用例 ID，逐条结果写到 Agent 摸不到的地方（`verify_io/`），防止 Agent 伪造"全部通过"的输出；
4. **独立验证**：`mas/verifier.py` 的 `attest` 拿到框架的原始结果后，重新统计通过数、核对文件 hash 与签名，生成 `verification_attestation.json`（证据包）。

若测试失败：生成**缺陷单**（含复现步骤/期望/实际/堆栈），流程走向 `optimize` 节点（研发修复），修完再回来复测。本次离线运行首轮测试即 74/74 全过；真实大模型运行 `20261026-024610-997b` 则是首轮 73/74——缺陷单→修复→回归自测→复测 74/74，完整走了一遍这个闭环。

测试中若遇到需求歧义，测试 Agent 还能发起**协商**：通过 Leader 中介向研发提问，研发应答，全程落事件。真机运行的 `20261026-024610-997b` 里发生了 6 轮协商（`prompts/consultation#0-developer-*.md`），**未闭环的协商会阻塞验收**。

### 第 5 步：review —— 评审 Agent 审查

评审 Agent 做三件事（都以确定性证据为准）：

1. **AST 静态分析**：框架（不是 LLM）解析代码语法树，检查缺文档字符串、缺类型标注、超长函数、裸 except、eval/exec、漏 import 等（`mas/sandbox.py` 的 `analyze`）；
2. **功能点覆盖审计**：对代码清单里每个 `file::symbol` 映射，逐一验证——文件真实存在、符号真实定义、**且被"通过了的冻结测试"真实 import/使用**。审查因此必须发生在测试之后（"先测试后审查"原则）；
3. **重算阻塞项**：LLM 自己报告的"这个问题很严重"不作数——框架按规则重算 blocking 级别，LLM 的意见降级为参考（`mas/agents/reviewer.py` 的 `_recompute_blocking`）。

审查报告带 `code_hash`（对最终代码树的 hash）。**若之后代码又改了，门禁会重算 hash 发现对不上，旧审查就不能给新代码签字**——防止"审查通过后偷偷换代码"。

> 本次离线运行唯一的一次回退就发生在这里：审查发现 10 项阻塞问题（首轮注入的"缺文档字符串"缺陷被静态分析抓住），verdict=reject 退回研发 → 重写 → 重新测试 → 重新审查通过。这正演示了"审查不是橡皮图章"。

### 第 6 步：acceptance —— 门禁裁决（全项目最硬的一步）

`kind: gate` 节点，Leader 执行 `_run_gate`（`mas/leader.py`），依次做：

1. **逐条判表达式**：`config/flow.yaml` 里给 acceptance 配的判据，如 `test_report.summary.failed == 0`、`test_report.coverage.functional.rate >= 1.0`。表达式由 `mas/expr.py` 用 **AST 白名单**方式安全求值（只允许比较、算术、len/sum 等白名单函数，其他语法直接报错——不可能被注入恶意表达式）；
2. **执行隐藏用例**：从 run 外的冻结副本现场执行那 74 条隐藏测试，要求零失败（门禁代码 `_verify_hidden_suite`）；
3. **证据链重验**：重算测试文件 hash → 验 HMAC 签名 → 逐项比对证据包（`verify_evidence`），任何一项对不上即 fail-closed；
4. **契约重验**：验需求契约签名、验规格未在冻结后被改动；
5. **审查绑定**：重算 `code_tree_hash` 与审查报告里的比对（上面说的"旧审查不能签新代码"）；
6. **签署**：只有拥有 `can_block_acceptance` 权限的角色（评审 Agent）签署意见才有效，其他角色说"我同意"不算数。

全过 → 发布 `acceptance_gate` 产物（`passed: true`）。本次运行 18 项判据全部通过。

### 第 7 步：report —— 报告 Agent 出验收报告

报告 Agent 读全部产物，产出 `reports/acceptance_report.md|.json`（你可以在报告开头看到"验收结论：pass（来源：acceptance_gate；run_id=...；gate_config_hash=...）"）和 `evidence/index.jsonl` 证据索引。

**注意一个细节**：报告 Agent 只有"转述权"。Leader 最后会做**报告对账**（`_reconcile_report_gate`）：报告里的结论和 run_id 必须与门禁裁决一致，不一致直接强制整次运行判 fail。报告 Agent 想写"通过"是没用的，门禁说不过就是不过。

### 收尾

写 `run_summary.json`（结论/步数/回退数/缺陷数/指标）、`timeline.md`（人类可读时间线）、原子化检查点 `checkpoint.json`（支持断点续跑）、终态经验反馈与晋级。终端打印：

```text
[DONE] 运行结束 20261026-040431-eb6e｜验收：通过｜步数 10｜回退 1 ...
```

## 5. 五个角色 Agent 详解

每个 Agent 的"人设、职责、输入产物、输出产物、权限"全部配置在 `config/roles/*.yaml`，代码在 `mas/agents/`。

### 共同骨架（`mas/agents/base.py`）

所有 Agent 走同一条生命周期 `act()`：**感知**（读黑板）→ **检索经验**（历史教训注入）→ **组 Prompt** → **调 LLM**（可选 ReAct 多轮工具循环）→ **落地 apply**（校验并发布产物）。任何异常统一转为 `status=fail` 并留事件。

权限是代码强制的：`base.py` 里会真拦截——没有 `can_write_code` 权限的角色根本写不了代码文件，没有 `can_execute` 的角色跑不了沙箱命令。

### 产品 Agent（product.py）

- 输入：`requirement_source`（+ 附图，如果需求带图）
- 输出：`requirement_spec`（需求规格）、`requirement_contract`（冻结契约）、`hidden_suite`（隐藏用例）
- 特点：做交付形态判定（纯后端/全栈 SSR/全栈 SPA），形态决定后面测试策略（SPA 要求浏览器证据）；被驳回的规格会存档到 `rejected/` 留痕

### 研发 Agent（developer.py）

- 输入：`requirement_spec`、`solution_design`、`review_report`、`bug_reports`、`acceptance_gate`（按任务类型取用）
- 输出：`solution_design` / `code_manifest` + `implementation_summary` / `fix_summary` + `fix_test_report`
- 四种任务模式：first（首次实现）→ rework（按审查意见改）→ fix（修缺陷）→ 回归自测
- 修复纪律：修完每个缺陷必须用**框架的冻结测试**做定向回归（只跑该缺陷对应的用例），回归不过节点直接判 fail；产出的 `fix_test_report` 结论只能写"等待测试 Agent 复测确认"——研发无权宣布"已修复"

### 测试 Agent（tester.py）

- 输入：`requirement_spec`、`solution_design`、`code_manifest` 等
- 输出：`test_report`、`bug_reports`、`ui_evidence`
- 覆盖率门禁：功能点 × 功能/异常/边界三类的覆盖矩阵算出来，有缺口就把缺口清单回灌 LLM 重生成，重试次数用完仍缺则**不冻结任何测试、直接判 fail**——缺口不可能被"冻结进死档"
- 判定 pass 的硬条件：总用例数>0、零失败、证据签名有效、协商闭环、（SPA 形态时）UI 证据有效

### 评审 Agent（reviewer.py）

- 输入：需求契约、代码清单、通过的测试报告、AST 分析结果
- 输出：`review_report`、`design_review`（strict 档才有方案审查）、`acceptance_opinion`（签署）
- 特点：LLM 意见只是参考，**blocking 级别由框架重算**；审查结论绑定 `code_hash`

### 报告 Agent（reporter.py）

- 输入：全部产物 + `acceptance_gate`（门禁产物缺失或 run_id 不符直接 fail）
- 输出：`acceptance_report`、`evidence_index`、自学习效果报告；成功运行可被沉淀为技能

## 6. 核心机制深入

### 6.1 黑板：版本化的共享记忆（mas/blackboard.py）

- 每个产物一个目录，`publish()` 写入不可变的 `v1.json、v2.json...` 和一个 `latest.json` 指针。**版本号靠扫描磁盘取 max+1**，所以两个进程同时发布也不会互相覆盖；
- 每条产物记录：名字、版本、生产者、digest（内容哈希前 12 位）——"这份产物是谁、什么时候、产了什么"可完整追溯；
- 发布受**产物策略**校验（`mas/artifacts.py`）：产物名必须在角色声明里、`acceptance_gate` 等关键产物**只有 Leader 能发**——测试 Agent 想自己发一个"验收通过"？直接抛异常；
- 跨进程并发安全靠**文件锁**（`mas/filelock.py`，Windows 用 msvcrt、Linux 用 flock，零第三方依赖）。

### 6.2 消息总线：禁止私聊，全部留痕（mas/bus.py)

三种模式：**direct**（点名发送）、**broadcast**（按广播矩阵群发，如 `review_rejected → [developer, tester, reporter]`）、**request/response**（协商用，应答必须带原请求的 correlation_id 才算闭环）。

Agent 接活时不会读全部消息——`digest()` 把和自己相关的消息压缩成每条 ≤160 字符的摘要注入 Prompt。所有消息落盘 `messages.jsonl`。

### 6.3 防作弊体系（本项目最核心的设计）

把整章单独拎出来讲，因为这是项目区别于"普通多 Agent demo"的根本。**设计哲学：对"Agent 说谎"的防御是密码学和代码强制的，不是提示词恳求的。**

五道防线 + 一道总闸：

| # | 防线 | 防的是什么 | 实现位置 |
| --- | --- | --- | --- |
| 1 | **需求契约冻结** | 中途偷改需求"让需求迁就实现" | `mas/contract.py`：条款切分→映射校验→HMAC 冻结→门禁重验 |
| 2 | **测试执行权归框架** | Agent 声称"测试通过"但根本没跑 / 伪造输出 | `mas/verifier.py` 冻结+签名；`mas/verify/runner.py` 只执行冻结清单内用例，结果写到 Agent 摸不到的 `verify_io/` |
| 3 | **隐藏用例** | "照着实现写测试"（测试和实现一起糊弄） | `mas/hidden.py`：只看契约生成、存 run 外、门禁现场执行、要求零失败 |
| 4 | **审查绑定 code_hash** | 审查通过后偷换代码 | `code_tree_hash` 重算比对（leader.py `_verify_review_binding`） |
| 5 | **报告对账** | 报告 Agent 把失败写成成功 | `_reconcile_report_gate`：报告与门禁不一致 → 强制整次运行 fail |
| 总闸 | **门禁唯一裁决** | 任何 Agent 绕过流程自行"宣布"验收 | `acceptance_gate` 产物只有 Leader 能发布；verdict 只由它算出 |

补充两个细节让防线更严：

- 证据包（attestation）里绑了**五个 hash**：需求、代码、可见测试、隐藏测试、环境——换任何一个都会验签失败；
- 测试文件在冻结后被 Agent 改过？`restore_if_changed` 直接把它**恢复成冻结副本**，改动被静默丢弃并留痕。

### 6.4 自学习闭环：让系统越用越好（mas/experience.py）

```text
事件日志 ──规则化提炼──▶ 分级经验库 ──打分检索──▶ 注入后续 Prompt
   ▲                       L1 运行级                          │
   │                       L2 项目级                           │
   └────── reinforce 反馈（好经验加分/坏经验降权）◀── 消费效果 ──┘
```

- **三级库**：L1 只在本次运行内复用（如"刚才审查驳回的原因"当轮就注入修复环节）；L2 项目级、L3 全局级跨运行复用；
- **提炼是规则化的**（不是让 LLM 总结）：从事件里按固定规则提取，如"审查拦截了缺文档字符串" → 经验 `avoid_missing_function_docstring`；"运费计算出边界缺陷" → `guard_calc_shipping__boundary`；
- **打分检索**：相关度 0.45 + 置信度 0.25 + 使用次数 0.15 + 新近度 0.15 加权，有双层 token 预算控制注入量；每次注入都在 `prompts/*.md` 头部留痕（经验 ID、层级、命中分）；
- **晋级与降权**：好经验（命中后确实避免返工）按"有效成功次数"晋级 L1→L2→L3；导致回退的经验被降置信度——防止"反复注入但每次都致返工"的坏经验爬到全局；
- **可度量**（这是设计亮点）：离线 Provider 会消费经验的 `action_key`——一旦经验库里有 `guard_calc_shipping__boundary`，离线生成代码时就**不再注入那个运费缺陷**。于是"第二轮运行缺陷数下降、步数下降"变成可复现的确定性对比（`python -m mas demo` 三轮演示就是在展示这个，最后打印多轮对比表）。

### 6.5 门禁表达式引擎（mas/expr.py）

`test_report.coverage.functional.rate >= 1.0` 这类判据是配置写的，必须安全求值。实现：把表达式解析成 Python AST，然后**只允许白名单内的语法节点**（比较、算术、布尔、len/min/sum 等函数、属性取值），其他一律抛错。字段缺失不算异常，而是把该判据判为 False（fail-closed：宁可不通过，不放过）。

一个实现细节：布尔组合**不短路**（and/or 两边都会求值），所以写条件时引用不存在的字段会整条判 False——这是刻意为之的保守设计。

### 6.6 上下文管理：Prompt 里的内容是被管制的（mas/compress.py、mas/context.py）

产物可能很长，Prompt 装不下。压缩策略只改"**进模型的内容**"，**绝不改黑板上的产物本体**，且门禁永远走黑板快照求值——所以"压缩导致门禁误判通过"在结构上不可能发生。LLM 客户端侧还有超窗治理（截断→裁剪→紧凑化）和思考链降级链（max_tokens 被思考耗尽时自动降低 reasoning_effort 重发）。

## 7. 配置驱动：改 YAML 就是改流程

`config/` 是这个项目的"宪法"。五个核心文件：

| 文件 | 管什么 | 关键内容举例 |
| --- | --- | --- |
| `system.yaml` | 全局运行时 | LLM provider/model/凭据外注变量名、沙箱后端、技能/ReAct/上下文开关、MySQL/Redis/MQ 开关 |
| `flow.yaml` | **流程拓扑** | 8 个节点（intake/solution/implement/test/review/optimize/acceptance/report）、每节点的角色/输入产物/输出产物/pass-fail 走向/重试次数、门禁判据表达式 |
| `collaboration.yaml` | 协作规则 | 感知矩阵（谁必读谁的产物）、广播矩阵（12 类事件通知谁）、协商规则（tester↔developer，最多 6 轮，未闭环阻塞验收）、回退策略（review→implement 最多 3 次、acceptance→optimize 最多 2 次）、全局回退上限 8 次 |
| `learning.yaml` | 自学习 | 三级库容量、检索权重、提炼触发器、晋级阈值（L1→L2 命中 1 次）、注入预算 1000 tokens、回退降权系数 |
| `inputs.yaml` | 输入源 | 飞书解析、文档 MCP 解析、联网搜索 provider（默认免 Key 的 bing_web） |

**"改配置即改流程"的两个现成例子**（`config/profiles/`）：

- `strict.yaml`：在 solution 和 implement 之间**插入**一个 `solution_review` 节点（方案也要评审），并给门禁加一条 `design_review.verdict == 'pass'` 判据。运行时加 `--profile strict` 即生效；
- `lean.yaml`：给 review 节点写 `skip: true`——加载器自动**裁掉该节点并把流转边重接**（implement 完直接去 test），验收回退上限也降为 1 次。

也就是说：加节点、删节点、改走向、改门禁、改回退上限，全部是编辑 YAML，零代码改动。代码里的 `_is_rollback`、`_run_gate` 等只是"执行宪法"的机制，宪法本身在 config/。

## 8. LLM 接入：离线模式与真实大模型

### 8.1 两种 Provider

| | `offline`（默认代码值） | `openai_compatible`（当前实配，DeepSeek） |
| --- | --- | --- |
| 需要 API Key？ | 不需要 | **需要，没有直接报错**（不会偷偷回退 offline） |
| 原理 | 内置**算子库**（`mas/providers/ops.py`）：把需求关键词匹配到 7 个预置算子（金额解析/折扣/运费/优惠券/分摊/总价/校验），每个算子带正确实现、典型缺陷实现、三类测试契约 | 标准 `/chat/completions` 接口，任意需求 |
| 确定性 | 同样输入必得同样输出（无随机采样）——适合回归测试和教学演示 | 自然 |
| 真实性 | **代码生成、测试执行、静态审查、门禁判定全部真实发生**，只有"自然语言理解"被规则替代 | 全真实 |

理解 offline 模式很重要：**它不是"假跑"**。它生成的 `order_pricing/core.py` 是真实可 import 的 Decimal 实现，测试是真实执行的，缺陷是真实被测试抓住的。它的价值是让整条流水线可以**无 Key、可重复**地跑通与回归——661 个单元测试大多依赖它。

### 8.2 凭据不落盘的三通道（优先级从低到高）

1. `config/credentials.yaml`（前端"设为默认"写入；已在 .gitignore，不进版本库）；
2. 环境变量 `MAS_LLM_API_KEY` / `MAS_LLM_BASE_URL`；
3. 运行时注入：CLI `--api-key/--base-url`，或前端表单填写（仅当次生效）。

前端"模型配置"弹窗还有"测试连接"（校验 Key 并拉取可用模型列表）、上下文窗口设置（Token 用量条 80% 转橙、95% 转红）。

### 8.3 openai_compatible 的工程细节（mas/llm.py）

- 流式接收默认开启（规避网关对长非流式请求的 300 秒断连），带 1800 秒总看门狗；
- 429/5xx/超时按配置自动重试（线性退避），4xx 立即失败；
- "返回空正文"降级链：检测到 max_tokens 被思考链耗尽 → 自动降低 reasoning_effort 重发；
- 带图为 400 → 自动去图重发一次，并在 Prompt 里如实声明"图片未发送，不得声称看过图"（防幻觉）。

## 9. 能力扩展层：技能、MCP、联网搜索

这一层是**独立于流水线的能力层**：不占流程节点、不加角色，全部有开关且默认不启用，关掉后行为与没有这一层完全一致。

### 9.1 技能（Skill，mas/skills.py）

一个技能 = 一个目录 + `SKILL.md`（六个必填字段：name/description/when_to_use/trigger/inputs/steps）+ 可选脚本。CLI：`skill list/show/add/edit/remove/check`。

两种用法：

- **注入 Prompt**：按关键词/意图/节点匹配（前 3 个），把"怎么做这类任务"的方法论注入对应节点的 Prompt；
- **注册为工具**：声明了 `tool.script` 的技能经 function calling 暴露给 LLM，模型可主动调用，脚本在沙箱里执行。

**沉淀不自动发生**：一次运行通过后不会偷偷写技能；只有明确执行 `python -m mas skill add --from-run <run_id>` 才提炼——且只保留最终通过路径、剔除回退试错、把本机绝对路径替换成 `{{workspace}}`/`{{run_id}}` 占位符。

### 9.2 MCP 工具（mas/mcp.py + mas/toolrunner.py）

MCP（Model Context Protocol）是给 LLM 接外部工具的行业标准协议。本项目**零 SDK** 实现了最小 JSON-RPC 客户端，支持 stdio（子进程）和 sse（远端流）两种传输。`python -m mas mcp check <name>` 分五阶段诊断（解析→校验→连接→握手→冒烟），失败会告诉你坏在哪一阶段。当前配置了 playwright（浏览器）和 docparse（文档解析）两个服务。

`toolrunner.py` 把 MCP 工具 + 技能工具 + 联网搜索统一注册成 function calling 工具面，交给节点白名单（`tools_nodes`，当前只有 intake）内的 Agent 在 ReAct 循环中使用。工具报错会以字符串回传给模型让它自我纠正，而不是直接崩掉。

### 9.3 联网搜索（mas/websearch.py）

四个可插拔后端：`bing_web`（免 Key，默认）、bing Azure、tavily、serpapi。设计原则：**搜索失败只留事件不中断流程**（返回空列表）。用法：intake 节点前置富化（先搜背景资料再拆需求）或作为 `web_search` 工具被模型自主调用。

### 9.4 交付形态识别与输入源

- `intent.py` 四层判定交付形态：关键词预分类 → 产品 Agent 契约字段 → 兜底 → **沙箱真实文件探测**（发现 vite/react 配置就收紧为 SPA，只许收紧不许放松——防 LLM 把 SPA 申报成纯后端绕过浏览器验证）；
- `sources.py` 输入源：文本 / Markdown 等直读 / docx（zip+XML 抽取）/ 更多格式走 MCP / 飞书文档 / 前端上传（白名单后缀、≤10MB）/ 需求附图（≤5MB、≤4 张）。

## 10. 工程基础设施

### 10.1 沙箱（mas/sandbox.py）——真实执行 + 静态分析

**local 后端**：只能执行 python 命令（显式拒绝 cmd/sh/bash/powershell）、剥离名字含 KEY/TOKEN/SECRET/PASSWORD/CREDENTIAL 的环境变量、路径越界拦截、POSIX 下加 CPU/内存/文件大小 rlimit。文档里诚实标注：这是"防误踩"不是安全边界。

**container 后端**（`sandbox_backend: container`）：Docker `--network none --cap-drop ALL --read-only` + 内存/CPU/进程数限制，初始化时运行时不可用**直接拒绝启动**（fail-closed，不降级）。

**AST 静态分析**：对生成的代码逐文件并行分析——语法错误（critical）、缺文档字符串/类型标注、超长函数（默认 60 行）、可变默认参数、裸 except、eval/exec（critical）、import 网络库（15 类模块）、"用了 os 但没 import os"（必 NameError）、未用 import、超长行、TODO 残留等。前端资产（HTML/JS）也有弱检查（标签配平、括号配平、占位符残留）。

### 10.2 存储：文件系统是唯一事实，MySQL/Redis 是可选加速（mas/store/）

`workspace/` 的 jsonl 文件永远是真相之源；MySQL（六张表：运行/事件/产物索引/LLM 痕迹/经验/指标）和 Redis（运行注册表、取消键、读缓存、分布式锁）是**软依赖**：没装驱动、没起服务、连接失败——一律返回 None 自动降级，绝不抛异常打断流水线。一键拉起：`deploy/docker-compose.store.yml`（MySQL 8 + Redis 7，端口只绑 127.0.0.1）。

### 10.3 消息队列与 worker：把"运行"和"发起"解耦（mas/mq.py + mas/worker.py）

默认不开。开启后 `python -m mas run --enqueue` 只把任务投进 Redis Stream 立即返回，由独立进程 `python -m mas worker` 消费。可靠性设计（对新人是很棒的分布式入门教材）：

- **幂等**：同一次运行重复入队会被去重键挡住；已完成的运行被再次投递会被跳过；
- **租约**：worker 执行前抢一把 300 秒的 Redis 锁，后台线程每 30 秒续租——worker 崩了锁自动过期，别的 worker 能接手；
- **ACK / PEL / 认领**：处理完才确认（ACK）；worker 挂掉后未确认消息留在 PEL（待确认列表），超时后被其他 worker 用 XAUTOCLAIM 认领重跑（at-least-once 语义）；
- **重试与死信**：只有基础设施类异常才重试（退避 5/30/120 秒，最多 3 次），重试仍失败进死信队列（DLQ）；业务失败（比如验收不过）**不重试**——重跑也是同样结果；
- **心跳**：`mas:run:<id>` 键 90 秒 TTL，前端靠它显示"运行中还活着"。

### 10.4 断点续跑与取消

每次节点完成+分支落定后原子写 `checkpoint.json`；进程被杀后重发同一需求，Leader 从检查点恢复（需求 hash 不一致会拒绝续跑——需求变了就得重跑）。前端/CLI 取消是**协作式**的：打取消标记，当前节点执行完毕后在节点边界安全停止，而不是粗暴杀线程。

### 10.5 前端面板（frontend/）

纯 Python 标准库 HTTP 服务（1537 行）+ 原生 JS 单页（1379 行），零前端依赖。三个视图：**运行流水线**（对话式发起运行、看执行步骤/事件流/思考过程/验收报告）、**经验库**、**自学习报告**。1.5 秒轮询刷新。

安全设计值得一看（`frontend/server.py`）：非本机访问必须设令牌（三种传递通道 + 常量时间比较防时序攻击）；令牌换取 HttpOnly Cookie；CORS 只回显白名单；所有 POST 有 Origin 校验防跨站；`run_id`/profile 走正则白名单、需求文件必须位于 uploads/ 目录内（防路径穿越）；API Key 只回掩码不回明文。

## 14. 新人常见误解 FAQ

**Q1：offline 模式是不是"假运行"，只走个过场？**
不是。代码生成（真实可 import 的 Decimal 实现）、测试执行（真实 subprocess 跑 unittest）、AST 静态分析、门禁五组硬校验全部真实发生。被规则化替代的只有"自然语言理解"这一环（算子库匹配需求）。README 原话："代码生成、测试执行、静态审查、门禁判定全部真实发生，只有自然语言理解部分被规则化算子库替代，用于可重复回归。"

**Q2：测试失败了是不是就"回退"？**
不一定。"fail 分支"和"回退"是两个概念。`implement fail → test`、`optimize → test` 是普通迭代（代码里 `_is_rollback` 只认 `collaboration.yaml` 的 rollback 段显式声明的边，如 review→implement）。只有回退才计入 `rollbacks` 并消耗回退预算（全局上限 8 次，超了触发升级策略出"验收不通过"报告）。

**Q3：门禁是不是就是 flow.yaml 里那十几条表达式？**
远不止。表达式只是明面判据；门禁还要做隐藏用例执行、证据链签名重验、契约重验、审查 code_hash 绑定四组框架硬校验 + 评审角色签署。**删掉 yaml 里的判据并不能放松验收**。

**Q4：报告 Agent 权力最大吧？它写"通过"就是通过了？**
恰好相反，它是权力最小的。verdict 只由门禁产物算出（`acceptance_gate.passed and not forced_fail`），报告与门禁不一致会被 Leader 强制改判 fail。任何 Agent 都改不了结论——这套系统的防谎手段是密码学（HMAC）+ 代码（权限拦截），不是提示词。

**Q5：MySQL / Redis / 消息队列是不是必装？**
全都是软依赖。不装、不启、连不上，系统自动降级回文件系统模式照常跑（`mas/store/__init__.py` 的构建函数一律返回 None 不抛异常）。mq 默认关闭，开了才有 worker/死信那套。

**Q6：每次运行成功后会自动沉淀一个"技能"吗？**
不会，刻意设计成不自动。只有显式执行 `python -m mas skill add --from-run <run_id>` 才提炼，且剔除回退试错、参数化绝对路径——避免污染技能库。

**Q7：为什么 int(1.5) 这种"看起来没问题"的缺陷值得专门注入演示？**
因为它是运费续重计算的真实业务缺陷（1.5kg 续重应向上取整为 2kg 计费，int 截断成 1kg 少收钱；还漏了偏远省份加收）。离线模式首轮故意注入它 → 边界用例真实失败 → 缺陷单 → 修复 → 回归 → 复测闭环，让你 5 秒钟看完整个"缺陷生命周期"。

**Q8：Agent 能看到隐藏用例吗？**
不能，这是信息隔离设计。隐藏用例生成时只给契约不给实现，生成后存到 run 目录之外并签名，执行由门禁现场完成。Agent 的 Prompt、产物、沙箱可见范围内都拿不到它。

**Q9：这个项目和大厂的多 Agent 框架（LangGraph/AutoGen 等）什么关系？**
没用那些框架，核心调度/黑板/总线/门禁全部自研（依赖仅 PyYAML）。`docs/27-Codex与multi_agent架构对比.md`、`docs/05-多Agent技术对标大厂分析.md` 有详细对标分析；上下文管理参考了 Codex 的分层治理思路（`docs/35`）。

## 15. 建议的代码阅读路线

不要按文件名顺序读，按"一条运行的生命周期"读。推荐五步：

**第 1 天：先当用户（不读代码）**
跑 `python -m mas demo`（offline），打开 `workspace/runs/<最新>/timeline.md` 和 `reports/acceptance_report.md`，把第 4 节的旅程对上号。再开前端面板点点看。

**第 2 天：读"宪法"（配置）**
`config/flow.yaml`（最短最重要，137 行）→ `config/collaboration.yaml`（感知/广播/回退矩阵）→ 挑 `config/roles/tester.yaml` 看角色配置长什么样。此时你已经能解释"为什么 test 失败会去 optimize"。

**第 3 天：读主干（调度）**
`mas/leader.py` 的 `run()`（392 行起，状态机主循环在 663 行附近）→ `_run_gate()`（1146 行起）。配合 `mas/expr.py`（很短，246 行）。此时你理解了状态机和门禁。

**第 4 天：读防作弊三件套**
`mas/contract.py` → `mas/verifier.py` → `mas/hidden.py`，再回看 `mas/verify/runner.py`（很短）。此时你明白第 6.3 节的五道防线分别在哪个文件实现。

**第 5 天：读一个角色 + 黑板 + 经验**
`mas/agents/base.py` 的 `act()` 与权限拦截 → `mas/agents/tester.py`（最丰富的角色：冻结/覆盖门禁/协商都有）→ `mas/blackboard.py` → `mas/experience.py`。读完你就可以上手改代码了。

> 改代码的保命符：改完跑 `python -m unittest discover -s tests`。661 个测试是你的安全网；其中 `tests/test_gate_evidence.py`、`test_verifier.py`、`test_hidden_repair.py` 直接对应第 6.3 节的防线，改防作弊相关代码前先读它们。
