## 3. 九个修复的详细记录（改动 / 原因 / 影响范围）

### F1 `mas/llm.py`：流式（SSE）输出 —— 根因：环境/端点约束

- **现象**：implement 单节点 900.1s 空输出 = 3 次尝试 × 300s（默认 → low → high 降级链每次都被网关掐断）。
- **根因**：端点网关 openresty `proxy_read_timeout=300s` 按「两次读之间间隔」计；非流式下模型生成完才吐首字节，300s 即被判超时（504）。长生成任务（全量代码 JSON）必然触发。
- **改动**（+105 行）：`LLMClient` 新增 `stream` 配置（默认 true）；`_request_generation` 分流到新增的 `_request_generation_stream`——SSE 逐 chunk 读取，累加 content/reasoning_content/tool_calls（按 index 合并），读完后按非流式响应结构组装 body 复用 `_parse_response`（字段口径完全一致）；重试语义与原有 `_post_with_retry` 相同（网络错误与 429/5xx 重试、4xx 立即失败）；服务端忽略 `stream=true` 返回普通 JSON 时按 Content-Type 判定退化为一次性解析。
- **影响范围**：仅 openai_compatible 路径；offline Provider 不触网不受影响；tools 开启时 tool_calls 增量合并已实现。
- **验证**：新增 5 个流式单测（`tests/test_token_budget.py`）；真实端点小请求探测 6.8s 返回、usage 完整；attempt06 implement 单节点 849.5s 完整生成 42289 token 代码（不再被 300s 掐断）。

### F2 `config/system.yaml`：输出预算与流式声明

- **改动**：`max_tokens: 16000 → 64000`；新增 `stream: true`（均带注释说明实测依据）。
- **原因**：实现/测试类任务（多文件全量代码 + 用例）需 2~6 万输出 token，而推理模型的思考链计入 `max_tokens`（既有实测结论）；16000 会被思考链吃光导致正文为空/截断。流式解除网关时长墙后，生成时长只受客户端 `timeout=600s`（单次 socket 读超时）约束。
- **影响范围**：全局 LLM 调用；DeepSeek 上下文 131072 > prompt(~4K)+64K，无溢出风险。

### F3 `mas/agents/tester.py`：契约外输出防御 —— 根因：代码实现问题

- **改动**（4 处 isinstance 守卫）：`_negotiate` 中 negotiation 非 dict 时降级为空 questions 且过滤非 dict 问题项；`apply` 文件循环跳过结构非法的文件项；`_coverage`/`_track_bugs` 跳过非 dict 用例记录。
- **原因**：attempt02 实测 LLM 把 `negotiation` 输出成字符串，原实现直接 `.get("questions")` 抛 AttributeError，整个 test 节点崩溃（沙箱都没跑到）。
- **影响范围**：仅 tester 的数据解析路径；契约合规时行为不变。

### F4 `mas/agents/tester.py`：执行协议写入交付契约 —— 根因：设计方案缺陷（契约缺口）

- **改动**：`contracts["default"]` 新增 `execution_protocol`（marker `<<<MASS_RESULT>>>`、`--only` 参数、result_json 八字段、用例方法命名约定 `test_{category}_{op}_{name}`、fp_id/category 回填要求、exit code 语义）；`cases` schema 补 `op`/`name`/`expect_error` 字段（缺陷跟踪按方法名反查需要）。
- **原因**：`grep` 证实 marker/`--only` 协议只存在于离线 Provider 的测试文件模板（`mas/providers/offline.py`），LLM 路径的 Prompt 契约完全没有它——LLM 生成的测试文件不可能自带回传协议，沙箱解析不到结果（用例统计 0、覆盖率门禁必败）。
- **影响范围**：仅 tester 的 Prompt 契约；离线 Provider 不读契约，不受影响（有单测锁定）。

### F5 `mas/leader.py`：回退判定只认显式回退边 —— 根因：设计方案缺陷

- **改动**（`_is_rollback`，-2/+12 行）：只有 `collaboration.rollback` 显式声明的边（review→implement / test→optimize / acceptance→optimize）才算回退；流程配置里的普通转发边（optimize→test 修复闭环、implement→review 失败中转）重新进入已执行节点属于**迭代**，不走回退策略与权限检查。
- **原因**：attempt03 实测 optimize 修复后再测试被误判为回退，而 developer 角色 `can_rollback: false` → `permission_denied` → 流程终止，闭环被「权限」杀死。回退次数仍由三条显式边各自的 max_attempts（3/3/2）与全局 8 次上限约束，不会失控（`max_steps=40` 兜底）。
- **影响范围**：Leader 状态机分支判定；回退事件/计数的语义收紧（普通转发不再计入 rollback 指标）。

### F6 `mas/agents/base.py` + `config/system.yaml`：感知段预算 900 → 10000 字符

- **改动**：`perceive()` 从 `runtime.prompt_artifact_max_chars` 读预算（默认 10000，兼容旧默认）；system.yaml 显式配置。
- **原因**：attempt03 的 implement Prompt 全文仅 4604 字符，requirement_spec（8130 字符）在 900 字符处被截断——LLM 只看到 FP-01/03/06 的片段就在「信息残缺」下实现 12 个功能点；测试文件的 `import cronsched.cli.main` 也是因为 manifest 函数清单被截断（看不到真实的 `cli_main`）而猜错 API，导致修复后 import 崩溃、15 个回归全败。
- **影响范围**：所有角色的 Prompt 感知段变大（implement Prompt 4604 → 28432 字节）；token 成本上升，DeepSeek 131K 上下文可承受。

### F7 `mas/agents/developer.py`：回归证据补 stderr —— 根因：代码实现问题（诊断缺失）

- **改动**（+3 行）：`_apply_fix` 的回归证据字典增加 `stderr_tail`。
- **原因**：attempt03 的 15 条回归全部 exit_code=1 且 stdout_tail 为空——import 崩溃的 traceback 在 stderr，原实现不留痕，现场无法诊断（我手动复现才拿到 `ImportError`）。
- **影响范围**：仅 fix_test_report 的证据字段。

### F8 `mas/agents/tester.py`：参考 runner + 坑位警示 —— 根因：代码实现问题

- **改动**（+~90 行）：模块级新增 `_REFERENCE_RUNNER`（与离线模板同源、生产验证过的自定义 TestResult 收集器），写入 `execution_protocol.reference_runner`；requirements 明确「必须采用参考实现；禁止重复遍历已执行的 suite——unittest 执行后元素置 None，二次迭代触发 `'NoneType' object has no attribute 'id'`（attempt04 实测）」。
- **原因**：attempt04 的 LLM 自建 main() 二次遍历已执行 suite 崩溃，marker 未输出 → 用例统计 0。LLM 每次自建 runner 都会重新踩这个坑；框架给出可抄的参考实现并把坑写进契约。
- **验证**：参考 runner 本身经过真实执行冒烟（3 用例：1 过 2 错、category/fp_id 回填正确、`--only` 过滤正确）；attempt06 的测试节点据此产出 48/48。

### F9 `mas/agents/tester.py`：协议违规诊断 —— 根因：代码实现问题（静默失败）

- **改动**：marker 解析失败时发 `test_protocol_violation` 事件（含 stdout/stderr tail），test_report 增加 `protocol_note` 字段。
- **原因**：原实现 marker 缺失时静默按 0 用例继续，门禁只看到「覆盖率为 0」看不到为什么。
- **影响范围**：仅测试报告与事件流。

### F10 `mas/agents/reviewer.py`：审查 Prompt 增强 —— 根因：设计方案缺陷

- **改动**（+57 行）：`ReviewerAgent.build_prompt` 覆写——review 节点把「AST 静态分析证据（findings/loc/functions/syntax_errors）+ 沙箱真实源码（40000 字符预算）」追加进 Prompt 并同步落盘。
- **原因**：reviewer 的 `build_context` 算了 AST 分析，但 `_generate_openai` 根本不消费 context——LLM 路径的 reviewer 只能看到 manifest 清单，拿不到源码也拿不到确定性证据，于是连续以「未提供任何可读取的源文件内容」驳回（attempt03/04/05 同一措辞）。这同时意味着 README 宣称的「真实 AST 静态分析」在 LLM 路径实际是空转。
- **效果**：attempt06 的 review 1 带着源码与行号证据驳回了一个**真实缺陷**（FP-07 要求并行不阻塞，实现却同步 `future.result()` 串行执行，证据精确到 `executor.py:33-66`），review 2 逐条核验修复后放行——审查从「形式驳回」变为「实质审查」。
- **影响范围**：仅 reviewer 的 review 节点 Prompt（solution_review/acceptance 不变）；reviewer LLM 调用耗时上升（78s → 400~493s，在读源码）。

## 8. 多 Agent 能力边界（基于本轮实测）

### 8.1 能做到（本轮已验证）

1. **完整流水线闭环**：需求文档/文字输入 → 功能点拆解 → 技术选型（多候选打分）→ 编码 → AST 静态审查 → 测试生成与沙箱真实执行 → 缺陷单 → 定向回归 → 修复 → 门禁判定 → 验收报告，全流程无人工干预。
2. **真实质量门禁**：门禁表达式作用于真实产物（沙箱执行结果、AST 分析、覆盖率统计），不是 LLM 自评；覆盖率按回传用例的 fp_id+category 机器统计。
3. **缺陷闭环**：能发现并修复真实缺陷（FP-07 串行执行、RunLogger 坏目录不抛错等），回归证据落盘。
4. **自学习**：事件日志 → 规则化经验提炼 → L1/L2/L3 分级注入；同类任务第二轮节点耗时显著下降（intake 181s → 33s）。
5. **双 Provider**：offline 确定性模式可无 Key 回归全流程（冒烟 4.46s 通过）；openai_compatible 处理任意领域需求。
6. **配置驱动**：流程节点/门禁/回退/Profile（strict/lean）全部走 YAML，改配置即改流程。

### 8.2 做不到 / 需要人工兜底（本轮实测边界）

1. **非 Python 交付物**：沙箱命令白名单只放行 Python 解释器（`sandbox_command_policy`），C++ 任务无法编译验证——见任务三探针结果。
2. **单次生成的体积上限**：implement/test 单节点一次生成全部文件，实测上限约 4.5 万输出 token / 1100 行；超出即 length 截断。`docs/08` 记录的「产物分批生成」方案本期未实现，是已知天花板。
3. **LLM 契约遵从不完全稳定**：类型防御、参考 runner、感知预算扩容只能把违背概率降到「循环可收敛」，不能归零；覆盖率完整性在不同测试代际间波动（attempt06 经历了 6 轮测试代际才同时满足「全过 + 全覆盖」）。
4. **确定性仅存在于 offline 模式**：真实 LLM 路径同一需求两次运行的产物不同（温度 0.2 + 思考链随机），回归对比需靠门禁而非逐字节比对。
5. **长任务耗时**：单轮端到端 40~120 分钟（6~21 个 LLM 调用，单节点 30s~1030s），不适合交互式场景；离线模式秒级。
6. **API 漂移风险**：跨节点/跨代际的公开接口一致性依赖 manifest 函数清单 + Prompt 约束，无强制契约检查（本轮靠测试暴露后修复）。

### 8.3 修复后 vs 修复前（同一任务同一门禁）

| 维度 | 修复前 | 修复后 |
|---|---|---|
| implement 长生成 | 300s 必 504，900s 空输出 | 849s 完整生成 42K token |
| 测试结果回传 | LLM 无从得知协议，用例统计 0 | 参考 runner 入契约，48 用例真实执行 |
| 审查 | 只能看清单，形式驳回 | 带源码 + 行号的实质审查 |
| 失败恢复 | optimize 一次失败即被权限拦截终止 | 修复闭环可迭代至收敛 |
| 感知完整性 | 规格 90% 被截断 | 万元级预算完整透传 |
