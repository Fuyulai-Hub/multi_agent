## 3. 匹配语义（确定性，不依赖 LLM）

`trigger` 四字段分两类，语义刻意分开：

**硬门禁**（不满足即淘汰，不参与排序）
- `requires_artifacts`：声明了就必须全部在黑板就位——它是**前置条件**。
  不计分是本次实现的关键取舍：若「产物齐备」也算适用性证据，那么任何依赖
  `requirement_spec` 的技能会被灌进每一个下游节点，`demo-delivery` 实测就是这种情况
  （见 §5 的意外命中）。
- `nodes` / `roles`：声明了就必须命中当前节点 id 或角色 id。

**适用性证据**（计分，全不命中即不注入）
- 关键词命中 `+2`（对需求文本做大小写无关子串匹配）
- 意图命中 `+3`（对 `{node_id, role_id, task_kind, delivery_shape, spec.tags}` 集合精确匹配）
- 作用域命中 `+1`

`min_score`（默认 1）之后按 `(-score, id)` 稳定排序取前 `max_items`（默认 3）。同一输入
必得同一输出，因此可回放、可 A/B。

渲染段（`render_for_prompt`）包含技能名/匹配度/命中依据/执行步骤（编号）/自检点/已知坑位，
并显式声明优先级：「只约束怎么做；与任务描述或交付契约冲突时以后者为准」——注入位置在
`# 交付契约` 之前，保证输出协议始终是最后一道强约束。

### 5.4 这次 fail 的根因（与技能注入无关，但如实记录）

取证对照：

| 证据 | 内容 |
| --- | --- |
| `code/tests/` | `test_functional.py`、`test_exception.py`、`test_core.py`、`test_io.py`、`test_boundary.py`、`run_all.py` 全都在 |
| `test_runs/iter01..03/result.json` | 三轮沙箱实际执行只有 boundary：10 → 7 → 18 条，`category` 计数恒为 `{'boundary': N}`，无一条 functional/exception |
| `artifacts/test_report` | `case_count` 声称 functional=14 / exception=5 / boundary=18（共 37），而 `coverage.functional.total=0`、`coverage.exception.total=0` |

即：**被测代码声明了功能/异常用例，但测试执行环节从未把它们跑起来**，覆盖度按真实执行结果求值为 0，
验收门禁与 `forced_fail` 正确地拒绝了「声称 37 例」的表象（`mas/leader.py:310`、`:347`）。

按四分类标注根因：**代码实现问题**（本项目 `tester` 节点的测试执行/发现范围只覆盖到
boundary 模块），不属于需求理解偏差、设计方案缺陷或环境构建问题。同一条需求在改造前的
`task06-tally-be` 曾以同样 13 步/3 回退通过（coverage functional=13/exception=7 全为真实执行），
说明这是运行级波动叠加 tester 执行范围缺陷，不是「该需求不可过」。

与技能注入的关系：`test` / `optimize` 节点的 prompt 头部为 `skills=[]`，即执行环节从未收到任何
技能文本；`intake` 收到的 `spec-scope-guard` 只约束功能点规模评估，不参与测试执行命令构造。
因此本次失败路径与本次改造无因果关系。为把这一点从「推理」变成「对照证据」，
已另起同需求、同配置、`skills.enabled=false` 的基线运行 `skillcheck-baseline-01`（结果见 §8）。

## 6. 能力边界（本次没做的）

1. **技能仍是「文本约束」，不是「可执行对象」**。`steps` 进 Prompt 由模型自觉执行，
   框架不核对它是否真照做；`scripts/` 目录里的脚本只有 `skill check` 冒烟会跑。
   要做执行闭环得走 `ToolRunner.register_local`，而那条路要求 `tools_enabled=true`
   且端点支持 `tool_calls`，与 `response_format(json_object)` 互斥（`docs/16` 的 05 文档 §4.3）。
2. **命中质量取决于手写 `trigger`**。当前 5 个手写技能只有 2 个声明了 `nodes`，
   其余靠关键词/意图，噪声与漏配都存在（§5.2 的「交付」即噪声例）。
3. **`distilled` 技能的复用路径尚未实测**。`distill_meta` 产出的 `keywords` 直接取需求 tags，
   因此只有「同类需求」才会命中；本次未构造跨需求复用场景，不给结论。
4. **真实运行只跑了一条任务**（`cli_tally_backend_only.md`）。多任务泛化、以及
   注入后缺陷率/门禁通过率是否变化，需要 A/B 两档多次运行——单条运行不构成效果证据。
5. 端点延迟噪声照旧（见项目记忆）：节点耗时不作为任何结论的依据，只看事件与落盘产物。

## 9. 合规取证：技能「进入请求」≠「模型照做」

§5.3 只证明了注入通道打通（`skill_matched` 事件、Prompt 正文含技能段、`skills_injected=6`）。
本节回答更强的问题：**模型是否真的按技能规定的做法产出**。方法是找技能独有的输出特征，
先排除「交付契约本来就要求它」这个混淆项，再与基线档对比。

### 9.1 排除混淆项：特征字段是否本来就写在契约里

全仓检索技能规定的标识符（`Grep` 覆盖 `mas/` 与 `config/roles/`）：

```
function_point_count / estimated_loc / scope_risk / batching_suggestion / unmeasurable_criteria
  → 只出现在 config/skills/spec-scope-guard/ 与 docs/04（本文早期分析），
    intake 节点的 JSON 契约与角色配置里一个都没有
untraceable / blocking_items / fp_id / suggestion
  → 只出现在 config/skills/evidence-cited-review/
```

结论：这些字段不是框架要求的，模型若产出它们，只能来自技能文本。混淆项已排除。

### 9.2 `spec-scope-guard`（intake，score=3）→ 确实照做 ✅

```
skillcheck-real-01   requirement_spec 顶层键含 scope_guard：
  scope_guard = {
    "function_point_count": 5, "estimated_loc": 200,
    "estimated_loc_note": "估算值：无模块信息，按功能点数 × 40 行的退化估算方式得出（5 × 40 = 200），非真实代码行数。",
    "scope_risk": false, "scope_risk_reason": "未提供 thresholds 阈值配置…",
    "batching_suggestion": [], "unmeasurable_criteria": [] }
skillcheck-baseline-01 requirement_spec 顶层键：无 scope_guard，六个特征字段全部缺失
```

三条独立证据，逐级收窄解释空间：
1. 容器键名 `scope_guard` 与技能步骤 6「把 {…} 写入 requirement_spec 的 scope_guard 键」逐字一致；
2. `estimated_loc_note` 复述了技能步骤 2 的**退化估算规则**（无模块信息时按功能点数 × 40），
   这不是任何契约要求的算法；
3. 该 note 里出现「估算」二字，对应 `error_handling` 第 1 条「摘要里必须写明「估算」二字」；
   技能还多给了一个契约里没有的 `estimated_loc_note` 键来承载它。
4. `scope_risk_reason` 说明「未提供 thresholds」，对应技能 inputs 里带默认值的 `thresholds` 参数。

### 9.3 `evidence-cited-review`（review + acceptance×3，score=1..3）→ 未照做 ❌

```
两档 review_report 顶层键相同：blocking / coverage / findings / recommendations / reviewed_files / stats / summary / verdict
技能规定的 untraceable、blocking_items、fp_id、suggestion 在两档正文中均为 False（检索命中 0）
两档 findings 每项键：file / line / message / rule / severity / symbol
```

即：技能要求「四项齐备且 suggestion 非空才进阻塞候选，其余降级进 untraceable」，
模型没有做这个改写——审查输出形状由 `# 交付契约` 的 JSON schema 主导，技能段被排在其前面但没赢得格式。
启用档 findings 更多（10 vs 3）不能算作技能生效的证据：这些是 AST 静态证据驱动的具体问题，
两档静态分析输入本就不同，属样本噪声。

### 9.4 `demo-delivery`（review，score=2）→ 无法判定，且注入无信息增量 ⚪

该技能六条步骤是「需求→方案→实现→审查→测试→验收」流水线的复述，与 `flow.yaml` 既有约束重合，
没有任何独有输出特征可供核验。它被匹配上是因为需求正文含关键词「交付」，
而它自身声明的 `requires_artifacts: [requirement_spec]` 在下游节点恒成立——
这类「通用复述型技能」会稳定命中大量节点，占用注入预算却不提供新规范。

### 9.5 汇总

| 技能 | 进入请求 | 模型照做 | 判据强度 |
| --- | --- | --- | --- |
| spec-scope-guard | ✅ | ✅ 是 | 键名+算法+措辞三重逐字对应，且基线档全缺 |
| evidence-cited-review | ✅ | ❌ 否 | 独有键在两档均不存在，输出形状由契约决定 |
| demo-delivery | ✅ | ⚪ 无法判定 | 步骤与流水线重复，无可核验特征 |

单样本结论：注入通道对**规约型**技能（规定输出里要有哪些字段、用什么算法）可以真实改变模型行为；
对**改写型**技能（要求把已存在的输出重新分类/降级）无效，因为它与交付契约争夺同一个 JSON 形状且输了。
这不是匹配器的缺陷，是「技能仍以纯文本形式与契约竞争」这一既有边界（§6 第 1 条）的直接体现。
