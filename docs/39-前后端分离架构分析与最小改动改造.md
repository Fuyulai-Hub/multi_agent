## 4. 是否已前后端分离：判定与证据

### 4.1 判定标准（业界通用的三条）

| # | 标准 | 含义 |
| --- | --- | --- |
| S1 | **职责分离**：前端只负责展示与交互，不含业务规则 | 业务逻辑变更不应改动前端代码 |
| S2 | **部署分离**：前后端是独立进程/容器，可各自独立发布 | 前端可静态托管到 CDN |
| S3 | **契约分离**：唯一的耦合面是 HTTP 接口契约，而非共享代码/共享目录 | 前端可用任意技术栈重写，后端无感知 |

### 4.2 当前状态（改造前）

| 标准 | 是否满足 | 证据 |
| --- | --- | --- |
| S1 职责分离 | **部分满足** | `app.js` 里有实质业务规则：`IMAGE_SUFFIXES` / `IMAGE_MAX_BYTES` / `MAX_IMAGES` 白名单常量（`app.js:26-28`）、上传文档 10 MB 上限（`app.js:959`）、上下文用量 80%/95% 两级阈值（`updateContextUsage`）、`profile` 与模型/供应商联动校验（`validateSettings`）、`navigate` 之外的全部状态机式 UI 逻辑。这些规则与后端配置（`system.yaml` 的 `llm.vision.max_image_bytes`、`mas/sources.py` 的 `IMAGE_SUFFIXES`）**手工保持一致**，属于典型的「双份真值」。 |
| S2 部署分离 | **不满足** | `frontend/server.py` 同一个进程里做三件事：托管 `index.html`/`app.js`/`style.css`（`_serve_static`）、提供全部 `/api/*`、**在进程内线程里执行流水线**（`start_run` → `threading.Thread`）。前端要改一个 CSS 也必须重启这个跑流水线的进程。 |
| S3 契约分离 | **名义满足、实质受限** | 接口是 JSON，前端只经 `fetch` 调用，没有共享代码——这一条其实做对了。但契约没有独立描述文件（无 OpenAPI），且路径硬编码为绝对路径 `/api/...`（19 处），前端无法指向另一个后端地址，因此**不能跨源部署**。 |

### 4.3 结论

**改造前是「同源单体 + 设计上已具备接口雏形」，不是前后端分离。**

说得更准确：它在**代码组织**上已经把页面、接口、编排分开放在不同目录（`frontend/` 与 `mas/`），接口层也确实只做 HTTP ↔ Python 的转换；但**部署上三个进程角色被压进同一个 Python 进程**，且前端写死了同源绝对路径。所以准确表述是：

> 一个「接口已成型、但部署未解耦」的同源单体。

这一点在 `docs/01` 里也有对应记录（「前端面板是纯标准库 `http.server`」，1555 行），只是当时没有把它作为架构问题提出。

## 5. 最小改动改造方案

### 5.1 设计原则

1. **不做无收益的重写**：不引入 FastAPI、不引入 React/Vue、不加构建工具。收益不在「技术栈更现代」，而在「部署与职责解耦」。引入构建链会破坏项目「零依赖可离线跑通」的核心卖点。
2. **默认行为逐字节不变**：不传新参数时，服务行为与改造前完全一致（同源托管 + 同源接口）。这是所有既有测试的基线。
3. **只在真正的耦合点上动刀**：耦合点只有两个——(a) 后端硬绑定「自己托管静态文件」，(b) 前端硬绑定「接口就是同源 `/api`」。其余代码无需改动。

### 5.2 改动点清单

| # | 文件 | 改动 | 行数量级 |
| --- | --- | --- | --- |
| C1 | `frontend/server.py` | `Handler.static_dir` 类属性 + `--no-static` / `--dist` 两个参数；`_serve_static` 在 `static_dir is None` 时直接 404 | 约 20 行 |
| C2 | `frontend/server.py` | `_cors_headers` 增加 `Access-Control-Allow-Credentials: true`（分离部署跨源带 Cookie 必需；仍只回显白名单具体来源，不破坏「不发 `*`」的既有约束） | 2 行 |
| C3 | `frontend/app.js` | 顶部读 `?api=` / `?static=` 两个查询参数，得到 `API_BASE` / `STATIC_BASE`；19 处 `fetch("/api/...")` 改为 `fetch(API_BASE + "/api/...")` | 约 20 行 |
| C4 | `frontend/app.js` | 新增 `backendPath()`：上传返回的是**后端视角绝对路径**，前后端不同机时把文件名重挂到 `?static=` 指定的根下 | 约 6 行 |
| C5 | `tests/test_frontend_{react,skills}.py` | 两处断言用正则匹配字面量 `fetch("/api/react"`，加了前缀后失配；改为匹配路径本身（约束强度不变） | 2 行 |

| C7 | `README.md` | 启动参数表补 `--dist` / `--no-static`，加分离部署样例 | 约 10 行 |

**总计：生产代码约 48 行，测试约 62 行。`mas/` 全部模块零改动。**

### 5.3 关键设计取舍

#### (a) 为什么用查询参数而不是构建期注入

常见做法是 `VITE_API_BASE` 之类的环境变量，但那要求构建工具。本项目无构建，`app.js` 是浏览器直接加载的静态文件。查询参数是零工具链条件下唯一能做到「同一份代码、多套部署」的机制：

```text
同源部署：  http://host:8000/                      （API_BASE = ""，与改造前等价）
分离部署：  http://fe:8001/index.html?api=http://be:8000
```

#### (b) 为什么不用 `localhost` 作默认值

写死 `const API_BASE = "http://localhost:8000"` 在三种常见场景下都会错：手机/局域网访问时 `localhost` 指向**访问者自己**；反向代理后 HTTPS 页面里的 `http://` 请求会被混合内容策略拦截；IPv6 环境需要 `[::1]`。默认空串 + 相对路径天然支持同源与反向代理，是最稳的默认。

#### (c) 为什么上传路径需要单独换算

`mas/sources.py:426` 返回 `str(target)`，是**后端进程视角的绝对路径**（如 `G:\...\workspace\uploads\x.md`），随后 `POST /api/run` 会用它做 `restrict_panel_path` 校验。前后端同一台机器时无需处理；不同机器时前端拿到的是「后端上的路径」，因此需要 `?static=` 提供可映射的根：

```text
后端返回          G:\ops\multi_agent\workspace\uploads\req.md
前端 ?static=     /home/ops/multi_agent        （容器内挂载路径）
前端提交          /home/ops/multi_agent/workspace/uploads/req.md
```

**限制（必须说明）**：这是「字符串拼接」而非真正的对象存储引用。跨机器部署要求前端能拿到后端同一存储上的路径映射；如果后端改用对象存储或引入上传 ID，应改为 `/api/upload` 返回 `upload_id`、`/api/run` 按 `upload_id` 解析——那是另一处改动，不在本次最小方案内。

#### (d) 为什么 CORS 是「显式白名单」而不是「全放开」

改造前已实现 `_origin_allowed`（同源或白名单）与「不发 `*`」。分离部署下如果图省事改成 `*`，会把 `/api/llm`（可写 LLM 凭据）、`/api/run`（可执行任意需求）暴露给任意网页。因此方案选择：**保持失败关闭**，分离部署必须显式设置 `MAS_PANEL_ORIGINS`。实测（第 6 节）确认未声明来源仍被 403。

### 5.4 未纳入本次改动的问题（需要更大改动，如实列出）

| 问题 | 现状 | 为什么不在最小方案内 |
| --- | --- | --- |
| 前端是「同源绝对路径 + 轮询」 | 1.5s 轮询，无 WebSocket/SSE | 换成 SSE 需要后端新增流式端点、前端改造渲染循环，属于功能优化不是分离必需 |
| 无 OpenAPI 契约 | 接口只存在于 `server.py` 的 docstring | 生成契约需要引入依赖或手写 AST 提取器；当前 19 个路由规模下手写成本高于收益 |
| 前端业务常量与后端重复 | 图片后缀/大小/张数在两处 | 改成 `/api/config` 下发需要新增接口并调整前端启动时序 |
| `--no-static` 下 `MAS_PANEL_TOKEN` 的登录跳转 | `/?token=` 换取 Cookie 的入口在后端；分离时应由前端宿主提供登录页或用 `Authorization` 头 | 需要前端新增登录页，改动面超过「分离」本身 |
| 后续若换前端技术栈 | 需重写 `app.js` | 接口契约已稳定（19 个 JSON 路由），**现在重写的边际成本最低**——这正是这次先把边界拆开的意义 |

## 7. 演进建议（按投入产出排序）

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| P0 | 已做：部署解耦（本方案） | 前后端可独立发布，边界清晰 |
| P1 | 前端业务常量改为 `/api/config` 下发 | 消除「双份真值」，改一处即全端生效 |
| P2 | 轮询改 SSE（`GET /api/run/events?since=<seq>`） | 1.5s 轮询在大事件流下浪费带宽；SSE 只需后端加一个流式端点 |
| P3 | 补 OpenAPI 契约 | 前端若换栈（Vue/React）可自动生成 client |
| P4 | 多用户与 RBAC | 当前是单一共享令牌，所有访问者权限相同 |

> 注意：P2 与 P3 都会触碰 `frontend/server.py` 的路由层。当前该文件已 1325 行，且承担「静态托管 + 接口 + 运行启动」三职；建议在 P2 之前先把路由分发抽成独立的 `routes` 表（数据结构化，不改行为），为后续拆分留出缝。
