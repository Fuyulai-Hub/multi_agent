# 架构重构 P0 最小化实施与验证报告

> 版本：v1.0　　实施日期：2026-10-14
> 依据：`docs/13-多Agent架构重构方案.md` §9「立即可执行的前三件事」中的前两件（代码部分）
> 原则：**尽可能保持现有功能与接口不变**；只做真实可执行的最小改动；实施后以实际运行验证

---

## 0. 结论（TL;DR）

对重构方案中唯一的**隐性正确性缺陷**（P0-A）与**闭环缺口**（P0-B/P0.3）实施了最小化修复，
外加一项支撑性修复（守护经验 action_key 与文档声明不一致，见 §2.4）。

| 项 | 实施前（实测） | 实施后（实测） |
| --- | --- | --- |
| 同一 Leader 实例并发运行 | A 轮 4 条协商事件 / B 轮 0 条（**证据链串扰**） | A 轮 2 条 / B 轮 2 条（**零串扰**，3 次重复稳定） |
| `reinforce()` 调用点 | 0（死代码） | 回退归因 + 终态双路径接线，事件可审计 |
| `promote()` 晋升依据 | 纯 `hits`（坏经验可升 L3） | `hits × success_rate`（高失败率经验不晋升） |
| 自学习契约（离线两轮） | 步数 11→7、缺陷 5→0、驳回 1→0 | **完全保持**（连续 4 轮稳定） |
| 测试套件 | 141 通过 | **152 通过**（新增 11，0 失败） |

公开接口零变更：`Leader(config).run()/distill_skill()`、`ctx.consult(...)`、
`ExperienceLibrary.add/retrieve/promote` 签名与行为不变；`reinforce()` 由无调用者的
内部方法扩展为三态反馈（新增可选参数，旧调用形态仍兼容）。

## 1. 方案审查结论（实施依据）

对 `docs/13` 的审查发现三点，直接决定了本次实施范围：

1. **P0-A 的真实形态与文档描述有出入**。文档称「两个 Leader 实例并发即串扰」；
   实测（§4.1）：两个**不同实例**因实例属性遮蔽而侥幸隔离，真正的缺陷是
   **同一实例被并发复用**（`leader = Leader(config)` 后在多线程中多次 `run()`，
   后一次运行覆盖前一次的运行时绑定）。两种形态修复后都由构造保证隔离。
2. **P0-B 若按方案原文全量接线会破坏自学习契约**。方案设计「回退即对全部已注入
   经验降权」；实测首轮运行中，test 节点失败时在册的只有 `review_rejected` 类经验
   （docstring 守护），全量降权会误伤它们 → 第二轮不再注入 → 审查驳回复现 →
   `test_second_run_self_learning` 失败。因此降权必须**按失败归因**（§2.3）。
3. **文档声明的守护动作键与实际提炼不一致**（§2.4）：README 与 docs 01/02/09 五处
   声明 `guard_calc_shipping__boundary`（算子键），实际生成 `guard_FP-03__boundary`
   （功能点键），离线 Provider 只认前者——守护经验从未真正生效，自学习仅靠 op 无关的
   `boundary_tri_state` 勉强维持，契约脆弱。此为与文档相违的实现缺陷，需一并修复。

14 周完整路线图（异步化、Storage 抽象、Docker、混合检索等）不在本次最小化范围。

## 2. 改动点

### 2.1 P0-A：消灭类属性运行时绑定（`mas/leader.py`）

- 删除类属性 `_current_bus/_current_events/_current_agents/_current_ctx` 与 `_bind_runtime()`；
- `_consult_factory(ctx, bus, events, agents)`：运行时引用由参数显式传入并被闭包捕获，
  每次 `run()` 持有独立运行时；`_build_tool_runner(events)` 同样改为显式传参；
- `run()` / `distill_skill()` 两个调用点同步更新。

### 2.2 P0-B：`reinforce()` 三态反馈（`mas/experience.py`）

- `Experience` 新增 `hits_success` / `hits_failed` 计数字段与 `success_rate` 属性
  （无反馈数据取中性 0.5；旧库文件缺字段时默认 0，**向后兼容**）；
- `reinforce(ids, *, outcome, reward, evidence)`：
  - `positive`（运行通过）：置信度 `+reward_on_effect`（0.05），`hits_success+1`，
    发 `experience_reinforced` 事件；
  - `negative`（回退归因）：置信度 `-penalize_on_rollback`（0.1，下限 0.05），
    `hits_failed+1`，发 `experience_demoted` 事件；
  - `neutral`（未通过但无法归因）：仅留痕，不奖不罚；
  - 兼容单字符串入参（旧形态 `reinforce(ids, reward=...)` 参数保留）；
  - 锁内**强制重载**后修改，避免同工作区并发反馈互相覆盖（与 `add()` 模式一致）。

### 2.3 P0-B 接线：回退归因降权 + 终态奖惩（`mas/leader.py`）

- 新增 `_FAILURE_TRIGGER_BY_EVENT` 映射（失败事件 → 经验 trigger，与提炼规则一一对应）：
  `review_completed→review_rejected`、`bug_reported→bug_found`、`gate_evaluated→acceptance_rejected`；
- 回退分支：取失败节点本次执行的事件（校验 `verdict=reject` / `passed=false`），
  **只降权 trigger 匹配的已注入经验**——「声称能预防该类失败却没能预防」才降权，
  无关经验不误伤；同运行内不重复降权；
- 终态（verdict 计算后、晋级前）：通过 → positive（跳过本运行已降权者）；
  未通过 → neutral。

### 2.4 P0.3 + 支撑修复

- `promote()`：晋升依据由纯 `hits` 改为 **`hits × success_rate`**（有效成功次数），
  高失败率经验不得晋级；
- 缺陷守护经验的 `action_key` 改为算子键优先（`guard_<op>__<category>`，缺 op 回退 fp_id），
  与 Provider 的 `guarded_ops` 匹配逻辑及五处文档声明对齐（`leader.py:_facts_from_events`
  透传 `op`，`experience.py:extract_from_events` 生成键）。

### 2.5 配置（`config/learning.yaml`）

- `feedback` 段新增 `penalize_on_rollback: 0.1`（旧配置缺该键时代码取同值默认，兼容）。

### 2.6 测试

- `tests/test_runtime_isolation.py`（新增，6 例）：并发隔离（同实例/两实例）、
  协商闭包绑定、positive/negative/neutral 端到端、归因精确性（不误伤无关经验）；
- `tests/test_experience.py`（更新/新增 8 例）：新晋升语义、reinforce 三态、
  下限与持久化、算子键生成；
- `tests/test_function_calling_e2e.py`（2 例）：适配 `_build_tool_runner(events)` 新签名。

## 3. 执行结果（实测记录）

### 3.1 并发隔离（修复前后对比，探针：各轮 `negotiation_closed` 事件数，单跑基线=2）

| 形态 | 修复前 | 修复后 |
| --- | --- | --- |
| 同一 Leader 实例并发 | A=4 / B=0（**B 的协商事件写进 A 的日志**） | A=2 / B=2 ✅（3 次重复稳定） |
| 两个不同实例并发 | A=2 / B=2（侥幸隔离） | A=2 / B=2 ✅（构造保证） |

### 3.2 自学习契约（离线 Provider，同一工作区连续 4 轮）

| 轮次 | 结论 | 步数 | 回退 | 审查驳回 | 缺陷 |
| --- | --- | --- | --- | --- | --- |
| 1 | pass | 11 | 2 | 1 | 5（闭环 5） |
| 2 | pass | 7 | 0 | 0 | 0 |
| 3 | pass | 7 | 0 | 0 | 0 |
| 4 | pass | 7 | 0 | 0 | 0 |

守护经验演化：`guard_calc_shipping__boundary` L1→L2→L3，`hits_success` 逐轮 +1、
`hits_failed=0`；无错误降权。

### 3.3 坏经验降权端到端（G2 验收）

预置一条 trigger=bug_found 但实际无效的守护经验（L2, conf 0.8）→ 运行（test 失败回退）
→ 该经验 `hits_failed≥1`、置信度 0.8→0.7、`success_rate=0`、**不晋升**；
同时一条无关的 `review_rejected` 类经验 `hits_failed=0` 且获得正向反馈（归因不误伤）。

### 3.4 旧数据兼容

仓库真实 workspace 的 83 条旧格式经验（无 `hits_success` 字段）直接加载运行：
`success_rate` 取中性 0.5，一轮后 11 条获得 positive 反馈并正常落盘，无异常。

### 3.5 CLI 与前端

- `mas run`（文档需求）：pass，11 步 / 2 回退 / 5 缺陷闭环，与基线一致；
- `mas experience list`（含新计数字段）、`mas report show latest`、
  `mas skill add --from-run`（走改动后的 `distill_skill` 路径）：均正常；
- 前端 `frontend/server.py`：`/`、`/api/runs`（35 runs）、`/api/experience`（83 条）、
  `/api/metrics` 全部 200。

### 3.6 真实 LLM 路径（demo，进行中）

`python -m mas demo`（openai_compatible + 真实网关）持续运行：多轮真实歧义协商
（tester 提问 → developer 应答 → `negotiation_closed`）内容真实有效，回退/升级路径
正常触发，无崩溃、无错误输出。该路径的不稳定性为文档已注明之既有特征。

## 4. 验证结论

1. **功能正确性**：P0-A 串扰消除（同实例并发从 A=4/B=0 恢复为 A=2/B=2，与单跑基线一致）；
   P0-B 闭环真实闭合（降权/奖励/晋级均有端到端证据与事件留痕）；P0.3 坏经验不再晋升。
2. **系统稳定性**：全量测试 152/152 通过；自学习契约连续 4 轮稳定；并发隔离 3 次重复稳定；
   真实 LLM 路径长时运行无错误。
3. **与原有架构兼容性**：公开接口零变更；自学习两轮契约（11→7 步、5→0 缺陷、1→0 驳回）
   完全保持；83 条旧格式经验无缝兼容；CLI/前端全链路可用。

## 5. 已知限制（诚实声明）

- 同工作区**多运行并发**时，经验库计数（hits/hits_success）仍为先到先得式的
  文件锁串行写，`reinforce` 已做到锁内强制重载，但 `retrieve()` 的 hits 自增仍沿用
  既有模式（先写覆盖风险仅影响计数精度，不损坏文件、不串扰运行证据链）。
- 回退归权是「trigger 匹配」粒度而非「因果证明」粒度；无法归因时保守不降权（neutral）。
- `neutral` 终态不写盘（仅返回命中数），避免无变化写放大。
- 14 周路线图其余项（异步化、Storage 抽象、Docker 隔离、混合检索、可观测性）未动，
  见 `docs/13` 分阶段规划。
