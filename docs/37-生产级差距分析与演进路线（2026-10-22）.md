# multi_agent 生产级差距分析与演进路线

> 分析日期：2026-10-22
> 代码基线：本仓库当前工作区（`mas/` 44 个 Python 文件，`mas/` + `frontend/` 合计 18,166 行）
> 分析对象：8 节点固定流水线（product → developer → reviewer → tester → reporter + Leader），MySQL 索引层 + Redis 协调层 + Streams worker + 沙箱 + 技能/MCP/ReAct 可选能力
> 结论口径：区分「原型质量」与「生产可依赖」，所有判断尽量落到 `文件:行号` 或实测数据；无法从代码证明的能力明确标注为未验证。

---

## 0. 结论（BLUF）

**当前系统是一个工程质量明显高于普通 demo 的本地代码交付原型，成熟度大约在 L1.5（介于「原型」与「单机可用」之间），还不是生产级。**

它已经具备的生产雏形：确定性状态机、受限步数与回退预算、append-only 事件日志、版本化黑板、真实执行测试、LLM 重试/流式/上下文压缩、Redis Streams 与 worker、配置门控与软依赖降级。这些不应推倒重来。

但距离生产级还有四个**硬缺口**，它们的共同点是：**不是靠再加 Agent、技能或 ReAct 能解决的**。

| 序号 | 硬缺口 | 一句话事实 | 后果 |
|---|---|---|---|
| P0-1 | 执行边界 | 生成代码以当前用户权限跑在宿主机的 `subprocess` 里，无网络/文件系统隔离 | 一条恶意需求或提示注入就可能让生成代码读宿主凭据、访问其他运行、外连 |
| P0-2 | 验证权威 | 测试由被测方每轮重写，覆盖率按模型填的 `fp_id` 统计，审查 `blocking` 直接采信 LLM JSON | 可以通过「把测试写弱」而不是「把代码写对」通过门禁 |
| P0-3 | 持久化与租约 | Leader 状态全在内存，`run_summary.json` 只在结束时写；消息 10 分钟可被其他 worker 认领，运行可长达 4 小时 | 重启即从头跑、重复执行、双倍成本、取消失效 |
| P0-4 | 身份与租户 | 面板无认证、CORS `*`、`GET /api/llm` 回显完整 Key、`requirement_path` 可读任意绝对路径、全局单 workspace | 一旦离开 localhost，面板就是一个高权限的代码执行/数据外泄面 |

**时间量级（估算，不是承诺）**：

- 单租户、内部可信需求、以「产出可审查的 PR」为交付目标：**2–3 人约 10–12 周**；单人约 4–6 个月。
- 对外开放的多租户 Agent 平台：在上述基础上**再加 3–6 个月**（身份、隔离、配额、计费、合规、HA）。
- 若只做「本地演示/课程项目」，当前状态已经足够；但不应以「生产级 Agent」对外描述。

**一个必须先纠正的直觉**：生产级的核心不是「Agent 更自主」，而是「**系统在不可信输入、进程崩溃、重复投递、恶意代码和多人使用下仍然可控**」。当前系统最该补的是信任边界与验证权威；继续加角色、加技能、打开 ReAct，只会扩大攻击面和成本。

## 1. 评估口径：什么叫「生产级」

### 1.1 本文采用的定义

一个生产级 Agent 系统至少要同时满足六件事：

1. **边界可信**：不可信输入（需求文本、生成代码、第三方依赖）不能突破执行环境，不能读取宿主或其他租户的数据。
2. **结论可信**：验收结论来自独立于生成方的证据，而不是模型自述；证据可复现、可追溯、防篡改。
3. **失败可控**：进程被杀、网络抖动、Redis 故障、重复投递时，运行可恢复、可重试、无重复副作用；取消能及时生效。
4. **身份可控**：谁发起了运行、能看什么、能改什么、能花多少，都有认证、授权、配额与审计。
5. **可运维**：有镜像、迁移、健康检查、指标、日志、追踪、告警、SLO、回滚手册。
6. **质量可度量**：有冻结的基准集与隐藏测试，能回答 pass@1、误通过率、单次成功成本、p95 时延，而不是只看「这次跑通了」。

### 1.2 成熟度标尺

| 等级 | 含义 |
|---|---|
| L0 | 没有该机制 |
| L1 | 原型级：happy path 可用，异常/对抗/并发下不可依赖 |
| L2 | 单机可用：可信单用户、手工运维下可工作 |
| L3 | 生产可依赖：经过故障与对抗测试，有自动化与 SLO |
| L4 | 规模化：多租户、HA、合规、成本治理 |

### 1.3 评分卡

| 维度 | 当前事实 | 等级 | 生产门槛 |
|---|---|---|---|
| 流程编排 | 固定 8 节点、`max_steps=40`、回退/重试预算、转移显式 | **L3** | 保持；补节点级检查点 |
| 证据链 | `events.jsonl` + 版本化黑板 + `refs`，可复盘 | **L2** | 加哈希链/签名、对象存储、保留策略；当前可追溯但不可防篡改 |
| LLM 韧性 | 重试/退避、流式、空输出降级、上下文 90%/95% 压缩 | **L2** | 加模型网关、预算、限流、熔断、跨 provider 回退 |
| 验证可信度 | 测试由 tester 每轮生成；覆盖率=模型填的 FP 编号比例；审查结论=LLM JSON | **L1** | 独立 verifier + 冻结/隐藏测试 + 真实覆盖率 + 确定性规则 |
| 执行隔离 | 宿主 `subprocess` + 命令白名单 + 环境变量清洗；无 netns/fs 隔离 | **L1** | 容器/microVM、无网络、非 root、只读根、资源上限、无宿主挂载 |
| 持久化/恢复 | 运行态在内存；结束才写 `run_summary.json`；无检查点 | **L1** | 每节点检查点 + 幂等恢复 + 对象存储 |
| 队列/租约/幂等 | Redis Streams + PEL/XAUTOCLAIM；10 分钟可被认领；无续租/运行锁 | **L1** | 租约续期 + fencing + 单运行锁 + 幂等副作用 |
| 取消/预算/配额 | 节点边界轮询取消；无运行级 token/成本/时限预算 | **L1** | 流式期间可取消；预算硬停；租户配额 |
| 身份/授权/租户 | 无认证；CORS `*`；单 workspace；无租户概念 | **L0** | OIDC + RBAC + 租户隔离 + 审计 |
| 密钥/数据治理 | Key 可回显；凭据明文文件；prompt/trace 落盘无脱敏/保留策略 | **L1** | 密钥托管、只写不回显、脱敏、加密、保留/删除 |
| 可观测性 | 事件、LLM trace、prompt、metrics、timeline 很完整 | **L2** | OTel 全链路 + 指标 + 告警 + SLO 看板 |
| CI/CD/部署 | 无应用 Dockerfile、无 CI、无迁移自动化、依赖未锁定 | **L0** | 镜像、流水线、迁移、健康检查、灰度/回滚 |
| 质量评测 | 48 次探索性运行，20 次 pass；无冻结基准/隐藏测试 | **L1** | 30–50 题冻结基准 + 隐藏测试 + 夜间回归 + 发布门禁 |
| 交付集成/人工闸门 | 产物落在 `workspace/`，无 Git/PR/CI/人工批准 | **L0** | 分支 + PR + CI + 人工 approve 后合并 |
| 多语言验证 | 只真正执行 Python 测试；非 Python 交付会报 `verification_gap` | **L1** | 按语言提供编译/测试镜像；否则明确限定支持范围 |

**综合判断**：除「编排」和「证据记录」外，其余关键项集中在 L0–L2。系统的工程习惯不错，但生产属性尚未建立。

## 2. 已经做对的部分（生产化时必须保住）

这一节不是表扬，而是确定「不要重构掉什么」。

1. **确定性状态机而非自由漫游的 Agent 群**。`config/flow.yaml` 把 8 个节点、转移、门禁、回退预算写死；`mas/leader.py:478` 的循环有 `max_steps` 上限，`mas/leader.py:1082` 的节点重试有 `max_attempts`。这带来可审计、可重放、可定位问题，是生产系统最需要的属性。不要为了「更像多 Agent」把它换成 LLM 动态路由。
2. **事件溯源 + 版本化黑板**。`events.jsonl` 记录每次节点动作、证据、门禁和回退；黑板产物带版本；`refs` 让报告能指回证据。这个方向是对的，生产化只需补「防篡改 + 持久存储」。
3. **真实执行，不是嘴炮**。tester 会写测试文件、用沙箱跑、解析 `<<<MASS_RESULT>>>`，没有用例回传就判失败（`mas/agents/tester.py:432-440`）。这比多数「让 LLM 自评」的 demo 强。
4. **LLM 调用有工程化处理**。重试/退避、流式、空输出降级阶梯、上下文压缩、token 估算都在；`mas/llm.py` 与 `mas/context.py` 不是简单封装。
5. **配置门控与软依赖降级**。MySQL/Redis/MQ/技能/MCP 都有开关，缺依赖时回到旧路径而不是崩掉。这种「默认关闭、逐字节兼容」的改动习惯，对生产发布很有利。
6. **测试与文档的诚实性**。`tests/` 有 32 个测试文件、457 个 `test_` 方法；2026-10-22 全量 `python -m unittest discover -s tests` 实测 `Ran 457 tests in 89.732s / OK`。`docs/11` 明确记录过 probe-02 的假通过。这种「把失败写进文档」的文化，比任何架构图都更接近生产团队。

## 3. 四个 P0 硬缺口（不补不能上线）

### 3.1 P0-1：执行边界不是安全边界

#### 事实

- `mas/sandbox.py:220-278` 的执行方式就是：

  ```python
  completed = subprocess.run(
      cmd, cwd=str(workdir), capture_output=True, text=True,
      timeout=timeout or self.timeout, env=env, shell=False, **spawn_kwargs,
  )
  ```

  子进程直接跑在宿主机、当前用户、当前工作区。

- `mas/sandbox.py:281-307` 的 `_check_command()` 只检查 `cmd[0]` 的 basename。它挡的是「框架自己发起 `bash -c`」，挡不住生成代码内部：

  ```python
  import os, subprocess, socket, ctypes
  os.system("...")
  subprocess.run(["...", "..."])
  socket.create_connection(("...", 443))
  ```

- `sandbox.analyze()` 确实会产出 `network_import`、`sandbox_command_bypass` 等 findings，但 tester 的 `_preexec_diagnosis()` 只筛选 `sandbox_command_bypass` / `*_not_imported` 一类，`mas/agents/tester.py:298-305` 仅 `events.emit("test_environment_gap", ...)`，随后 `mas/agents/tester.py:327` 仍然执行测试文件；`network_import` 甚至不在执行前诊断的筛选集合里。**发现了不等于阻断了，而且有些发现连事件都不会触发。**
- `mas/sandbox.py:309-319` 只剔除名字里含 `KEY/TOKEN/SECRET/PASSWORD/PASSWD/CREDENTIAL` 的环境变量；它不限制文件系统。生成代码仍可读 `config/credentials.yaml`、`~/.ssh`、其他 `workspace/runs/<id>` 的 `events.jsonl` 和 prompt。
- `mas/sandbox.py:321-335` 的 rlimit 只在 POSIX 且 `threading.active_count() == 1` 时注入；前端面板是多线程，worker 也常是多线程，因此实际经常退化为「无 rlimit」；Windows 直接返回 `{}`。`mas/sandbox.py:355` 的隔离标签会如实写 `windows-no-rlimit`，但**标签不是隔离**。
- `mas/sandbox.py:121-128` 的注释自己写清楚了：没有网络命名空间隔离，静态检测只是「让高危依赖可见」。
- `subprocess.run(timeout=...)` 超时只会杀掉直接子进程；在 Windows 上孙进程可能存活，继续占用 CPU/端口。当前没有进程组/作业对象清理。

#### 为什么是生产 blocker

这是一个「执行模型生成代码」的系统。模型生成什么，取决于需求文本、检索到的技能、历史经验和模型端点。任何一环被提示注入或投毒，生成的测试/代码就可以：

1. 读取 `config/credentials.yaml` 或用户目录下的云凭据；
2. 通过 `socket` 把数据发到外部（`network_import` 只是 major finding，不阻断）；
3. 读取其他运行的需求、代码、报告，造成跨任务数据泄露；
4. 写满磁盘、fork 炸弹、占用端口，影响宿主上的其他服务；
5. 在 `--host 0.0.0.0` 的面板场景下，被局域网内任何人触发。

**「命令白名单」防的是手滑，不是恶意。** 生产环境必须把「不可信代码」当成真的不可信。

#### 最小改造

1. **抽象 Executor 接口**，把 `mas/sandbox.py` 的 `run()` 改为委托：

   ```python
   class Executor(Protocol):
       def run(self, cmd: list[str], *, cwd: str, timeout: int,
               env: dict[str, str], result_marker: str | None) -> ExecResult: ...
   ```

   - `LocalSubprocessExecutor`：只允许开发/测试环境，启动时打印醒目的 `UNSAFE_LOCAL_EXECUTOR`。
   - `ContainerExecutor`：生产默认。Docker/Podman 起步，安全要求高时换 gVisor / Firecracker / 托管沙箱。

2. **容器参数最小集**：
   - `--network none`（需要装依赖时，单独走 egress allowlist 代理，不能直连）；
   - `--read-only`，`/tmp` 用 `tmpfs`，工作区只挂载**本次运行的副本**；
   - `--user 65534:65534`，`--cap-drop ALL`，`--security-opt no-new-privileges`；
   - `--pids-limit`、`--memory`、`--cpus`、`--ulimit fsize`、磁盘配额；
   - seccomp/AppArmor 默认 profile；
   - 不挂 Docker socket、不挂宿主 `config/`、不注入任何宿主凭据；
   - 结束后 ` tar` 拷出产物并校验，容器即弃。

3. **失败关闭**：生产配置下如果容器运行时不可用，**拒绝执行并判失败**，不能自动退回 `subprocess`。开发模式可以退回，但必须在事件和报告里标注。

4. **进程树清理**：用进程组/Job Object 启动，超时杀整棵树；容器场景直接 `stop --force`。

5. **红队用例**（先写测试，确认当前系统会失败，再改）：
   - 读 `../../config/credentials.yaml`；
   - `socket.connect` 到外部；
   - `subprocess` 起 `cmd.exe` / `sh`；
   - 写 `C:\Windows\Temp` 或 `/etc`；
   - fork 100 个进程；
   - 读其他 run 目录；
   - 通过符号链接越界；
   - 安装 pip 包。

6. **执行环境与凭据分离**：LLM Key 只存在于 worker 进程内存，绝不进入 executor；executor 容器不挂载 `config/`。

> 参考实现顺序：先 Docker + `--network none` + 非 root + 资源限制，能挡住 90% 的现实风险；再评估 gVisor/Firecracker。不要一开始自研内核级隔离。

### 3.2 P0-2：验证权威是模型自报，不是独立证据

#### 事实

- `mas/agents/tester.py:268-289` 每轮把 LLM 生成的 `tests/*` 写入工作区；同名文件被覆盖。也就是说，**测试套件由被测方在每轮重新生成**。
- `mas/agents/tester.py:782-796` 的 `_coverage()`：

  ```python
  fps = {case.get("fp_id") for case in category_cases if case.get("fp_id")}
  coverage[category] = {
      "total": len(category_cases),
      "fps": len(fps),
      "fps_total": fp_total,
      "rate": round(len(fps) / fp_total, 4) if fp_total else 0.0,
  }
  ```

  统计的是「测试用例元数据里填了多少个功能点编号」，不是代码行/分支覆盖，也不验证该用例是否真的执行了对应路径。给 25 个用例都填上不同 `fp_id`，覆盖率就是 1.0，哪怕断言是空的。
- `mas/agents/reviewer.py:219-227`：

  ```python
  verdict = str(data.get("verdict", "reject"))
  ...
  result.status = "pass" if verdict == "pass" else "fail"
  ```

  `blocking` 也直接取 `data.get("blocking", 0)`。框架没有用 AST/SAST 的确定性 findings 重算阻塞数；LLM 说 0 就是 0。
- `config/flow.yaml` 的验收门禁读的是：

  ```
  test_report.summary.failed == 0
  test_report.coverage.functional.rate >= 1.0
  review_report.blocking == 0
  bug_reports.open == 0
  ...
  ```

  这些字段全部来自模型/Agent 自己发布的产物，形成「模型生成测试 → 模型报告结果 → 模型审查 → 门禁读模型字段」的闭环。
- `docs/11` 记录过 `task04-cpp-probe-02` 的假通过：C++ 需求补了一份 Python 复刻 + Python 测试，25 条全过、三类覆盖率 1.0、8 项门禁全绿，而 `.hpp` 从未编译。后来加的 `verification_gap`（`mas/agents/tester.py:566-625`）修掉了这个具体漏洞，但**「测试由被测方生成、门禁读自报字段」的结构没有变**。
- `tests/` 里的 457 个单测是**框架自身**的测试，不是交付质量的基准集；它们不能证明某次生成的应用是对的。

#### 为什么是生产 blocker

生产验收要回答的是「这个交付物是否满足需求」，而不是「模型是否声称它满足需求」。当前结构存在稳定的 reward hacking 路径：

1. 测试写弱（少断言、只测 happy path、把失败 catch 掉）；
2. 覆盖率靠填 `fp_id` 注水；
3. reviewer 被同一段代码说服，`blocking=0`；
4. 门禁全绿，报告写「验收通过」。

这不是模型「不诚实」，而是系统把**生成方和验证方合并**了。只要验证方没有独立证据，通过率就没有意义。

#### 最小改造

1. **职责分离**：
   - `TestAuthor`：只负责提出测试草案；
   - `TestVerifier`：独立进程/服务，持有冻结测试与隐藏测试，负责执行、覆盖率、变异测试、签名；
   - 生成方不能修改 verifier 的测试目录，只能提交「测试变更请求」，由 verifier 版本化。

2. **冻结测试**：
   - 首次通过审查后，对 `tests/` 全量文件计算 SHA-256，写入 `test_manifest.json`；
   - 后续轮次如果 hash 变化，必须走显式 review 并生成新版本；
   - 门禁增加 `test_manifest.hash == verifier.attestation.test_hash`；
   - 隐藏测试不进入生成方可见的工作区。

3. **真实覆盖率**：
   - Python：`coverage.py` / `pytest-cov`，产出 `coverage.json`；
   - JS/TS：`c8` / `istanbul`；
   - 浏览器：Playwright 断言 + 截图/视频证据；
   - C/C++：编译 + 单测框架（GoogleTest/Catch2）+ `gcov`/`llvm-cov`；
   - 覆盖率门禁读 verifier 生成的报告，不读模型填的 `fp_id`。

4. **变异测试**：对核心模块注入变异体，要求 mutation score 达到阈值（例如 60%）。这比行覆盖率更难造假。

5. **确定性阻塞重算**：
   - reviewer 的 LLM findings 只作「建议」；
   - 框架用 AST/SAST/类型检查/编译/lint/依赖漏洞扫描的结果重算 `blocking`；
   - `review_report.blocking` 由框架写入，而不是采信模型 JSON；
   - 门禁增加 `verification.attestation.valid == true`、`verification.mutation_score >= 0.6`、`verification.hidden_tests.failed == 0`。

6. **证据签名**：verifier 的报告包含测试文件 hash、容器镜像 digest、命令、退出码、覆盖率、时间戳、verifier 身份，并用服务端密钥签名；门禁只认签名报告。

7. **反作弊**：
   - 生成方看不到隐藏测试；
   - optimize 阶段不允许直接改测试；改测试必须走 review；
   - 对「测试全过但覆盖率为 0」「用例数骤降」「断言数为 0」直接判失败；
   - 定期人工抽检 false pass，记录在基准报告里。

> 关键判断：**LLM-as-judge 可以作为补充，不能作为唯一验收权威。** 生产门禁必须有至少一个独立于生成模型的确定性证据源。

### 3.3 P0-3：没有持久化执行，租约与幂等也不成立

#### 事实

- `mas/leader.py:478-596` 的主循环把 `iterations`、`rollback_counts`、`steps` 全部放在内存；只有结束时 `mas/leader.py:689` 才写 `run_summary.json`。中途没有节点级检查点。`events.jsonl` 虽然持续追加，但代码里没有「从事件重建 RunState / 幂等重放副作用」的恢复器，所以事件日志目前只用于复盘，不用于恢复。
- `mas/worker.py:281-285` 在消息重投时直接 `Leader(config).run(...)` **从头开始**；`_archive_partial_run()`（`mas/worker.py:289`）只是把上次半截目录移到 `run_attempts/`，不是恢复。
- `mas/mq.py:566-572` 用 `visibility_timeout_ms` 作为 `XAUTOCLAIM` 的 `min_idle_ms`；`config/system.yaml:211` 默认 600,000ms（10 分钟）。而实测运行中位数 27.4 分钟、p90 115.8 分钟、最长 4 小时 12 分。**只要有两个 worker，运行到第 10 分钟就可能被另一个 worker 认领并重复执行。**
- `mas/worker.py:161` 和 `mas/worker.py:196` 只在空闲/开始时心跳；真正执行期间没有周期心跳。`mas/runhub.py` 的 Redis 运行键 TTL 默认 90s（`config/system.yaml:198`），`mas/leader.py:494` 只在节点边界续期。一次 LLM 调用超时配置就是 600s（`config/system.yaml:43`），节点执行很容易超过 90s。键过期后，`mas/store/redis_backend.py:364-369` 的 `request_cancel()` 直接返回 `False`（面板报 404），跨进程取消失效。
- `mas/worker.py:185-191` 的「幂等」只检查 `run_summary.json` 是否存在；运行中的任务没有 summary，所以重复消息会通过检查并启动第二次执行。
- `mas/store/redis_backend.py:424` 有 `acquire_lock/release_lock`，但全仓库没有调用者（`grep` 只命中定义处）。也就是说，**分布式锁能力存在，但没有用在运行互斥上**。
- MySQL 是索引/投影层（`mas/leader.py:692` 注释明确 SSOT 仍是 `run_summary.json` / `metrics.jsonl`），不是事务性运行状态；本地磁盘一丢，索引也补不回来。

#### 为什么是生产 blocker

生产环境一定会发生：部署滚动重启、Pod 被驱逐、Redis 主从切换、网络分区、重复投递、用户点两次。当前系统的行为是：

- 重启 → 从头再来，本轮已花的 token（样本 17 万–44.7 万）全部作废；
- 重复投递 → 两个 worker 同时写同一个 `workspace/runs/<id>`，产物互相覆盖；
- 节点中途 Key/TTL 过期 → 取消 404，用户以为停了，实际还在烧钱；
- 长运行 + 10 分钟 visibility → 在多 worker 场景下，重复执行是结构性风险，不是边缘情况。

**没有幂等和租约的 at-least-once，等于 at-least-twice。**

#### 最小改造

1. **持久化 RunState**：
   - 每节点结束后写 `checkpoints/<seq>-<node>.json`，至少包含：
     - `run_id`、`node_id`、`iteration`、`steps`、`rollback_counts`；
     - 黑板产物名 + 版本号 + hash；
     - `node_input_hash`、`budget_used`、`started_at`/`finished_at`；
   - 恢复时校验 hash，从最后一个完整检查点继续；
   - 产物与事件同时写对象存储（S3/MinIO），本地盘只作缓存。

2. **幂等键**：
   - `run_id + node_id + iteration + node_input_hash`；
   - 节点副作用（写文件、发消息、建 PR）都以该键去重；
   - 重复执行同一节点时，若已有完整结果则直接复用，而不是重跑 LLM。

3. **租约而非 visibility 猜测**：
   - worker 取到任务后获取 `run:<id>` 分布式锁（TTL 30–60s），后台线程每 15–20s 续租；
   - 锁带 fencing token，写入产物时校验 token，过期 worker 的写入被拒绝；
   - `visibility_timeout_ms` 必须显著大于租约 TTL（例如 3 倍），或干脆不用 XAUTOCLAIM 处理在跑任务，只看锁；
   - 锁丢失 → 当前 worker 立即停止，不能继续写。

4. **取消独立于运行键**：
   - `request_cancel()` 即使运行键不存在也写入 `run:<id>:cancel`（或单独 cancel key），不要用「键不存在」判断「不能取消」；
   - 在 LLM 流式回调、工具调用、沙箱执行之间轮询取消；不要只在节点边界；
   - worker 执行期间保持独立心跳线程。

5. **部署形态**：
   - API 与 worker 分开；生产不要在 Web 进程里内嵌 worker；
   - 单 run 并发度 1，多 worker 靠锁互斥；
   - 用成熟 durable workflow（Temporal/Restate）替代自研循环是合理选择；如果坚持自研，至少把上面的检查点/租约/幂等做完整。

6. **MySQL 投影**：
   - 用 outbox/CDC 或「先写事件再异步投影」，不要双写后静默失败；
   - 运行状态以 Postgres/Redis+对象存储为准，MySQL 只用于查询。

> 验收方式：在任意节点 `kill -9` worker，重启后必须从最近检查点继续；同时投递同一条消息 3 次，只能产生一次执行；取消请求在 60 秒内生效。

### 3.4 P0-4：没有身份、租户与密钥边界

#### 事实

- `frontend/server.py:284` 的 `GET /api/llm` 返回 `"api_key": api_key`（完整 Key），同时还有 masked 字段。注释写的是「本地面板回显，便于修改/切换其他 Key」——这是本地工具的假设，不是生产假设。
- `frontend/server.py:776` 对所有响应加 `Access-Control-Allow-Origin: *`；`do_GET/do_POST` 没有任何认证、会话、CSRF、权限检查。
- `POST /api/run` 接受 `requirement_path`，`mas/config.py:771-781` 的 `load_requirement()` 对绝对路径直接 `read_text()`。也就是说，任何能访问面板的人都能让系统读取宿主上的任意文本文件，并把内容送进 LLM prompt / trace。
- `images` 路径同样由请求传入，没有限制在 `workspace/uploads/` 内。
- 全局只有一个 `workspace`、一份 `config/credentials.yaml`、一个经验库；没有 tenant/user 维度。并发运行共享经验、技能、报告目录。
- 凭据明文落在 `credentials.yaml`；Redis 客户端支持 AUTH 但没有 TLS 配置；prompt/trace 落盘，没有脱敏、保留期、删除接口。
- `README.md:87` 直接建议 `--host 0.0.0.0` 开放局域网访问，但没有提示「面板无认证，等于把代码执行权交给局域网」。

#### 为什么是生产 blocker

这个面板不是「查看报表的 UI」，而是「发起一条会执行模型生成代码的流水线」的控制台。无认证 + 任意文件读 + 宿主机执行，三者组合起来就是一个**高权限的代码执行/数据外泄面**；能否稳定触发取决于模型是否被诱导，但安全不能寄托在这上面。即使只在内网，也违反最小权限；一旦端口被映射、被反向代理、被同事误开，风险立即变成现实。

此外，单 workspace 意味着两个用户/两个团队无法隔离：A 的运行能读 B 的需求、代码、报告；经验库的「学习」也会跨用户污染。

#### 最小改造

1. **认证与授权**：
   - OIDC/SSO 或至少 session + 密码哈希；生产不要用「无认证 + localhost」作为唯一防线；
   - RBAC：viewer / operator / admin；发起运行、改模型配置、改技能开关、读 Key 分开授权；
   - 所有写操作加 CSRF token；CORS 改为明确 allowlist。

2. **租户隔离**：
   - `tenant_id` 进入 run、queue message、workspace 路径、artifact key、experience 命名空间；
   - 每个租户独立 workspace/对象存储前缀/配额；
   - 查询接口强制按 tenant 过滤，禁止跨租户 `run_id` 访问。

3. **路径与上传**：
   - `requirement_path` 只允许 `workspace/uploads/<tenant>/` 下的文件；
   - `images` 同样限制；上传做扩展名、MIME、大小、数量校验；
   - 禁止绝对路径、`..`、符号链接；resolve 后再校验前缀。

4. **密钥**：
   - Key 写入后只返回 masked；`GET /api/llm` 永不返回完整 Key；
   - 用 Vault/KMS/云 Secret Manager，或至少加密存储 + 进程内解密；
   - Key 不进入 prompt、events、traces、报告、Redis payload；
   - 支持轮换；审计「谁在何时改了 Key」。

5. **网络**：
   - 默认只 bind `127.0.0.1`；需要远程访问时放在 TLS 反向代理 + SSO 后面；
   - 面板与 worker/executor 分网；executor 无出网；
   - 管理端点（`/api/llm`、`/api/store/status`、`/api/mq/status`）单独限权。

6. **数据治理**：
   - prompt/trace 脱敏（邮箱、手机号、Key、路径）；
   - 保留期与删除接口；
   - 明确「需求文本会发送给第三方模型」的告知与租户级开关；
   - 经验库跨租户禁用，或经人工审核后全局提升。

> 快速止血（1–2 天）：去掉 Key 回显、CORS 改 allowlist、`requirement_path`/images 限制在 uploads、面板默认只 bind localhost、README 删除无认证的 `0.0.0.0` 建议。这些不能替代上面的完整改造，但能立刻降低风险。

## 4. P1：能跑之后，决定「能不能长期跑」的缺口

### 4.1 预算、成本与模型网关

**事实**：

- `mas/llm.py:108` 只有单次 `max_tokens`（默认 3000，`system.yaml` 配 64000）和单次 timeout；没有 run 级 `max_total_tokens`、`max_cost`、`max_wall_time`。
- 实测单次运行 17 万–44.7 万 tokens；上下文压缩（`mas/context.py`）只控制单次请求，不控制整条流水线的累计花费。
- 只有一个 provider/endpoint；`_post_with_retry()` 只对同一端点重试；端点挂了不会切模型。
- 没有租户/用户配额、并发上限、速率限制；多个运行可以同时打满端点。

**改造**：

- 新增 `mas/budget.py`：`RunBudget(max_total_tokens, max_cost, max_wall_s, max_per_node_tokens)`；每次 LLM/tool 调用前扣减，超限发 `budget_exceeded` 并终止；`run_summary` 输出实际用量与估算成本。
- 模型网关：provider 列表、优先级、熔断、指数退避 + jitter、429/5xx 分类、按租户限流；记录每次调用的 model/latency/tokens/cost。
- 定价表按模型维护；成本按 run/tenant/day 聚合；设置硬上限与告警。
- 对长任务设置 wall-clock deadline；到点先尝试收尾（写报告），再强制取消。

### 4.2 可观测性与运维

**已有**：`events.jsonl`、`llm_traces.jsonl`、`prompts/`、`metrics.jsonl`、`timeline.md`、`run_summary.json`，对单次复盘非常好。

**缺口**：

- 没有 OpenTelemetry span，无法把 API → queue → worker → LLM → sandbox → verifier 串成一条 trace；
- 没有 Prometheus 指标（runs_total、duration、tokens/cost、queue depth、PEL、DLQ、worker heartbeat、sandbox failures）；
- 没有告警（运行卡住、DLQ>0、p95 超阈值、pass 率骤降、成本异常）；
- 没有日志脱敏与保留策略；
- 没有 SLO/on-call/runbook。

**改造**：

- `mas/telemetry.py`：OTel tracer/meter，`run_id`/`node_id`/`tenant_id` 作为属性；
- `/metrics` 暴露核心指标；Grafana 看板；
- 告警规则与值班手册；
- 结构化日志 + 脱敏；
- 健康检查 `/healthz`、`/readyz`；启动时校验依赖（Redis/MySQL/容器运行时）。

### 4.3 CI/CD 与部署

**事实**：仓库没有应用 `Dockerfile`、没有 `.github/` CI、没有 `pyproject.toml`；`mas/store/schema.sql` 用 `CREATE TABLE IF NOT EXISTS` 建表，但没有版本化迁移/回滚；`requirements.txt` 只有 `PyYAML>=6.0`，未锁版本；`deploy/` 只有 MySQL/Redis 的 compose。`tests/` 的 Redis/MySQL 集成测试在依赖缺失时会 skip（`tests/test_store_integration.py:90` 等），意味着 CI 不装服务就永远不会覆盖 MQ/store 路径。

**改造**：

- 应用/worker/executor 三个镜像；多阶段构建、非 root、固定 digest；
- CI：ruff + mypy（或 pyright）+ unittest + 集成测试（compose 起 Redis/MySQL）+ 镜像扫描 + SBOM；
- 迁移：Alembic 或自研版本表；启动时 `migrate` 而不是隐式建表；
- 部署：compose（单机）/ K8s（生产）；readiness/liveness；PDB；资源 requests/limits；
- 发布：灰度/蓝绿、回滚、数据库备份与恢复演练；
- 依赖锁定（uv/poetry/pip-tools），定期升级与漏洞扫描。

### 4.4 评测体系：没有基准，就没有「变好」

**事实**：

- 48 次运行是探索性任务，不是冻结基准；任务、需求、模型版本都在变；
- 测试由模型生成，没有隐藏测试；无法区分「真的变好」和「测试变松」；
- 没有 pass@1、false pass rate、cost per accepted task、p95 latency 的正式统计；
- 改动 prompt/模型/技能后，没有回归门禁。

**改造**：

- 建 30–50 题冻结基准，覆盖：backend_only、full_stack_ssr、full_stack_spa、不同语言、含歧义需求、含对抗需求；
- 每题配隐藏验收测试（不进入生成方上下文）和人工评分 rubric；
- 指标：pass@1、false pass rate（人工抽检）、verifier catch rate、mutation score、cost per accepted、p50/p95 duration、rollback rate、人工接受率；
- 夜间跑基准，和基线比；回归超过阈值（如 pass@1 -2pp 或成本 +20%）阻止合并；
- 版本化模型、prompt、技能、流程配置，保证可复现；
- 定期做「红队需求」：提示注入、越权、虚假证据、测试削弱。

### 4.5 交付集成与人工闸门

**事实**：`mas/leader.py:210` 明确「全流程无人工干预」；产物落在 `workspace/runs/<id>/`，没有 Git 分支、commit、PR、CI 状态、人工 approve。对「代码交付」这个产品形态，这等于把最后一百米留给了人工手工搬运。

**改造**：

- 每个 run 对应一个 Git 分支/工作树；产物提交为 commit；
- 自动开 PR，附验收报告、测试证据、覆盖率、风险摘要；
- 接 CI（lint/test/build/security），PR 上展示状态；
- 人工 reviewer approve 后才能合并；生产部署再加变更审批；
- 支持回滚（revert PR）与审计（谁批准、哪次 run、哪版模型）；
- 与 Issue/Jira 关联，需求来源可追溯。

**原则**：Agent 可以提议合并，但不能无人批准直接合入主干。

### 4.6 多语言与能力边界

**事实**：`mas/agents/tester.py:20` 的 `_EXECUTABLE_LANGUAGE = "python"`；沙箱白名单可含 node；非 Python 选型会通过 `_verification_gap()` 判失败（这是诚实的，不是 bug）。C++ 任务在 probe 中被强制 fail。

**建议**：

- 明确支持矩阵：Python 后端、JS/TS SSR、SPA（浏览器证据）、其他语言「暂不支持」；
- 若要做 C++/Go/Java，给每种语言提供编译+测试镜像、覆盖率工具、verifier 适配器；否则不要在市场材料里写「多语言」；
- 对不支持的语言 fail closed，保持现在的诚实行为。

### 4.7 技能/MCP/ReAct 的真实状态

避免把「代码存在」当成「能力已上线」：

- `config/system.yaml:47` `tools_enabled: false`；`config/mcp.yaml:9` `servers: []`；`config/system.yaml:126` 技能工具 `tools_enabled: false`；
- `runtime.react.enabled: true`（`config/system.yaml:170`），但 `_generate_with_react()` 在无工具时直接退化为单轮 `generate`（`mas/agents/base.py:337-340`）；
- 因此默认配置下，ReAct/function calling 实际是**惰性能力**，不能作为生产卖点；
- 技能文本注入可能改变模型行为，但没有基准证明其稳定收益，且技能内容会进入 prompt，存在供应链/提示注入风险；
- 生产建议：技能包签名 + 版本锁定 + 租户白名单 + 审计；工具调用必须有权限、超时、预算、沙箱和人工可审批的高危动作。

### 4.8 Agent 能力层：固定流程是优点，但契约与评测仍是缺口

这一节回答「Agent 本身离生产级还有多远」，避免只谈基础设施。

| 能力维度 | 当前实现 | 生产判断 |
|---|---|---|
| 规划 | 8 节点固定图；节点内由 LLM 产出结构化 JSON；没有动态增删节点/重规划 | 对「代码交付」是**优点**（可审计、可预算）；对「开放任务」是能力边界，不应宣传为通用 Agent |
| 工具使用 | function calling / ReAct 代码存在，但 `tools_enabled=false`、MCP 为空、技能工具关闭；无工具时退化为单轮生成 | 默认配置下 Agent **不能真正操作环境**；开启前必须先有权限、超时、预算、沙箱、审计 |
| 消息契约 | 角色间靠黑板产物 + 消息摘要；`contracts` 只拼进 prompt；`mas/schemas.py` 只有 dataclass，没有运行时 JSON Schema 校验 | 生产需要 Pydantic/JSON Schema 校验、契约版本化、畸形产物拒收；否则一个字段类型错误会穿透到门禁 |
| 记忆/经验 | JSONL + bigram 检索 + 自动 `promote()`；跨 run 共享 | 有检索、无因果验证；存在经验投毒、跨租户污染、过拟合历史任务；需要 provenance、隔离、人工/自动审核、A/B |
| 反思 | reviewer 的 LLM 审查 + AST 规则 | LLM 反思不能替代独立验证；AST 规则覆盖有限且可绕过 |
| 协作 | Leader 串行调度；tester→developer 协商最多 6 轮；无并发 Agent | 串行可控，但长尾时延高（p90 近 2 小时）；并发需要锁、配额、冲突解决 |
| 轨迹评测 | 有事件、prompt、token trace | 缺 trajectory 级指标：工具成功率、无效轮次、上下文浪费、人工接管率 |
| 内容信任 | 需求、技能、历史经验都直接进入 prompt | 需要内容信任级别（用户输入/技能/经验/模型输出）、来源标记、提示注入检测、工具权限与人工审批 |

**结论**：如果产品定位是「代码交付流水线」，固定流程 + 强验证是正确的取舍，不需要为了「多 Agent」而引入动态规划；如果定位是「通用 Agent 平台」，那么规划、工具、契约、记忆治理、轨迹评测都还处于原型阶段，不能与前者混为一谈。

## 5. 目标架构：控制面 / 数据面 / 交付面分离

当前是「一个 Python 进程 + 本地文件系统 + 可选 Redis/MySQL」；生产建议拆成三层，信任边界清晰：

```
┌────────────────────────────────────────────────────────────────────┐
│ 控制面 Control Plane                                               │
│  Console/API → AuthN/RBAC/Tenant → Run API → Durable Workflow      │
│                                      ↓                             │
│                               Queue + Lease + Budget/Quota         │
└───────────────────────────────┬────────────────────────────────────┘
                                │ signed task (tenant, run, budget)
┌───────────────────────────────▼────────────────────────────────────┐
│ 数据面 Data Plane                                                  │
│  Worker Pool → LLM Gateway → Model Providers                       │
│       │                                                            │
│       ├→ Sandbox Executor (container/microVM, no network, no creds)│
│       ├→ Verifier (frozen/hidden tests, coverage, SAST, signature) │
│       └→ Artifact Store (S3/MinIO, hash, retention)                │
└───────────────────────────────┬────────────────────────────────────┘
                                │ signed evidence
┌───────────────────────────────▼────────────────────────────────────┐
│ 交付面 Delivery Plane                                              │
│  Git branch/commit → PR → CI → Human approval → Merge/Deploy       │
│  Audit log / SLO / Cost / Incident runbook                         │
└────────────────────────────────────────────────────────────────────┘
```

**六条信任边界**：

1. 用户/租户 → API：认证、授权、配额、输入校验。
2. API → worker：任务签名，携带 tenant/run/budget，worker 不信任 payload 里的任意路径。
3. worker → executor：不可信代码，无凭据、无网络、无宿主挂载、资源受限。
4. worker → LLM：数据最小化、脱敏、provider 策略、预算。
5. verifier → gate：独立证据、签名、隐藏测试；生成方不能改。
6. gate → VCS：人工批准，Agent 不自动合并主干。

**买 vs 自建**：

| 能力 | 建议 |
|---|---|
| 持久化工作流 | Temporal / Restate / 云队列 + 状态机；不建议继续扩自研循环 |
| 沙箱 | Docker 起步；高风险用 gVisor/Firecracker/托管沙箱（E2B 等） |
| 认证 | Keycloak/Auth0/云 IAM，不要自研密码体系 |
| 密钥 | Vault/KMS/云 Secret Manager |
| 可观测性 | OpenTelemetry + Prometheus/Grafana + 云日志 |
| 对象存储 | S3/MinIO，产物/事件/报告统一 |
| 队列 | Redis Streams 可用，但必须补租约/幂等；规模大时 SQS/Kafka |

## 6. 分阶段路线图

> 假设：2–3 名工程师（1 后端/平台、1 Agent/评测、1 前端/DevOps 兼职），已有代码基础。时间是工程量级估算，不是承诺。

### 阶段 0：止血（第 1 周）

目标：先把「最容易被利用」和「最容易丢工作」的口子堵上，不动架构。

- 面板默认只 bind `127.0.0.1`；README 删除无认证的 `0.0.0.0` 建议；
- `GET /api/llm` 去掉完整 Key；CORS 改 allowlist；
- `requirement_path`/`images` 限制在 `workspace/uploads/`；
- 生产配置禁用 Web 进程内嵌 worker；
- 写红队用例，记录当前失败（作为基线）；
- 测试文件 hash 清单，门禁检测 hash 漂移（先只告警，下一阶段转阻断）。

**完成判据**：局域网无法直接访问面板；API 不返回 Key；任意路径读取被拒绝。

### 阶段 1：可信执行 + 独立验证（第 2–6 周）

目标：让「跑模型生成的代码」这件事在安全边界内发生，让「通过」有独立证据。

- Executor 抽象 + Docker 沙箱（无网络、非 root、只读根、资源上限、进程树清理）；
- 生产 fail closed；本地开发模式显式标注；
- TestAuthor/TestVerifier 分离；测试冻结 + 隐藏测试；
- 真实覆盖率 + 变异测试（Python 先行）；
- 框架重算 `blocking`；门禁读 verifier 签名报告；
- 红队用例全绿；假通过基准（历史 task04）验证。

**完成判据**：红队无法读宿主/外连/越界/炸资源；测试被篡改会失败；历史假通过案例被独立 verifier 挡住。

### 阶段 2：持久化、租约、取消（第 5–9 周，可与阶段 1 并行）

目标：任何进程在任何时刻死掉，都不丢已完成的工作、不重复执行。

- RunState/检查点；从最近检查点恢复；
- 幂等键 + 原子产物写；
- 运行锁 + 租约续期 + fencing token；
- visibility 与租约匹配；重复投递测试；
- 取消键独立 + 流式轮询；worker 周期心跳；
- API/worker 分离；对象存储。

**完成判据**：随机 kill worker 20 次，全部恢复；3 个 worker 抢同一任务只执行一次；取消 p95 < 60s。

### 阶段 3：身份、预算、运维（第 7–11 周）

目标：能交给团队用，而不是只能作者本机跑。

- OIDC/RBAC/租户；路径/上传/密钥治理；
- 运行级 token/成本/时限预算；模型网关/限流/回退；
- OTel + Prometheus + 告警 + SLO；
- 应用/worker/executor 镜像；CI/CD；迁移；健康检查；备份/回滚；
- 日志脱敏与保留策略。

**完成判据**：无 Key 泄露；跨租户访问被拒；超预算自动停止；有看板/告警/回滚手册；一条命令部署。

### 阶段 4：评测与交付闭环（第 9–12 周）

目标：能证明「变好了」，并能把产物真正交付出去。

- 30–50 题冻结基准 + 隐藏测试 + 人工抽检；
- 夜间回归 + 发布门禁（pass@1、false pass、成本、p95）；
- Git 分支/commit/PR/CI；人工 approve 后合并；
- 复盘模板：失败分类、根因、修复、回归证据；
- 安全评审 + 故障演练（Redis 挂、worker 驱逐、端点 429/504、磁盘满）。

**完成判据**：基准报告可重复；PR 流程跑通；发布有门禁；演练有记录。

### 阶段 5（可选）：多租户 SaaS（3–6 个月）

- 租户隔离、计费、配额、审计、数据删除；
- 多区域/HA、队列与存储的容灾；
- 合规（SOC2/等保等按市场）；
- 自助式技能/模型市场与供应链签名；
- 独立安全评估与渗透测试。

## 8. 明确不要做的事

1. **不要用「再加几个 Agent/技能」作为生产化路线。** 当前瓶颈是信任边界、验证权威、持久化和身份，不是角色数量。更多角色只会增加调用次数、成本和攻击面。
2. **不要让 LLM 自报覆盖率/阻塞数/验收结论。** 可以作为线索，不能作为门禁的唯一输入。
3. **不要把面板暴露到局域网/公网。** 在加上认证、授权、路径限制之前，它就是一个代码执行控制台。
4. **不要用 MySQL 双写当 SSOT。** 当前 `run_summary.json`/`metrics.jsonl` 才是主记录；双写失败静默会导致索引与事实不一致。生产用 outbox/CDC 或对象存储 + 索引重建。
5. **不要在生产用 `subprocess` 沙箱跑不可信代码。** 命令白名单不是安全边界，AST 检测也不是。
6. **不要把 `runtime.react.enabled: true` 当成 ReAct 已生效。** 默认没有工具，循环会退化为单轮生成；能力声明要以配置和实测为准。
7. **不要在没有 per-language verifier 时宣称多语言。** 当前只真正验证 Python；其他语言 fail closed 是正确行为。
8. **不要自动合并主干。** Agent 可以开 PR、跑 CI、写报告；合并必须是人的决定。

## 9. 最终判断与建议定位

### 9.1 当前最准确的定位

> **一个可审计、可配置、能真实执行测试的代码交付流水线原型；在可信单用户、本机环境、人工盯守的前提下，可以完成一部分中小型任务；不具备生产级的安全性、验证可信度、故障恢复和多用户能力。**

它不是「玩具」：457 个框架测试、事件溯源、真实执行、上下文治理、MQ/存储接入，都说明作者理解系统工程。它也不是「生产级」：四个 P0 缺口任意一个都足以让生产事故变成数据泄露或错误交付。

### 9.2 建议的产品定位

优先做 **A：内部可信代码交付流水线**。

- 固定角色、固定流程、强验证、产出 PR；
- 服务对象是「一个团队的可信需求」，不是公开多租户；
- 卖点是「可审计、证据完整、能接 PR」，不是「全自主 Agent」；
- 这与现有优势（确定性状态机、事件链、真实执行）一致，改造量最小。

谨慎做 **B：通用多 Agent 平台**。

- 需要工具生态、沙箱、记忆、权限、市场、计费、多租户、HA；
- 当前代码只是起点，不是 3 个月能补齐的；
- 在没有 A 的验证与隔离能力之前做 B，只会把风险放大。

### 9.3 如果只做三件事

按投入产出排序：

1. **把生成代码关进容器（无网络、非 root、资源限制），并让生产环境 fail closed。** 这是唯一能防止「一条需求读走宿主凭据」的措施。
2. **把测试冻结、把验证独立、把覆盖率换成真实工具，框架重算 blocking。** 这是唯一能让「通过」有意义的方法。
3. **加运行级租约/检查点/幂等，并把面板加上认证与路径限制。** 这是唯一能让系统在重启、重复投递和多人使用下不崩、不泄露的方法。

这三件事做完，系统才配谈「生产级 Agent」；在此之前，更多的 Agent 角色和技能只是把 demo 做得更热闹。

> 落地状态（2026-10-22）：上述四项已完成最小代码实现并通过回归，详见
> [docs/38 生产级 P0 加固落地记录](38-生产级P0加固落地记录（2026-10-22）.md)。
> 注意：容器后端仍是可选配置（默认 `local`），面板是单令牌而非多租户身份体系，
> 检查点是节点粒度至少一次；「已实现」不等于「已达到生产就绪」。
