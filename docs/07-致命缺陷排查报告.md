## P0-1　验收门禁：签署 Agent 失败被静默降级为"通过"

**问题描述**
门禁节点（`acceptance`）会让 reviewer Agent 出一次"验收签署意见"。若这次调用失败（网络异常、返回不可解析内容、超时），Leader **完全不检查它的执行状态**，直接按"无人反对"处理，门禁判定为通过，整条流水线输出"验收通过"。

**判定依据** — `mas/leader.py:396-415`，`Leader._run_gate`：

```python
396        signoff: Dict[str, Any] = {}
397        if node.role and node.role in agents:
398            signoff_result = agents[node.role].act(task)          # ← 从不检查 .status
399            self._track_experience(ctx, signoff_result)
400            signoff = signoff_result.artifacts.get("acceptance_opinion") or {}   # 失败时 = {}
...
415        passed = all_pass and str(signoff.get("verdict", "pass")) != "reject"   # ← 缺省 "pass"
416        failed = [item for item in criteria_results if not item["passed"]]
```

成因链条：
1. `BaseAgent.act`（`mas/agents/base.py:77-84`）把所有异常吞掉转成 `result.status="fail"`，此时 `result.artifacts` 为空；
2. `_run_gate` 只读 `artifacts`，不读 `status`；
3. 第 415 行的 `signoff.get("verdict", "pass")` 把"没有签署意见"默认成 **pass**。

**触发条件**：任何导致 acceptance 签署 LLM 调用失败的原因——网络错误、读超时（见 P1-4）、模型返回非 JSON、权限/配置问题。

**实证**（`probe_gate.py`，端到端跑通后注入 `acceptance_signoff` 异常）：

```
[node_error]    agent=reviewer node=acceptance payload={'error': 'RuntimeError: 模拟：验收签署调用 LLM 失败（网络异常）'}
[gate_evaluated] agent=leader node=acceptance payload={'passed': True, 'failed_criteria': [],
                                                        'signoff': {'verdict': '', 'opinion': ''}}
verdict = pass | steps = 11 | forced_fail = False
```

**影响范围**
系统唯一一处"人工/模型否决验收"的闸门失效，产生**假阳性通过**结论：报告写"验收通过"、CLI 退出码 0、`run_summary.verdict=pass`。这是最危险的失效模式——出错时系统表现得比正常时更乐观。

**修复方向**
判定 `passed` 前先校验 `signoff_result.status`；签署失败应视为门禁不通过（或至少记为 `forced_fail=True` / `verdict=unknown` 并强制走 fail 分支），并把"签署缺失"写进 `failed_criteria` 让报告可追溯。

## P0-2　经验库读-改-写无锁 + 陈旧快照 → 并发运行互相覆盖，可致整库清零

**问题描述**
经验库用 `load → merge → save` 全文件重写模式持久化。`save()` 在锁内，但 **`load()` 在多条路径上完全不加锁**，且 `add()` 在已加载过时**跳过重载**，仍用内存里的旧快照整文件覆盖磁盘。并发运行下会丢数据；在 `save()` 的截断窗口内读取则会把整个库清掉。

**判定依据** — `mas/experience.py`：

```python
221    def save(self) -> None:                       # 整文件重写
223        with self.path.open("w", encoding="utf-8") as handle:     # ← "w" 先截断
224            for entry in self._entries:
225                handle.write(...)

234    def add(self, entries, *, source_run="") -> ...:
240        with self._locked():
241            self.load() if not self._loaded else None    # ← 已加载则跳过重载，写的是陈旧快照
...
286            self.save()

290    def retrieve(...) -> ...:
301        self.load() if not self._loaded else None       # ← 锁外读取
```

锁外读取还发生在 `entries` 属性（:227-231）、`stats()`（:670）、`reinforce()`（:449）、`promote()`（:466）、`prune()`（:694）的 `load()` 调用上。

**触发条件**：两个及以上运行共享同一 workspace。前端 `frontend/server.py:301-341` 的 `start_run` 对每次 `POST /api/run` 无并发限制地起后台线程，共享同一 `workspace/knowledge/experience.jsonl`——这是默认可达路径。

**实证**（`probe_conc.py`）：

```
B 写入后，磁盘条目 = ['B 学到的经验']
A 写入后，磁盘条目 = ['A 学到的经验']
>>> B 的经验是否丢失 = True

截断窗口内 load() 读到条目数 = 0 （_loaded= True ）
D 之后再读磁盘 = ['D 的经验']        # 原有的 'A 学到的经验' 被整文件覆盖抹掉
```

**影响范围**
跨运行的自学习资产静默丢失；严重时整个 `experience.jsonl` 被覆盖为单条。文件锁本身是有效的（实测同进程多线程互斥正常，`probe_lock.py`），问题出在"读不在锁内"和"复用陈旧快照"，锁并不能阻止这两类丢失。

**修复方向**
`retrieve/stats/entries/reinforce/promote/prune` 的 `load()` 也纳入 `self._locked()`；`save()` 改"写临时文件 + `os.replace` 原子替换"；`add()` 在锁内**强制** `load()`（去掉 `if not self._loaded` 短路）。

## P1-4　读响应超时不被重试逻辑覆盖，`llm.retry` 对其完全无效

**问题描述**
`_post_with_retry` 只捕获 `HTTPError` 与 `URLError`。而 `urlopen` 在"等待响应头 / 读 body"阶段的超时抛的是 `TimeoutError`（`OSError` 子类，**不是** `URLError`），会直接逃出重试逻辑。

**判定依据** — `mas/llm.py:195-213`：

```python
195    def _post_with_retry(self, request):
199        for attempt in range(1, attempts + 1):
200            try:
201                with urllib.request.urlopen(request, timeout=self.timeout) as response:
202                    return json.loads(response.read().decode("utf-8"))   # ← response.read() 超时同样逃逸
203            except urllib.error.HTTPError as exc:
...
207            except urllib.error.URLError as exc:
208                last_error = f"LLM 网络异常: {exc}"
209                retryable = True
210            if not retryable or attempt == attempts:
211                raise AgentError(last_error)
```

**实证**（`probe_timeout.py`，服务端 5s 不发响应，客户端 `timeout=1`）：

```
捕获到其它异常 -> TimeoutError | 是 URLError 子类: False | 是 OSError 子类: True
```

**影响范围**
`config/system.yaml:32` 注释写明该端点实测单次响应 150~200s、`timeout: 600`；一次读超时即可让节点判 fail → 回退 → 升级 → 整轮 fail。更关键的是：**把 `llm.retry.max_attempts` 调大也不会重试这类错误**，运维手段失效。`config/system.yaml:41` 当前 `max_attempts: 1`（默认不重试），所以任何网络抖动都直接落到节点失败。

**修复方向**
增加 `except (TimeoutError, OSError) as exc:` 并置 `retryable = True`（或统一 `except Exception` 后按类型分类）；同时给 `response.read()` 单独加保护。

## P1-5　自学习闭环在"运行末尾提炼"路径上永久失效 + 经验条目无限膨胀

- `config/learning.yaml:62`：`L1_to_L2: 1`（要求 `hits >= 1`）。

## P1-7　歧义协商把"轮数"当"条数"用，≥3 条歧义时测试节点恒定失败、验收门禁恒定不满足

```python
210            "closed": closed,
211            "open": len(questions) - closed,          # ← 未协商的问题全部计入 open
212            "status": "closed" if closed >= len(questions) else "open",
```

配合 `tester.py:139` `result.status = "pass" if summary["failed"] == 0 and negotiation["open"] == 0 else "fail"`、`config/collaboration.yaml:33` `max_rounds: 2`、`config/flow.yaml:98` 门禁项 `test_report.negotiation.open == 0`。

**影响范围**

**修复方向**
新增独立配置 `negotiation.max_questions` 限制条数，`max_rounds` 只用于单条问题的多轮追问；或默认对全部问题逐条协商。

## P2-8　MCP 客户端子进程泄漏

**判定依据** — `mas/toolrunner.py:49-68`：`client.start()` / `initialize()` 成功后，只有在 `list_tools()` 返回**至少一个**工具时才把 client 登记进 `self._clients`（:58）。若工具列表为空，或在 `list_tools()` 处抛 `ConfigError`（:67-68 直接 `continue`），该 client 从未登记，`close()`（:120-126 只遍历 `self._clients`）也就回收不到它。

```python
49            try:
50                client = MCPClient(server)
51                client.start()            # ← stdio 子进程已启动
52                client.initialize()
53                for tool in client.list_tools():
...
58                    self._clients[name] = client        # ← 只有拿到工具才登记
...
67            except ConfigError:
68                continue                  # ← 未 close，子进程泄漏
```

**影响范围**
`llm.tools_enabled=true` 且 MCP 服务异常/无工具时，每次运行泄漏一个 stdio 子进程。默认 `tools_enabled: false`，影响面有限。

**修复方向**
用 `try/finally` 或显式在异常分支与"无工具"分支调用 `client.close()`。

## 疑似风险（未构造出必然触发路径，标注为推测）

### S1　Blackboard `get()` 返回活引用，tester 原地修改上一轮缺陷状态

- **依据**：`mas/blackboard.py:132-140` 的 `get()` 直接 `return self._latest[name]`（返回本体，无深拷贝）；`mas/agents/tester.py:243-262`、`:289-292` 的 `_track_bugs` 对 `previous[...]` 取出的对象做 `prior.update({"status": "fixed", ...})` **原地修改**。
- **推测影响**：`_track_bugs` 执行后、`publish("bug_reports", ...)` 之前若抛异常（如 `write_text` 的 `OSError`），黑板缓存里的 `bug_reports` 已被改成 `status=fixed`，而磁盘仍是 v1（open）。随后 `acceptance` 门禁读 `bug_reports.open == 0`（`config/flow.yaml:94`）会读到被改过的缓存 → 可能误判通过。
- **不确定性**：需要"变异之后、发布之前"恰好抛异常才会改变最终结论；未构造出必然触发路径，故只列为疑似。
- **修复方向**：`get()` 返回深拷贝；`_track_bugs` 用副本构造 `items`。

### S2　前端无并发运行上限

- **依据**：`frontend/server.py:301-341` 的 `start_run` 对每次 `POST /api/run` 起一个 daemon 线程，无运行数上限、无互斥。
- **推测影响**：直接放大 P0-2/P0-3。附带后果：`mas/sandbox.py:307-313` 的 `_spawn_kwargs` 在 `threading.active_count() > 1` 时**跳过 rlimit 注入**，因此前端路径下 POSIX 资源限制（CPU/内存/文件/进程数）完全不生效；Windows 本来就无 rlimit。
- **修复方向**：加运行队列或单例运行锁；或按 run 隔离 workspace 目录。
