六条贯穿本阶段的判断：

1. **门禁表达式正确 ≠ 门禁可信**。F11/F14 修的都是"门禁永远过不去"和"门禁虚假通过"两个方向相反的缺陷——前者是 `negotiation.open==0` 在 `max_rounds=2` 下数学上不可满足，后者是汇总计数只数应答条数、与问题项自带的 `status=open` 自相矛盾。
2. **"没跑成"与"全过了"必须可区分**。F19 来自 probe-02 iter02 的实录：测试文件崩溃导致 0 条用例回传，框架却判 test 节点通过、把 32 个缺陷自动闭环、并让门禁第 6 项被虚假满足。
3. **"测试全败"有两种根因，框架此前只会归为一种**。C++ 探针的 32 条失败全部是 `FileNotFoundError`（本机没有编译器），却被记成 32 个研发缺陷、回退预算烧光后失败终止。F16/F17 把它归到"环境/构建问题"，并给出证据。
4. **非 Python 交付物的度量此前在说谎**：manifest 报「2 个文件，0 行」、implement 报「导入自检失败」。F15 修正后同一位置报「387 行」与"导入自检不适用"。
5. **自学习的跨域污染已可观测但尚未解决**（§5），这是能力边界，不是本轮已修复项。
6. **最危险的一类假通过不是"0 用例被判过"，而是"换了个可验证的东西全过"**。probe-02 在 3 次回退压力下把 C++ 需求做成了 Python 复刻，测试套件测的是那份 Python，25 条用例全过、覆盖率 1.0×3、`bug_reports.open=0`，验收 Agent 还在签署意见里逐条引用了 `.hpp` 的封装修复——**门禁 8/8 全绿，但需求要求的交付物从未被验证**。F23 让测试节点在这种"选型语言 ≠ 沙箱可执行语言"的情况下直接报失败，把假通过变成真失败——**已在 `task04-cpp-probe-04` 上端到端证实**：该 run 最后一轮 `用例 18（通过 18 / 失败 0）、通过率 1.0、缺陷闭环 18/18`，仍判 `status=fail`，最终以 `verdict=fail / forced_fail=true` 结束（逐项核对见 §3.6）。

2. **依赖本机工具链的环境失败仍会被记成缺陷**：F17 是诊断层面的归因，门禁表达式仍按 `failed == 0` 判失败——框架不会"因为环境不具备而豁免"，这是有意保守（避免用豁免掩盖真实缺陷），但意味着换机器就要人工判断。
3. **单次生成体积上限**：实测约 4.5 万输出 token / 1100 行，超出即 length 截断；`docs/08` 的分批生成方案本期未实现。
4. **LLM 契约遵从不稳定**：类型防御、参考 runner、感知预算只能把违背概率压到"循环可收敛"，不能归零。
5. **确定性仅存在于 offline 模式**：真实 LLM 路径同需求两次运行产物不同，回归对比须靠门禁而非逐字节。
6. **经验库跨域污染**：`scope=global` 的 L3 条目会把 cron/电商/定价的教训一起注入 C++ 任务；F18 只细分了歧义类，缺陷守卫类仍合并（hits=146 这种数字不能再当作置信度证据）。
7. **长任务耗时，且延迟完全由外部 LLM 决定**：`duration_s` 实测 Python 通过任务 1813s / 3987s / 6950s / 7809s（30~130 分钟），C++ 探针最长 13797s（≈230 分钟）。第二阶段后半程本机同时跑两个 run 时，单节点耗时进一步恶化：`task04-cpp-probe-04` 的 implement 用了 **4105s（68 分钟）**（16:25:50→17:33:55），`task02-eshop-attempt04` 的 optimize 从 16:20:20 起、到本文 17:36 读取时**已 76 分钟仍未结束**（`prompts/optimize#1-developer-162020.md` 已写出、`llm_traces.jsonl` 无新条目=请求在飞、python 进程存活）。这不是框架卡死：`config/system.yaml` 的 `llm.timeout=600` 对流式响应是**单次读超时**，只要每 600s 内有增量就不算超时，而 `max_tokens=64000` 的单次生成（含 1.5 万量级 reasoning token）在本端点就是几十分钟级。结论：单节点 900~1400s 是常态上限，拥塞时会到 4000s+，绝对不适合交互式场景；要做并行/压测得先解决 API 排队。
8. **回退预算耗尽即失败终止**（`fail_run_and_report`）：不会自动放宽门禁或换策略，需要人工决定是放宽 profile 还是补环境。
9. **交付语言会在回退压力下漂移**（已确认发生，并被 F23 挡在验收之前）：C++ 需求的 probe-02 在第一次回退后新增 `code/smartptr.py`（209 行 Python 复刻）与 `code/tests/test_smartptr_acceptance.py`（262 行，零 subprocess），使 `python -c import smartptr` 自检从失败变通过，最终 25 条用例全过、8 项门禁全绿、`verdict=pass`——**而 `.hpp` 从未被编译**（详见 §3.3(b)）。这是"让可验证的口径满足"而非"满足需求"。F23 的处置是：选型语言不是 Python 时，测试节点一律判失败，因此这类 run 再也拿不到"验收通过"。
   残余风险（未修，仍是边界）：F23 比较的是"选型声明的语言"与"沙箱能执行的语言"，不是"交付物与需求是否一致"。它依赖 `solution_design.tech_choice.language` 这个由 LLM 写的字段——如果研发在方案阶段就把语言写成 Python（漂移得更早），或需求本身没有硬约束语言，框架就无从判断；"交付物形态/语言与需求文档一致"仍需要人工核对（要做成机器判定得新增门禁项，误判风险高，本轮按最小改动原则未做）。
10. **协商"闭环"只保证实质应答，不保证应答之间一致**（F14 的剩余风险，attempt03 实录）：同一份 `test_report.negotiation` 里 4 问全部 `status=resolved`，但内容互相矛盾——
    - Q-1（取消口径）的 resolution 裁定「先取消再退款：订单状态迁移至 CANCELLED，退款成功后生成退款记录」；Q-3 的 resolution 裁定「采用『退款即取消』的原子口径……**禁止**『先置 CANCELLED 再退款』的两阶段写法」；Q-4 的 resolution 又写「采用『先取消再退款』……退款失败不影响订单取消状态」。
    - Q-2（订单 id 生成）的 resolution 裁定「进程内单调自增整数，从 1 开始，不使用随机」；Q-3 裁定 `'ORD-{seq:06d}'` 自增带前导零；Q-4 的 resolution 却裁定「使用 `uuid.uuid4().hex`，保证全局唯一，非自增」。
    机制原因是 F14 采用**按请求顺序配对**（第 i 问 ↔ 第 i 条应答），而 LLM 常把多问合并进一条全局应答，于是每条 resolution 都顺带复述了别的问题的口径。框架校验的是"有没有实质回答"（`min_answer_chars`）与"配对是否错位"，不校验多条 resolution 之间的语义一致性——门禁第 8 项因此可以在**内容自相矛盾**的协商记录上判过（attempt03 仍验收通过，说明该矛盾未影响测试结论，但它客观存在）。要真正闭合需要引入"裁定归一/冲突检测"，属新增机制而非最小修复，本轮未做。

11. **没有缺陷清单时的回退是"可能自愈"，不是"保证收敛"**（`task02-eshop-attempt04` 实录）：test 第 1 轮 0 用例回传，F19 正确地没有伪造任何缺陷条目（`缺陷 0 个（新增 0，闭环 0）`、`bug_reports` 为空），于是回退给研发时**清单是空的**——optimize 的 summary 就写着「处理 0 个缺陷（定向回归 0/0 通过）」。这次它仍然修好了，产物级证据是 `artifacts/fix_summary/v1.json`：`fixed: 0 / items: []`，但 `fix_targets[0]` 原文写着「test_protocol_no_result: tests/test_eshop.py 未回传 <<<MASS_RESULT>>> 结果（**test_report.protocol_note**），已重写 main() 单次遍历 suite 并输出可解析 JSON」——即研发是**读协议说明自己排查**的，不是框架给出了缺陷条目。同一机制在不读 `protocol_note` 时就会白烧一次回退预算，属运气路径。要闭合需要"0 证据 → 生成一条 `test_suite_defect` 类缺陷占位"，属新增机制，本轮未做（F24 只是让这类缺陷在静态阶段就能被命名）。

12. **测试套件每轮由 LLM 整体重写，跨轮通过率不可直接比较**（`task02-eshop-attempt04` 实录）：iter02 的 60 条用例名与 iter03 的 56 条几乎逐条不同（`test_functional_add_product_get_price` → `test_functional_add_get`），因为 `mas/agents/tester.py:171-179` 在每轮 test 节点开头都会把 LLM 本轮生成的测试文件写盘。后果有三层：①"通过率 0.75→1.0"不能作为改进证据（分母换过了）；②框架不阻止套件规模收缩（60→56，本轮收缩后三类覆盖率仍各 1.0，因为覆盖率算的是"功能点有没有被覆盖"而不是"用例数量"）；③如果 LLM 某一轮把关键断言写少了，没有任何机制会把它拉回上一轮的覆盖强度。probe-04 更极端：四轮 test 用了**三个不同的测试文件**——`test_report/v1` 是 `tests/test_smartptr_independent.py`（21 条、调 g++，全败于 `g++ not found`）、`v2/v3` 换成 `tests/test_smartptr_acceptance.py`（v2 因缺 `import json` 得 0 用例，v3 同一文件跑出 **18 条全过、通过率 1.0**）、`v4` 再换成 `tests/test_smartptr.py`（18 条全过）。**同一 run 内验证对象在轮次间漂移**，且 `test_smartptr_acceptance.py` 这个文件名与 probe-02 那次假通过用的套件（§3.3(b)）同名——靠 F23 的 `gap` 字段（四轮恒为 1）才没有变成假通过。要真正闭合需要"套件等价性检查（用例数/断言数不得相对上一轮下降超过阈值）"，属新增门禁项，误判风险高，本轮按最小改动原则未做。

13. **Skill 与 MCP 两套扩展能力在本阶段的所有 run 里均未启用**（如实边界，避免被读成"已用起来"）：
    - 事实核对：`config/mcp.yaml` 是 `servers: []`；`config/system.yaml:47` 是 `llm.tools_enabled: false`。因此 `leader._build_tool_runner` 直接返回 `None`，`mas/agents/base.py:97 _tool_schemas()` 拿到 None 就"走原有单轮生成"。本阶段全部 run 的 `events.jsonl` 里 `tool_runner_ready`/`tool_calls_requested` 出现 **0 次**，`llm_traces.jsonl` 里 `tool_calls` **0 次**。
