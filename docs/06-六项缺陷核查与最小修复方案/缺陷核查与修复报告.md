## 二、逐项核查证据

### 2.1 缺陷 1：单进程架构且缺乏并发处理能力 —— 确认存在

**证据链：**

1. `mas/leader.py:156` 的状态机是单线程顺序循环：`while node_id and node_id not in flow.terminal and steps < max_steps:`，节点逐个执行，`agents[node.role].act(task)` 同步调用，前一个节点未结束不会启动下一个。
2. Agent 间协商（`leader.py` `_consult_factory`）是同线程内的同步请求-应答：`agent.consult()` 直接调用并等待返回。
3. `mas/` 全部 20 个源文件中无 `asyncio`、`multiprocessing`、`concurrent.futures`、`ThreadPool` 导入（修复前 grep 命中为 0，仅 `blocking` 等英文单词误命中）。
4. 全项目仅有的线程在两处，均不属于 Agent 执行层：
   - `frontend/server.py:25,30` `ThreadingHTTPServer`（HTTP 并发接入）+ `:340` 每次运行起一个 daemon 线程跑 Leader——每个 run 内部仍是串行流水线；
   - `mas/mcp.py:259` stdio 传输的读线程（IO 读取用，非任务并行）。

**边界说明（如实标注）：** 该缺陷的准确表述是「**核心交付流水线为单进程串行**」。前端具备并发起多个 run 的能力，但（a）每个 run 内部无并行；（b）并发 run 共享 `workspace/knowledge/experience.jsonl` 且无锁，会互相覆盖——这与缺陷 2 叠加。完全节点级 DAG 并行超出「最小可行」范围，本次交付并发原语 + 可并行热点（静态分析）并行化。

### 2.2 缺陷 2：文件状态无法支持分布式共享 —— 确认存在

**证据链：**

1. `mas/blackboard.py:68` `self._latest: Dict[str, Any] = {}`：黑板真相状态是**进程内内存字典**，文件只是备份。
2. 版本号 `version = len(self._refs.get(name, [])) + 1`（修复前 `blackboard.py:75`）：按**进程内计数**生成。两个进程/实例同时发布同一产物都会写 `v1.json`，后写覆盖先写，历史版本直接丢失。
3. 全仓库无任何文件锁（无 `fcntl`/`msvcrt`/`LockFile`）：`Blackboard.publish`、`ExperienceLibrary.save`（`experience.py:181-185` 全量覆写）、`MessageBus`/`EventLog`（append-only JSONL，仅这一种写入是并发安全的）均无互斥保护。
4. `MessageBus.digest()`（`bus.py:147`）基于进程内 `_messages` 列表：其他进程发的消息对本进程不可见。
5. 经验库 `load()` 全量读 + `save()` 全量覆写：两个并发运行会各自 merge 后覆写，丢经验。

**边界说明：** 严格意义上的「分布式」需要共享存储后端（对象存储/数据库），那属于架构演进而非最小修复。本次交付的第一层能力是：**同一共享卷上的多进程/多实例可以安全协作**（锁 + 版本防冲突 + 跨进程可见），这已消除「并发即丢数据」的问题。

### 2.3 缺陷 3：沙箱隔离机制仅停留在路径级别 —— 确认存在

**证据链：**

1. `mas/sandbox.py:105-108` `resolve()` 的全部隔离能力就是路径包含检查：`if self.root not in path.parents and path != self.root: raise SandboxError`。
2. `Sandbox.run()`（修复前 `sandbox.py:159-186`）：
   - `env = dict(os.environ)` **全量继承**环境变量——包括 LLM API Key（`MAS_LLM_API_KEY` 等），沙箱内执行的 LLM 生成代码可直接读取凭据；
   - 无用户/命名空间隔离、无网络隔离、无 CPU/内存/文件大小/进程数限制；
   - 命令参数由 LLM 输出决定（`tester.py:72` 直接 `python <test_file>`），路径检查约束不了子进程内代码的任意行为。
3. 静态分析有 `eval_usage` 危险调用检测，但无网络相关检测。

**边界说明（如实标注）：** 网络隔离在纯标准库 + 跨平台（Windows 主用）前提下**无法真正实现**（无 network namespace，Windows 无 Job Object 标准库封装）。本次采用「命令白名单 + 资源限制 + 敏感变量剥离 + 网络导入**检测**」的组合，并在事件中如实记录实际生效的隔离等级（如 `path+cmd +env-strip+windows-no-rlimit`），不宣称不存在的隔离。

### 2.4 缺陷 4：经验库不具备语义检索功能 —— 确认存在

**证据链：**

1. `mas/experience.py:348-353`（修复前） relevance 的全部文本匹配：
   - `tag_overlap`：标签归一化后的**集合精确交集**；
   - `keyword_overlap`：`_normalize(kw) in haystack`——**子串精确包含**。
2. 无 embedding、无向量索引、无相似度模型、无同义词机制（`LearningConfig` 无对应字段）。
3. 直接后果：「运费计算必须向上取整」的经验，无法被「物流费核算逻辑」这样的同义改写查询召回（子串零重叠 → `keyword_overlap = 0`）。

### 2.5 缺陷 5：未采用 function calling 机制 —— 确认存在

**证据链：**

1. `mas/llm.py:132-148`（修复前）`_generate_openai` 的 payload 只含 `model/messages/temperature/max_tokens/response_format`：**无 `tools`、无 `tool_choice`**；响应解析只取 `message.content`，**不解析 `tool_calls`**；`Generation` 无工具调用字段。
2. `mas/mcp.py` 的 `MCPClient` 实现了 `initialize/tools_list/tools_call`，但唯一调用方是 CLI 的 `mcp check` 健康检查（`cli.py:302` `cmd_mcp`）——工具清单从未进入 LLM 对话，Agent 生成过程中无法调用任何工具。
3. offline provider 是规则化算子库，本就不涉及工具调用；即两条 Provider 路径都不具备 function calling。

### 2.6 缺陷 6：权限控制、重试策略等配置声明未实际落地 —— 确认存在

**证据链（权限）：**

1. 五个角色 YAML 均声明 `permissions`（如 `tester.yaml: can_write_code: false`、`reviewer.yaml: can_rollback: true`），`mas/config.py:320` 加载进 `RoleConfig.permissions`。
2. 修复前全仓库检索 `permissions` 消费方：**只有 config.py 自身的加载代码**，无任何读取点。
3. 反证（ declaration 与行为矛盾）：`tester.yaml` 声明 `can_write_code: false`，而 `mas/agents/tester.py:59`（修复前）直接调用 `self.ctx.sandbox.write_file(...)` 写文件——声明对运行期没有任何约束力。

**证据链（重试）：**

1. `config/flow.yaml:21` 节点声明 `retry: { max_attempts: 1 }`，`mas/config.py:239` 加载进 `NodeConfig.retry`。
2. `leader.py` 状态机与 `BaseAgent.act()` 均不读取 `node.retry`；LLM 调用失败（`llm.py` 抛 `AgentError`）在 `base.py:63-65` 被捕获后直接返回 fail，**无任何重试**。
3. 注意区分：`collaboration.rollback`（回退策略）是**已落地**的另一套机制（`leader.py` 回退计数、`max_attempts`、升级策略都在工作）；未落地的是节点级 `retry` 与 LLM 网络重试。

## 三、最小修复方案（逐项）

### 3.1 修复 1：并发处理能力

**改动文件：**

| 文件 | 改动 |
| --- | --- |
| `mas/concurrency.py`（新增，约 60 行） | `parallel_map(fn, items, max_workers)`：保序并行 map，单任务异常按原位写回不拖垮整批；默认并行度 `min(8, cpu+4)` |
| `mas/sandbox.py` | `analyze()` 拆出 `_analyze_file()`（单文件纯函数，无共享状态），按文件 `parallel_map` 并行，结果按原顺序合并 |

**修改逻辑：** 选择线程池而非多进程——瓶颈是 IO 等待（文件读取/AST 解析中的解释器工作），且多进程会破坏 Blackboard/Bus 的进程内状态模型（与修复 2 的落地方式冲突）。并行度可由 `runtime.sandbox_analyze_workers` 覆盖。

**修复效果与验证：**
- 48 个文件（每个 120 个函数）基准：串行 0.617s → 并行 0.304s，**加速 2.03x**，且 `loc/findings/functions` 与逐文件串行完全一致（结果无损）；
- 新增测试 `test_parallel_map_preserves_order` / `test_parallel_map_propagates_task_exception_in_place` / `test_analyze_parallel_matches_per_file_serial`。

### 3.2 修复 2：文件状态支持分布式共享

**改动文件：**

| 文件 | 改动 |
| --- | --- |
| `mas/filelock.py`（新增，约 90 行） | 跨进程排他文件锁：Windows `msvcrt.locking` / POSIX `fcntl.flock`，超时抛 `FileLockTimeout`，退出 `with` 自动释放 |
| `mas/blackboard.py` | ① 版本号改为「扫描目录已有 `v*.json` 取 max+1」（`_next_version`，`blackboard.py:116`）；② `publish` 写文件在文件锁内完成；③ `get()/has()/require()/snapshot()` 进程内未命中时回落读磁盘 `latest.json`（`_load_from_disk`，`blackboard.py:142`） |
| `mas/experience.py` | `add/reinforce/promote/prune/retrieve` 的「load→改→save」全链路放入文件锁（`_locked()`）；`record_metrics` 加锁 |

**修改逻辑：** 保留进程内 `_latest` 作为同进程快速路径（性能不变），只把「版本号分配」和「写文件」做锁保护，把「读取」做磁盘回落——这样多进程发布不会互相覆盖，且任意进程能看到别人的最新产物。锁粒度是产物目录下的 `latest.json.lock` 伴随文件，不承载业务数据。

**修复效果与验证：**
- 双进程各并发发布同一产物 20 次：版本号 **1–40 连续无冲突**，双方写入**完整保留**（重复 3 轮 + 受控交错 1 轮，全部 PASS；修复前两个进程都会从 v1 开始互相覆盖）；
- 跨进程锁互斥直接验证：A 持锁 3s，B 在 1.01s 时按预期收到 `FileLockTimeout`；
- 新增测试 `test_file_lock_excludes_concurrent_holder` / `test_blackboard_versions_do_not_collide_across_instances` / `test_blackboard_get_falls_back_to_disk_for_foreign_publish`。

### 3.3 修复 3：沙箱隔离增强

**改动文件：** `mas/sandbox.py`（约 +120 行）+ `config/system.yaml`（新增 `runtime.sandbox_command_policy` / `sandbox_strip_sensitive_env` / `sandbox_limits` 配置段）

**修改逻辑（四层，均在既有路径检查之外新增）：**

1. **命令白名单**（`_check_command`）：只放行 Python 解释器（`python/python3/py`，兼容绝对路径与 `python3.13` 版本号变体）；显式拒绝 `cmd/sh/bash/powershell` 等 shell 解释器（`-c` 可绕过一切路径级约束）。既有全部调用点（tester 跑测试、developer 导入自检/回归、skill 冒烟）均为 `python`，不受影响。
2. **敏感环境变量剥离**（`_build_env`）：剔除变量名含 `KEY/TOKEN/SECRET/PASSWORD/CREDENTIAL` 的环境再进沙箱——LLM 凭据不会泄露给被测代码；非敏感变量（PATH 等）保留。
3. **资源限制**（`_spawn_kwargs` + `_apply_rlimits`，仅 POSIX）：`RLIMIT_CPU/AS/FSIZE/NPROC`。**取舍说明**：`preexec_fn` 在 fork→exec 窗口运行 Python 代码，多线程进程中有极小概率死锁，故仅在单线程进程（CLI 直跑）启用；多线程场景（前端面板）跳过并在 `sandbox_exec` 事件中标注 `rlimit-skipped-multithread`。Windows 无标准库等价方案，标注 `windows-no-rlimit`——**不宣称不存在的隔离**。
4. **网络导入检测**（`network_import` 规则）：AST 全树遍历标记 `socket/urllib/requests/aiohttp` 等导入，severity 默认 major，让 reviewer 能显式拦截高危外连依赖。这是**检测**不是隔离，finding 消息中已如实标注。

**修复效果与验证：** 每次沙箱执行的事件中记录实际隔离等级（实测输出 `path+cmd +env-strip+windows-no-rlimit`）；新增测试 `test_shell_interpreter_rejected` / `test_python_interpreter_allowed` / `test_sensitive_env_stripped_from_child`（探针脚本证实 canary 与 API Key 均不可见、PATH 保留）/ `test_network_import_flagged`。

### 3.4 修复 4：经验库语义检索

**改动文件：** `mas/experience.py`（`_tokenize_for_match` / `_expand_with_synonyms` / `_semantic_overlap`，约 +55 行）、`mas/config.py`（`LearningConfig.synonyms` 字段）、`config/learning.yaml`（新增 `synonyms` 词典段）

**修改逻辑：** 零依赖前提下用两级软匹配替代原来的关键词子串精确包含：
1. **中文 bigram + 英文词元**切分：`_tokenize_for_match` 把文本切为「中文单字 + 相邻二字 + 英文数字词」，用重叠系数（交集/较小集合）度量——「阈值比较」与「边界阈值处理」无公共子串但共享单字与 bigram，可得非零相似度；
2. **同义词扩展**：`learning.yaml` 的 `synonyms` 段（如 `运费: [物流费, 配送费]`、`计价: [计算, 核算]`）在检索时对查询做扩展，同义改写可召回。

**修复效果与验证：** 查询「物流费核算逻辑」成功召回 lesson 为「运费计算必须向上取整」的经验（修复前子串零重叠、召回失败）；`_score` 的 `detail` 中新增 `keyword_overlap` 便于审计；新增测试 `test_bigram_soft_match_beats_exact_substring` / `test_synonym_expansion_recalls_paraphrase`。

### 3.5 修复 5：function calling 闭环

**改动文件：**

**修复效果与验证：** 新增测试 `test_parse_tool_calls_normalizes_arguments` / `test_agent_tool_call_loop_executes_and_feeds_back`（假 LLM 两轮 + 假 Runner：验证工具被执行、结果以 tool 消息回传、二次生成携带 extra_messages、`tool_rounds` 计数）/ `test_tool_runner_static_schema_and_error_paths`（未知工具与静态工具返回错误文本而非抛异常）。真实 MCP 服务链路（握手/tools/list）由既有 `tests/test_mcp.py` 覆盖。

#### 3.5.1 function calling 端到端验证（真实组件，非 mock）

mock 测试只能验证骨架逻辑。为如实验证整条链路，新增 `tests/test_function_calling_e2e.py`，用**真实组件**跑通：

```
本地 OpenAI 协议桩 HTTP 服务（脚本化返回 tool_calls → 最终 JSON）
  → 真实 LLMClient（urllib 真实发包）
  → 真实 BaseAgent._generate_with_tools 闭环
  → 真实 ToolRunner.register_from_mcp（拉起 tests/fake_mcp_server.py 真实 stdio 子进程）
  → 真实 MCP JSON-RPC tools/call 执行
  → tool 消息回传，桩服务实录第二轮请求供断言
```

**5 个用例全部通过**（`Ran 5 tests ... OK`），实测报文（桩服务实录）：

```

       messages=[system, user]
第2轮：messages=[system, user,
                  assistant(tool_calls: echo({"text": "订单重量 1.3kg"})),

```

覆盖断言：tools schema 转换正确（echo/ping）、首轮下发 tools 且不带 response_format、tool_calls 归一化、MCP 工具**真实执行**且参数完整 round-trip、回传消息序列为 `assistant(带 tool_calls) → tool`、`tool_calls_requested` 事件、`llm_traces.jsonl` 每轮留痕、Leader 装配门禁（默认 false 不装配 / true 装配发 `tool_runner_ready` / 无服务降级发 `tool_runner_empty`）、offline Provider + tools 不触网。

**端到端验证过程中发现并修复了 3 个 mock 测试发现不了的真实缺陷：**

| # | 缺陷 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | tool 消息回传时缺少携带 `tool_calls` 的 assistant 消息 | 违反 OpenAI 协议，严格端点因 `tool_call_id` 找不到归属返回 400 | `base.py` 新增 `_assistant_tool_message()`，回传前先还原 assistant 消息 |

### 3.6 修复 6：权限控制与重试策略落地

**改动文件：** `mas/agents/base.py`、`mas/leader.py`、`mas/agents/developer.py`、`mas/agents/tester.py`、`config/roles/*.yaml`（补全注释与新键）、`config/system.yaml`（`llm.retry`）

**修改逻辑：**

1. **权限守卫**（`base.py:268` `permit()` + `:282 sandbox_write()` + `:290 sandbox_run()`）：
   - 语义映射：`tests/` 目录写入 → `can_write_tests`，其余写入 → `can_write_code`，命令执行 → `can_execute`（兼容旧键 `can_run_tests`）；
   - **关键兼容性设计：只有显式声明 `false` 才拦截，未声明的键默认放行**——现有五个角色的声明全部满足其实际行为（tester 只写 tests/、reviewer 不写不跑、developer 全放行），默认流程零影响；
   - 拒绝时发 `permission_denied` 事件并抛 `SandboxError`（Agent 骨架将其转为节点失败，理由可追溯）。
2. **门禁否决权**（`leader.py` `_run_gate`）：签署 verdict=reject 时校验 `can_block_acceptance`，无此权限的角色的否决不生效并发事件（product/reviewer/tester 已声明 true，developer/reporter 声明 false，默认流程无变化）。
3. **回退权限**（`leader.py:554` `_rollback_permitted`）：节点角色显式 `can_rollback: false` 时拒绝回退并终止流程（developer 已声明 false，但其节点的 fail 边均非回退边，默认流程无变化；tester 未声明 → 放行，test→optimize 回退不受影响）。
4. **节点级重试**（`leader.py:530` `_act_with_retry`）：`flow.yaml` 的 `retry.max_attempts > 1` 时失败原地重跑该节点，每次重试发 `node_retry` 事件。与 `collaboration.rollback` 正交（原地重试 vs 退回上游）。默认 `max_attempts: 1` → 行为不变。
5. **LLM 网络重试**（`llm.py:195` `_post_with_retry`）：按 `llm.retry`（默认 `max_attempts: 1`，即不重试）对网络错误与 429/5xx 指数退避重试，4xx 立即失败。

**修复效果与验证：** 新增测试覆盖：显式 false 拦截/未声明放行、tests/ 与代码写入分流、执行权限守卫、旧键兼容、节点重试至预算耗尽、回退权限拒绝、门禁否决权、重试默认值。端到端回归中默认流程 `permission_denied` 事件数为 0（不误伤）。

## 五、明确未做到的部分（如实标注）

1. **节点级 DAG 并行未实现**：流水线节点间有数据依赖（implement→review→test），真正的节点并行需要流重构，超出最小改动范围；本次交付的是并发原语与热点并行化。
2. **网络隔离未实现**：纯标准库 + Windows 主用前提下无可行方案，以「网络导入检测 + 事件标注」替代，未宣称隔离。
3. **Windows 无 rlimit**：Job Object 需 ctypes 封装约 60 行且风险较高，本次跳过并在事件中标注降级；POSIX 已完整支持。
4. **语义检索是轻量软匹配**：中文 bigram + 同义词词典不等于 embedding 语义理解；接入向量检索需要新增依赖（违背项目零依赖约束），已在代码注释与配置说明中如实标注。
5. **多机分布式未实现**：文件锁方案解决「同一共享卷多进程」，跨机器需要共享存储后端替换（架构演进项）。
6. **`python -m mas demo` 未完整实跑**：默认配置走真实 LLM 端点（openai_compatible + DeepSeek，单次响应 150~200s），三轮演示超出单次命令时限；已用临时 offline 配置跑通 CLI 端到端两轮作为替代验证。
