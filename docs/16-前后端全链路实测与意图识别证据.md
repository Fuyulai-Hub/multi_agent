## 二、意图识别：三层判定，各有产物

实现位置：[mas/intent.py:43](../mas/intent.py)（三值枚举 + 关键词表）、[mas/agents/product.py:57](../mas/agents/product.py)（L1 注入与事件）、[mas/agents/product.py:83](../mas/agents/product.py)（L3 兜底）。

| 层 | 性质 | 产出 | 本轮实测值 |
|---|---|---|---|
| L1 规则 `classify_delivery_shape()` | 确定性，不看模型 | `intent_classified` 事件 + 命中词 | 短链：`{"hint":"full_stack_ssr","explicit":true,"keywords":["前后端"]}`；tally：`{"hint":"backend_only","explicit":true,"keywords":["只做后端","只要后端","不需要前端"]}` |
| L2 模型契约 | 概率性，product 节点必填字段 | `requirement_spec.delivery_shape` + `delivery_shape_reason` | 两者均与 L1 一致，来源 `declared` |
| L3 框架校验 | 确定性兜底 | 非法/缺失值 → `backend_only` 并发 `intent_fallback` | 本轮未触发（模型给的值都合法） |

设计上的两处取舍，值得记住：
- 兜底取 `backend_only`：该形态下本模块不触发任何新行为，老任务零风险。
- 门禁新增两条 SPA 专用判据写成 `delivery_shape != 'full_stack_spa' or ui_evidence.…`（[config/flow.yaml:99](../config/flow.yaml)）。`expr.py` 的 BoolOp **不短路求值**，所以 `ui_evidence` 必须在任何形态下都被发布，否则老任务会被整条 criterion 误伤——tester 第 6.5 步无条件发布即为满足此约束。

## 六、能力边界（如实）

**能做**：需求 → 方案 → 实现 → 测试 → 验收 → 报告全自动闭环；交付形态可分纯后端 / SSR 全栈；页面类用例走真实 HTTP 响应体断言；缺陷可自我回退修复并复测；非 Python 语言或浏览器证据缺失时如实失败。

**不能做**：
- B 档（前端真在浏览器里运行的 SPA）：需要 `mas/uiprober.py` + Playwright MCP 提供浏览器证据，本机 `browser_ui_ready=false`，该形态门禁会判「证据不足」而 fail，**不会退化成「Python 测试全过就放行」**（这是 F23 教训的机制化）。
- 依赖第三方包（pip）、容器、真实外网访问的验收——沙箱命令白名单与无网络隔离决定其不在范围内。
- 部署/运维：验收止于本地可运行 + 测试通过。
