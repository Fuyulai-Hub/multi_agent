# 26 - 消息队列引入可行性评估

> 评估对象：`G:/mycv/cragent/multi_agent`（master，2026-10-19）
> 评估方法：只读代码 + 运行产物实测，结论逐条给出文件:行依据；无依据的判断显式标注「推断」。
> 与 `docs/25-MySQL与Redis接入评估.md` 的关系：25 号文把 MQ 列进了「不做（负面清单）」，
> 本文把那条结论展开成完整论证，并补上 25 号文遗漏的一个真实分布式场景。

> **状态更新（2026-10-19）：本文第 0 节的「不能直接上」结论已被实际实现取代。**
> 落地方式与本文建议一致——**不动 `MessageBus.send()` 的同步契约、不动 jsonl SSOT**，把 Redis Streams 作为传输层并行接入：
> - 任务队列：前端/CLI 入队 → 独立 `mas/worker.py` 通过消费组 `XREADGROUP` 领取，ACK/PEL/XAUTOCLAIM 认领、ZSET 延迟重试、DLQ 死信；长任务不再绑定前端进程生命周期。配置见 `config/system.yaml` 的 `runtime.mq`，代码见 `mas/mq.py`、`mas/worker.py`，前端入口在 `frontend/server.py`。
> - Agent 总线：`messages.jsonl` 仍是审计 SSOT，同一批消息双写 `mas:mq:agent:<run_id>`；每个角色独立消费组，协商的 `correlation_id` 与 Stream entry ID 一并记录（`mas/leader.py`）。
> - 原评估中的两个硬约束（同步返回 `Message`、进程内状态）未被破坏：`send()` 仍同步返回，MQ 投递失败时告警并回退本地路径；worker 以 `run_summary.json` 做幂等，部分运行归档到 `workspace/run_attempts/`。
> - 验证证据：`tests/test_mq.py` 14/14、`tests/test_mq_integration.py`（真实 Redis）6/6、全量回归 371 项 OK；worker E2E（`mq-e2e-161825`）bus 投递 11 条、事件流 99 条、errors 0、队列 PEL 0；前端内嵌 worker 排队→完成、排队中取消→「已终止」均已实测。

## 0. 结论

| 问题 | 结论 |
| --- | --- |
| 现在能上 MQ 吗？ | **不能直接上**。当前系统的「消息」不是线程间通信，而是运行内的审计留痕；把 `MessageBus.send` 改成投递给 broker，`send()` 的同步返回 `Message` 这条契约立刻断裂，而 `Leader._consult_factory`（`leader.py:750-784`）依赖它同步拿 `request.id` 作为 `correlation_id`。 |
| 上了有收益吗？ | **单机单运行形态下没有**。MQ 解决的三件事（削峰、解耦、跨进程/跨机异步投递）里，前两件本系统不存在瓶颈，第三件当前被「进程内状态模型」挡着（`concurrency.py:7-8` 自认）。 |
| 什么情况下应该上？ | 只有一种：**要把「一次运行」拆到多台机器执行**（长任务不被前端进程生命周期绑定、横向扩容）。这时 MQ 变成必需件而非优化件，但它必须和「状态外置」打包做，量级是一次架构重写。 |
| 现在真正该做的是什么 | 分两条独立的路：① 长任务从「前端线程」挪到独立 worker 进程（不一定要 MQ，文件队列就够）；② 已有 Redis 上把 `bus` 的**留痕路径**双写成 Stream（读模型，不动写模型）。这两件都不破坏任何现有契约。 |

一句话：**MQ 是架构形态的产物，不是性能补丁。当前架构里没有它的位置；而当前架构确实有一个真实痛点，那个痛点用「独立 worker + 任意队列」就能解，不必先引入 Kafka/RabbitMQ。**

## 1. 先认清：这个系统的「消息」到底是什么

`mas/bus.py` 的类注释写的是「让所有 Agent 相互通信」，但读实现会发现它更接近**审计日志**：

| 事实 | 依据 |
| --- | --- |
| 消息先 append 到 `_messages` 内存 list，再 append 到 `messages.jsonl`，没有任何阻塞/唤醒语义 | `bus.py:81-89` |
| `send()` **同步返回 `Message` 对象**，调用方立刻用它 | `bus.py:28-60` |
| 广播不扇出到消费者，只是写一条 `recipients=["all"]` 的记录；`inbox()` 是主动轮询过滤 | `bus.py:73-84`、`bus.py:110-121` |
| 「已读未读」靠 `since_id` 指针在内存 list 里做下标查找 | `bus.py:123-130` |
| 真正的请求-应答是**同线程直调**：`bus.send(request)` → `agent.consult()` → `bus.send(response)`，中间没有等待、没有超时、没有失败重试 | `leader.py:759-784` |
| 消费者只有「注入 Prompt 的摘要」一条：`digest()` 取最后 10 条压成 1600 字符 | `bus.py:132-140` |

所以它的真实职责是：**给 Prompt 提供「别人干了什么」的上下文 + 给复盘提供协作证据**。这两种职责都不需要 broker。

### 1.1 全流程是一次同步阻塞的 while 循环

`leader.py:296-424` 的主循环：取节点 → `_act_with_retry`（内部一次 LLM 调用，实测单次 30~400s）→ 门禁判定 → 决定下一个节点。**没有任何一处是两个 Agent 并发跑、靠消息交互**。`concurrency.py` 的线程池只用在「同一节点内按文件并行做静态分析」和「LLM 并发调用」，是 map 语义、要等全部结果。

这意味着：**引入 MQ 也换不来并行度**。想并行必须先改 `flow.yaml` 的拓扑（当前是单链 + 回退边），而 `docs/14-架构重构P0` 已明确不动拓扑。

### 1.2 数字支撑

| 指标 | 实测值 | 来源 |
| --- | --- | --- |
| 单次运行事件数 | 最大 349 条 | `workspace/runs/*/events.jsonl` 行数统计 |
| 单次运行消息数 | 数十条量级（每节点广播 + 协商各 2 条） | `bus.py` 调用点 |
| 单次运行耗时 | 62.6s / 893s / 2848s / 4961s / **13983s（3.9 小时）** | `workspace/knowledge/metrics.jsonl` |
| 累计运行数 | 55 | `workspace/runs` 目录数 |
| 消息吞吐峰值 | ≤ 10 msg/分钟（349 条事件里 message 类型更少） | 上两行推算 |

**10 msg/分钟**这个量级，用 MQ 描述是失真的——这不是消息系统，是一次运行内的几十条笔记。

## 2. 真正的约束：状态模型是进程内的

这是「上 MQ」最硬的一道墙，不是性能问题，是正确性问题。

| 状态 | 存放位置 | 换进程后会怎样 |
| --- | --- | --- |
| `run_state`（回退计数、injected 经验 id、negotiations…） | `leader.py:227-233` 的 dict，挂在 `AgentContext` 上 | 丢失，回退预算与经验反馈全部重置 |
| `MessageBus._messages` / `_counter` | `bus.py:57-58` 进程内 list | 新进程读不到历史消息；`inbox()` 返回空 |
| `Blackboard._latest` / `_refs` | `blackboard.py:70-71` 进程内缓存 | 只能回落读磁盘（`blackboard.py` 注释已说明「最终一致」） |
| 取消信号 | `RUNNING_TASKS` dict（`frontend/server.py:77`） | 跨进程不可见——`docs/25` 的 Redis registry 正在修这一点，`runhub.py` 已实现 |
| `ToolRunner` 的 MCP 子进程 | `toolrunner.py` 进程内 | 跨进程要重连（可做，但每个 worker 都得各自持有一份 stdio 子进程） |

`concurrency.py:7-8` 自己写了这句话：

> 无需把系统重构为多进程（多进程会破坏 Blackboard/Bus 的进程内状态模型）

所以「把每个 Agent 拆成独立消费者、靠 MQ 通信」这个最直观的 MQ 用法，等于要重做整个状态层。而这层的价值恰恰在于**可回放、可 diff 的证据链**（`events.py:1-5`）。

**结论**：MQ 化 ≠ 换传输层，MQ 化 = 状态外置 + 幂等重放 + 检查点续跑 + 分布式事务边界。这是三个月的工程，不是一次改造。

## 3. 真正的痛点：长任务被前端进程绑死

这是我认为当前最值得改、且**和 MQ 有关但不是必须用 MQ** 的地方。

现状（`frontend/server.py:454-471`）：

```python
cancel_event = threading.Event()
RUNNING_TASKS[run_id] = cancel_event

def worker() -> None:
    Leader(config).run(...)          # 实测最长 13983s = 3.9 小时

threading.Thread(target=worker, daemon=True).start()
```

问题链条：

1. 运行跑在一个 `daemon=True` 的后台线程里，**绑定前端服务的进程生命周期**。
2. 服务进程一重启 / Ctrl-C / 机器休眠 → 线程被 kill → 运行中断（无 `run_summary.json`，只能靠「目录存在但无 summary」判定为异常中断）。
3. 单进程 `ThreadingHTTPServer` + 线程，**并发跑两个运行会同时在 `experience.py` 的全局 `file_lock` 上争抢**（`docs/25` 已实测：四处 `add/reinforce/promote/retrieve` 都是全量 load→save）。
4. 运行中无法滚动升级前端：升级必须等运行结束。

**这才是需要一个「任务队列」的真实理由**：不是为了让 Agent 之间异步通信，而是为了让**运行的生命周期和 HTTP 服务的生命周期解耦**。

而这个需求的最小实现**不需要 Kafka**：

| 方案 | 工作量 | 收益 | 风险 |
| --- | --- | --- | --- |
| A. `POST /api/run` → 写一个 `pending/<run_id>.json` 到磁盘，独立 worker 进程（`python -m mas worker`）轮询并抢占（`file_lock` 或 Redis `SETNX`） | 小（半天级） | 前端重启不影响运行；可起多个 worker 横向扩容 | 已有 registry（Redis）可复用做判活，冲突面小 |
| B. Redis Stream（用的是已接入的 Redis，`store/redis_backend.py` 已实现 RESP2 客户端） | 中 | 同上 + 天然多消费者 + 消费确认 | 需补 `XADD/XREADGROUP` 命令（客户端现无这些方法） |
| C. RabbitMQ / Kafka | 大 | 与 B 相同能力，外加持久化/死信 | 新依赖、新运维、单机能跑但收益不增 |

**对当前规模，A 的收益/成本比最好；B 是 A 的自然升级；C 没有理由。**

## 4. 如果要上 MQ，可复用的东西和具体缺口

### 4.1 已有的地基（比想象中近）

| 已具备 | 位置 | 说明 |
| --- | --- | --- |
| 零依赖 Redis RESP2 客户端 | `store/redis_backend.py:38-120` | 只用标准库 socket，符合项目「除 PyYAML 外零依赖」的约定 |
| Redis 不可用即降级的契约 | `store/__init__.py:1-20` | 「不抛异常打断主流程」的既有约定可直接套到 MQ 上 |
| 运行注册表抽象 | `runhub.py:79-133` | `MemoryRunRegistry` / `RedisRunRegistry` 双后端，`build_registry` 永不返回 None |
| 节点边界的取消检查点 | `leader.py:296-303` | MQ 消费者要「中途放弃某任务的抢占」，这里就是天然检查点 |
| 事件日志的订阅者机制 | `events.py:44-51`、`_make_mysql_event_sink`（`leader.py:63-110`） | 已有一套「写主路径 + 异步双写索引」的模式，MQ 发布可以照抄这个形态 |
| 静态工具注册 | `toolrunner.py:80-104 register_local` | 现成的 `name/fn/description/parameters` 签名，用来注册一个 `mq_publish` 工具最省事 |

### 4.2 具体缺口（一行行看出来的）

| 缺口 | 位置 | 后果 |
| --- | --- | --- |
| `send()` 同步返回 `Message` | `bus.py:57-60`、`bus.py:73-84` | 改成投递后无法立刻拿到 `id`；`leader.py:764-775` 依赖 `request.id` 做 `correlation_id` |
| `bus.py` 无 `publish` / `subscribe` / ack 概念 | 全文 | 需要新增接口层，且要保证「默认路径逐字节一致」 |
| `RedisClient` 缺 Stream 命令 | `store/redis_backend.py` 只有 `get/set/setnx/expire/eval` 等通用命令 | 要发 MQ 就得补 `XADD/XREADGROUP/XACK`，约 50~80 行 |
| 消息 id 是运行内自增 | `bus.py:74` `f"msg-{self._counter:04d}"` | 天然冲突：两个运行、两个进程都是 `msg-0001`。要上 broker 必须换成全局唯一 id，而 `correlation_id` 又会随之变化——**这会污染历史证据的可比性** |
| 没有消费者身份 | 全仓无 consumer/worker 概念 | 拆消费者就必须引入「谁在跑哪个节点」的外置状态，见第 2 节 |
| 门禁表达式读的是黑板快照 | `leader.py:_run_gate` 用 `ctx.blackboard.snapshot()` | 若产物由另一个进程写入，门禁判定存在读不到最新版本的窗口（`blackboard.py` 自称「最终一致」，但门禁是严格判定的位置） |
| 测试夹具耦在生产配置上 | `config/system.yaml` 同时被 `tests/test_skill_injection.py` 当作夹具 | 新增 `mq:` 段必须默认关且不碰既有键（这是本项目踩过的坑，见 working memory） |

### 4.3 一个容易忽略的真实分布式场景（docs/25 漏了）

`docs/25` 的负面清单写「没有任何跨运行异步解耦需求」。严格讲这**不完全准确**——有一条场景是真跨机的：

`mas/toolrunner.py register_from_mcp` 支持的 MCP 服务既有 `transport: stdio` 也有 `transport: sse`（`config/mcp.yaml:4-6`）。走到 SEES/远端 MCP 时，**Agent 与工具是两台机器之间的一次异步请求-应答**，中间没有重试、没有超时后的幂等保证（`_call_one` 直调 `mcp.py` 的读写）。

如果你的下一步是「让 Agent 调用跑在集群上的工具」——比如 HPC 集群上的批量推理（中南 HPC 端点那种长任务），那么 MQ 就真的有位置了：**它承接的是「Agent ↔ 远端能力」的异步请求，而不是「Agent ↔ Agent」的内部消息**。这是当前唯一说得通的 MQ 落点，且优先级取决于你是否真要做跨机工具调用。至于 Agent 内部，仍然不需要。**（这一条属于架构推断，代码里目前没有正在使用 sse MCP 的证据：`config/mcp.yaml:9 servers: []` 是空的，下面全是注释示例。）**

## 5. 如果上，建议的形态（分三步，每步独立可回滚）

| 步骤 | 做什么 | 为什么这样切 | 验收 |
| --- | --- | --- | --- |
| S1 | **任务层队列，不是消息层队列**：`pending/` 目录 + `python -m mas worker` 独立进程，用 Redis `SETNX` 做抢占（或纯文件锁） | 解掉第 3 节那个真痛点，且完全不碰 `bus.py` / `blackboard.py` / `flow.yaml` | 前端 Ctrl-C 重启后，正在跑的任务继续跑到 `run_summary.json`；`tests/` 全绿 |
| S2 | **双写读模型**：`EventLog.emit` 与 `MessageBus.send` 各加一个「异步发布到 Redis Stream」的可选订阅者（复用 `_make_mysql_event_sink` 的形态，失败静默） | 主路径 SSOT 仍是 jsonl，MQ 只服务「实时推送 / 跨机观测」 | 关掉配置时逐字节一致；开时前端可由轮询改 SSE，且 `messages.jsonl` 内容不变 |
| S3 | **（仅当真做跨机工具时）MCP over SSE 的异步化**：远端工具调用走 MQ 请求-应答，带超时与幂等键 | 这是唯一有真实跨机语义的边界 | 远端工具超时能在 Agent 侧明确失败并留痕，不整轮崩 |

**不要做的事**：

1. 不要为了「看起来像分布式系统」把 `MessageBus` 换成 broker——它会毁掉 `send()` 的同步返回契约和消息 id 的可比性。
2. 不要在 Agent 之间引入异步投递——主循环是单链同步的（`leader.py:296-424`），异步投递只会让 `digest()` 读到不确定状态的消息，污染 Prompt。
3. 不要用 MQ 当「事件定时器 / 延迟重试」——`llm.py` 已有 `retry.max_attempts=3` + `downgrade_reasoning_effort` 的降级阶梯，"重试"要留在调用点。
4. 不要同时引入 MQ 和 MySQL 经验库改造（`docs/25` Phase C）——两件事都在改并发语义，一起做会无法归因回归失败。

## 6. 什么时候该重新评估这个结论

以下任一条件成立，第 0 节的「不要上」就应该翻转为「该上」：

1. **需要多机执行一次运行**（例如把 implement 节点放到有 GPU/大内存的机器，tester 放本机）——此时进程内状态模型必然被打破，MQ 成为必需件。
2. **运行并发数上到「同时 10+ 个，且共享经验库」**——`file_lock` 与全量重写会成为串行瓶颈，但这时的第一优选是 `docs/25` Phase C（MySQL UPSERT），不是 MQ。
3. **要接外部系统的事件**（例如 CI 触发运行、飞书机器人提交需求并异步回收结果）——这时的 MQ 是**入口**，与内部总线无关。
4. **任务量级到「每天上千次运行、需要按优先级排队与限流」**——这时才真正需要 broker 的排队、死信、优先级能力。

---

## 7. 一句话回答

**能上，但现在不该上。** 当前 MQ 的位置被两件事占着：内部是 `MessageBus` 这个「审计留痕 + Prompt 上下文」的同步列表（`bus.py`），外部是 `ThreadingHTTPServer` 里那条阻塞的 while 循环（`leader.py:296-424`）。前者换 MQ 是纯粹的负收益，后者用「独立 worker + 文件/Redis 抢占」就能解掉且不破坏契约。真正需要 MQ 的只有三处：跨机工具调用（MCP over SSE）、多机拆分一次运行、外部事件入口。在那之前，把精力放在 `docs/25` 的 Redis 协调层与 MySQL 经验库上，收益是确定的。
