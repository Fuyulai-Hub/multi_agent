# 多 Agent 任务协作系统 —— 代码库架构分析

> 分析对象：`G:/mycv/cragent/multi_agent`（Leader 统一调度的配置驱动多 Agent 流水线）
> 分析依据：源码实读（`mas/` 6,789 行 Python、`config/` 640 行 YAML、`tests/` 344 行、`frontend/` 1,555 行）
> 说明：本文所有结论均来自代码与 `workspace/` 实测数据；无法从代码确认的量化指标已用【待补充】标注。

## 1. 整体架构

单点 Leader 调度 + 五个角色 Agent 的**流水线状态机**，Agent 之间不互相调用，全部通过「共享黑板 + 消息总线」交换成果，并以**事件日志**作为全流程唯一事实来源。

```text
                        ┌──────────────────────────────────┐
                        │   config/*.yaml（配置驱动）       │
                        │  system / flow / collaboration /  │
                        │  learning / roles/*.yaml / profiles│
                        └───────────────┬──────────────────┘
                                        │ load_config() 深合并 + 校验
                                        ▼
   ┌─────────────────────────── Leader（mas/leader.py）────────────────────────┐
   │  状态机推进 / 门禁判定 / 回退计数 / 升级 / 协商中介 / 经验闭环             │
   └───┬────────────┬──────────────┬──────────────┬──────────────┬────────────┘
       │            │              │              │              │
   product     developer       reviewer        tester         reporter
  (需求评估)  (方案/编码/修复) (审查/签署)   (用例/执行/缺陷) (报告/证据)
       │            │              │              │              │
       └────────────┴──────┬───────┴──────────────┴──────────────┘
                           ▼
        ┌────────────────────────────────────────────────┐
        │  基础设施层                                     │
        │  Blackboard(版本化产物)  MessageBus(三种模式)   │
        │  EventLog(唯一事实来源)  Experience(L1/L2/L3)   │
        │  Sandbox(子进程执行 + AST 静态分析)             │
        │  LLMClient(offline / openai_compatible)         │
        └────────────────────────────────────────────────┘
```

| 模块 | 文件 | 职责 |
| --- | --- | --- |

## 2. Agent 职责划分

| 角色 | 节点 | 产物（黑板 artifact） | 可执行动作 |
| --- | --- | --- | --- |
| product | `intake` | `requirement_spec` | 解析需求 → 功能点/验收标准/样例/待澄清问题；缺样例直接判 fail |
| developer | `solution` / `implement` / `optimize` | `solution_design` / `code_manifest` / `implementation_summary` / `fix_summary` / `fix_test_report` | 写文件（沙箱）、导入自检（子进程）、定向回归执行、应答协商 |
| reviewer | `review` / `acceptance` | `review_report` / `design_review` / `acceptance_opinion` | AST 静态分析、需求一致性检查、验收签署；`can_write_code: false` |
| tester | `test` | `test_report` / `bug_reports` | 写测试文件、沙箱真实执行、覆盖率统计、缺陷跟踪与闭环判定、发起协商 |
| reporter | `report` | `acceptance_report` / `evidence_index` | 汇总事件日志与黑板事实 → Markdown 验收报告 + 证据索引 |
| Leader | 全局 | `acceptance_gate` / `run_summary` | 调度、门禁、回退、协商中介、经验提炼 |

**权限约束写在配置里**（`config/roles/*.yaml` 的 `permissions`）：reviewer 不可写代码（`can_write_code: false`），但 `can_rollback: true`、`can_block_acceptance: true`。不过这些权限字段目前**只在配置中声明，调度器未读取执行**——属于「声明了但未落地」，见第 7 节。

## 3. 协作与调度机制

### 3.1 状态机（配置驱动）

基础流程 8 个节点，流转边全部在 `flow.yaml` 里声明：

```text
intake → solution → implement → review → test → acceptance → report → end
                        ▲         │        │           │
                        │         │        │           └─fail→ optimize ─┐
                        │         │        └─fail→ optimize ─────────────┤
                        └─review fail─┘                                  │
                                        optimize ──pass/fail──→ test ────┘
```

- **回退策略按节点声明**：`review→implement ×3`、`test→optimize ×3`、`acceptance→optimize ×2`
- **兜底防死循环**：全局 `max_total_rollbacks: 8`、`flow.max_steps: 40`；达到上限走 `escalation.on_exhausted = fail_run_and_report`（仍出报告，但标注不通过）
- **回退识别**：`Leader._is_rollback()` 同时处理「显式声明的回退边」和「重新进入已执行过的节点」两种情况

### 3.2 Profile：改配置即改流程

`load_config()` 用 `deep_merge()` 做深合并（dict 递归、list/标量整体覆盖），Profile 可覆盖任意片段：

| Profile | 行为 |
| --- | --- |
| `strict` | 插入 `solution_review` 节点（8→9 节点），门禁增加「方案评审通过」，回退上限提到 4/3 |
| `lean` | `review: skip: true` 裁剪节点（8→7 节点），门禁收敛到 3 条，注入预算降到 600 token |

裁剪节点后 `_apply_skips()` 会**自动重接流转边**（把指向被裁节点的边改接到其后继，找不到后继直接报配置错误），并同步清理引用了已裁节点的回退策略。

### 3.3 三种通信模式

| 模式 | 实现 | 用途 |
| --- | --- | --- |
| 黑板（间接） | `blackboard.publish()` / `require()` / `snapshot()` | Agent 之间不直接调用，只通过产物交互；门禁表达式在 `snapshot()` 上求值 |
| 广播 | `bus.broadcast()` + `collaboration.broadcast` 矩阵 | 11 类事件（`review_rejected` / `bug_found` / `rollback` / `acceptance_passed` …）按矩阵分发给相关角色 |
| 请求-应答 | `ctx.consult()`，Leader 中介 | 测试发现需求歧义 → 向研发发起澄清 → 结论写入 `test_report.negotiation`，未闭环（`open > 0`）直接阻塞验收 |

感知关系由 `collaboration.perception` 矩阵声明，每个角色动手前必须 `require()` 自己的感知清单，缺失产物会显式写入 Prompt 的「缺失产物（请勿臆造，按缺失处理）」段。

### 3.4 门禁：表达式驱动，不是模型自评

`acceptance` 节点是 `kind: gate`，由两部分共同决定：

1. **8 条表达式**在黑板最新快照上求值（如 `test_report.coverage.boundary.rate >= 1.0`、`bug_reports.open == 0`、`test_report.negotiation.open == 0`）
2. **reviewer 的签署意见**（`verdict == reject` 一票否决）

表达式求值器 `expr.py` 用 `ast.NodeVisitor` 白名单实现：
- 只允许常量/名字/属性/下标/二元运算/比较/布尔/if 表达式/列表字典集合；
- 函数调用**只允许 14 个内置函数**（`len/min/max/all/any/sorted/int/str/bool` …）；
- `generic_visit` 兜底拒绝一切其他语法（因此导入、赋值、lambda、推导式全部被禁）；
- 字段缺失不抛异常，返回 `ExprResult(ok=False, error="字段缺失: xxx")`，让门禁能给出可读的失败原因；
- 配置加载期 `check_config_expressions()` 先做语法 + 白名单预校验，把错误前置到启动阶段。

## 4. 核心工具调用与数据流

### 4.1 工具调用的真实形态（重要，别在简历上说错）

**本系统没有使用 LLM 的 function calling / tool use API**。真实形态是：

> LLM（或 offline Provider）按「交付契约」输出结构化 JSON → Agent 用确定性 Python 代码执行工具 → 结果写回黑板

`BaseAgent.contracts` 为每个节点声明输出字段结构（如 `implementation` 契约包含 `files[{path,content}]`、`fp_mapping`、`defects_injected`），Prompt 的「交付契约」段把这个结构 JSON 化塞给模型；模型返回后由 Agent 的 `apply()` 落地。

| 工具 | 调用方 | 实现 |
| --- | --- | --- |
| 写文件 | developer / tester | `sandbox.write_file()`，路径越界检查后落盘到 `run_dir/code/` |
| 执行命令 | developer（导入自检、定向回归）、tester（跑测试套件） | `sandbox.run()`，`subprocess.run(shell=False)`，超时 180s → exit_code 124 |
| 静态分析 | reviewer | `sandbox.analyze()`，真实 `ast.parse` + `ast.walk`，12 条规则（文档字符串/类型注解/裸 except/eval/可变默认参数/函数过长/未使用导入/TODO 等） |
| 经验检索/写入 | 所有 Agent | `experience.retrieve()` / `add()` / `promote()` |
| LLM 调用 | 所有 Agent | `llm.generate()`，offline 或 `/chat/completions`（urllib，无 SDK） |

模型输出解析有容错：`parse_json_block()` 能剥掉 ``` 代码块围栏、定位首尾花括号、逐个候选尝试 `json.loads`。

### 4.2 数据流

```text
需求(file|--text)
  → [product] requirement_spec ──黑板──▶
  → [developer] solution_design ──黑板──▶
  → [developer] 写 code/ + 导入自检 → code_manifest ──黑板──▶
  → [reviewer] AST 静态分析 → review_report ──黑板──▶
  → [tester] 写 tests/ + 子进程执行 → test_report / bug_reports ──黑板──▶
  → (失败) [developer] optimize：修复 + 定向回归 → fix_test_report ──▶ 回到 test
  → [Leader+reviewer] acceptance：8 条表达式 + 签署意见 → acceptance_gate
  → [reporter] acceptance_report.md + evidence/index.jsonl
  → [Leader] run_summary.json + timeline.md + metrics.jsonl
```

**每步之后** Leader 会做一次增量经验提炼（`_extract_inline`，按事件 seq 增量处理），运行结束再做一次总结提炼 + 晋级 + 指标落盘。

## 5. 上下文与记忆管理（本项目的核心亮点）

### 5.1 分层经验库（L1 / L2 / L3）

| 层级 | scope | 生命周期 | 预算与门槛 |
| --- | --- | --- | --- |
| L1 | `run` | 本次运行即时经验，只注入同一 run 的后续节点 | 2 条 / 260 token / 置信度门槛 0 |
| L2 | `project` | 项目与领域经验，跨运行同域复用 | 3 条 / 360 token / 门槛 0.45 |
| L3 | `global` | 全局通用经验 | 3 条 / 420 token / 门槛 0.55 |

- **提炼**：`extract_from_events()` 是规则化提炼器，5 类规则从事件日志抽经验——审查拦截 → 提交前自检；缺陷模式 → 实现守护；验收未通过 → 前置校验；歧义协商 → 编码前澄清；成功路径/效率 → 可复用选型。
- **检索打分**：`相关性 0.45 + 置信度 0.25 + 使用频次 0.15 + 新鲜度 0.15`，其中相关性 = `0.5×角色匹配 + 0.3×标签重叠 + 0.2×关键词重叠`；新鲜度用 `exp(-days/30)` 指数衰减。
- **去重与合并**：同源经验（scope + action_key 哈希）命中即合并，置信度 +0.1、证据计数累加。
- **晋级**：`hits` 达阈值自动 L1→L2→L3（`L1_to_L2: 1`、`L2_to_L3: 2`），晋级时置信度 +0.05。
- **注入留痕**：每次 Prompt 落盘 `prompts/<node>#<iter>-<role>-<ts>.md`，头部注释记录注入的经验 ID 列表、token 估算、分层计数。

### 5.2 上下文膨胀的三道防线

1. **感知矩阵**：每个角色只看自己声明的产物，不是全量黑板；
2. **产物摘要截断**：`blackboard.brief()` 单产物最多 900 字符，超出标注「(截断, 共 N 字符)」；
3. **双层 token 预算**：分层预算（L3 420 / L2 360 / L1 260）+ 全局总预算 1000 token（lean 600），超预算的条目进 `skipped` 并注明原因（置信度不足 / 非本次运行 / 超条数 / 超预算），可审计。

### 5.3 经验闭环如何做到「可证伪」

注入的经验带**结构化动作标识 `action_key`**（如 `avoid_missing_function_docstring`、`guard_calc_shipping__boundary`、`boundary_tri_state`）。Offline Provider 的 `_implementation()` 会**真实消费**这些动作：

```python
guarded_ops = {op for op in matched if f"guard_{op}__boundary" in actions or "boundary_tri_state" in actions}
know_docstring_rule = "avoid_missing_module_docstring" in actions or "avoid_missing_function_docstring" in actions
if op_key in guarded_ops: continue          # 经验守护生效 → 不再注入该缺陷
with_docstrings = not (mode=="first" and strip_docstrings and not know_docstring_rule)
```

即：经验注入不是「塞进 Prompt 碰运气」，而是能被确定性执行体消费、从而产生**可测量的行为变化**。`workspace/knowledge/metrics.jsonl` 实测记录：

| 运行 | 步数 | 回退 | 审查驳回 | 缺陷 | 注入经验 |
| --- | --- | --- | --- | --- | --- |
| 首轮（offline） | 11 | 2 | 1 | 5 | 8 |
| 次轮（复用经验） | 7 | 0 | 0 | 0 | 20 |

> 注：`README.md` 与 `tests/test_pipeline.py` 注释写作「12 步 → 7 步」，`metrics.jsonl` 实测为「11 步 → 7 步」。写简历时建议用区间表述或直接引用仓库实测值。

## 6. 容错与可观测性

### 6.1 容错

| 机制 | 实现 |
| --- | --- |
| Agent 异常不炸主流程 | `BaseAgent.act()` 整体 try/except → 转 `status=fail` + 发 `node_error` 事件 |
| 沙箱超时 | `subprocess.TimeoutExpired` → `exit_code = 124` + 可读 stderr，不崩溃 |
| 沙箱路径越界 | `resolve()` 校验 `root in path.parents`，越界抛 `SandboxError` |
| 门禁字段缺失 | 返回 `ExprResult(ok=False)` 而非抛异常，门禁给出可读原因 |
| 节点回退 | per-node 次数上限 + 全局上限 8 + 升级策略 `fail_run_and_report` |
| 死循环兜底 | `max_steps = 40`，超限强制终止并发 `escalation` 事件 |
| 自环禁止 | 配置加载期校验 `forbid_self_loop`，禁止节点转移自身 |
| 产物缺失 | 感知阶段显式记录 `missing`，写进 Prompt 要求「按缺失处理，请勿臆造」 |
| LLM 失败 | HTTPError / URLError 统一转 `AgentError` → 节点 fail（`openai_compatible` 模式**未做重试与退避**） |

### 6.2 可观测性（证据链）

一次运行产出 7 类证据：

| 证据 | 路径 | 内容 |
| --- | --- | --- |
| 事件日志 | `events.jsonl` | seq / ts / agent / node / iteration / severity / payload / refs，唯一事实来源 |
| 通讯记录 | `messages.jsonl` | 全部 direct/broadcast/request-response，带 `correlation_id` |
| Prompt | `prompts/*.md` | 完整 system+user，头部注释含注入经验 ID 与 token 估算 |
| LLM 追踪 | `llm_traces.jsonl` | provider/model/延迟/tokens/**思考链**（GLM `reasoning_content`）/原始输出，单条截断 12,000 字符 |
| 产物版本 | `artifacts/<name>/v*.json` | 全版本保留 + `latest.json` + sha256 前 12 位摘要 |
| 测试执行 | `test_runs/iter*/{stdout,stderr,result.json}` | 真实子进程输出 |
| 证据索引 | `evidence/index.jsonl` | 汇总产物版本 + 关键事件 + 测试运行 |

外加 `run_summary.json`（结论/步数/回退/缺陷/各节点迭代次数/耗时）与 `timeline.md`。前端面板是纯标准库 `http.server`，提供 `/api/runs`、`/api/run`、`/api/experience`、`/api/metrics`、`/api/learning-report`、`/api/llm`、`/api/llm/test` 七个接口。

## 7. 关键技术选型与取舍

| 选型 | 理由（代码可印证） |
| --- | --- |
| **零第三方依赖**：`requirements.txt` 仅 `PyYAML` | 前端用标准库 `http.server`，HTTP 用 `urllib` 而非 openai SDK；沙箱/静态分析用内置 `ast`/`subprocess`。可离线端到端跑通 |
| **文件系统作为状态介质**（JSONL + JSON） | 无需数据库；事件日志天然可审计、可 diff；代价是单进程内运行 |
| **黑板 + 总线**而非 Agent 直调 | 角色解耦，产物版本化可追溯；「谁在第几轮改了什么」有据可查 |
| **AST 白名单求值**而非 `eval` / 模板引擎 | 门禁表达式来自配置文件，必须防注入；白名单 + 加载期校验双保险 |
| **AST 静态分析**而非模型自评代码质量 | 审查结论可复现、可回归，不受模型随机性影响 |
| **Offline 确定性 Provider** | 无 Key 也能端到端跑通，且让经验闭环的效果可被单元测试断言（`tests/test_pipeline.py`） |
| **凭据三级外注**（文件 < 环境变量 < 运行时） | 密钥不进版本库（`credentials.yaml` 在 `.gitignore`），支持脱敏回显 |
| **规则化经验提炼**而非模型总结 | 提炼结果稳定、可重复，便于回归测试 |

## 8. 主要技术难点

| # | 难点 | 代码位置 |
| --- | --- | --- |
| 1 | 配置驱动的状态机如何在「增删节点」后保持拓扑连通与校验前置 | `config._apply_skips()`、`_validate()` |
| 2 | 多 Agent 上下文传递与 token 膨胀控制 | `blackboard.brief()`、`bus.digest()`、`experience.retrieve()` 双层预算 |
| 3 | 自学习闭环如何避免「注了但没用」，做到可证伪、可测量 | `experience.extract_from_events()`、`providers/offline._implementation()` 消费 `action_key` |
| 4 | 门禁表达式来自配置，如何安全地求值且不因字段缺失崩溃 | `expr.py` |
| 5 | 没有 LLM function calling 时如何保证工具调用可靠 | 交付契约 JSON + 容错解析 `parse_json_block()` + 确定性落地 |
| 6 | 如何在无 API Key 环境下验证整个系统 | `providers/offline.py`（生成真实可运行代码 + 真实可执行测试） |

## 9. 代码中已识别的不足（面试被追问时的诚实答案）

以下均为源码核实结论，建议面试时主动提及并给出改进思路，体现工程判断力：

1. **声明了但未落地的配置项**：
   - `NodeConfig.retry`（`flow.yaml` 里 `intake.retry.max_attempts`）在调度器中**从未被读取**——节点级重试实际未实现；
   - `collaboration.guards.require_declared_artifacts: true`（节点必须产出声明的产物）**未被校验**；
   - `roles/*.yaml` 的 `permissions`（`can_write_code` 等）只在配置中声明，调度器未做权限拦截；
   - `learning.extraction.min_evidence` / `dedupe`、`feedback.penalize_on_ignore` 未被使用。
2. **反馈闭环只接了一半**：`ExperienceLibrary.reinforce()` 已实现但**全仓库无调用点**；置信度实际只通过 `add()` 合并（+0.1）与 `promote()`（+0.05）增长，`hits` 只在 `retrieve()` 时自增。
3. **单进程串行执行**：Leader 循环是同步 `while`，无并发/异步；且 `_consult_factory` 依赖 `Leader._current_bus/_current_agents` 等**类属性**，同一进程内不能安全地并行两个 run。
4. **沙箱是路径级而非系统级隔离**：仅校验 `root in path.parents`，仍以当前用户权限执行子进程，无 seccomp/namespace/资源限额，不可用于不可信代码。
5. **黑板的 `_latest` 是进程内字典**，跨进程/跨机器不可共享，因此「黑板」实际是单 run 作用域。
6. **经验检索是关键词 + 标签打分，无向量/语义检索**：同义表述的经验无法召回，长尾需求下效果有限。
7. **`openai_compatible` 模式实测未通过率高**：`metrics.jsonl` 中 2026-10-11 的多条真实 LLM 运行 `acceptance: false`（步数 9~15、回退 3~9），说明长 JSON 生成与门禁刚性条件下的稳定性仍是开放问题——**具体通过率需实测统计，此处为【待补充】**。
8. **测试覆盖有限**：仅 344 行 unittest（配置/表达式/经验/端到端流水线四个文件），无并发、无 LLM mock、无异常注入测试。
