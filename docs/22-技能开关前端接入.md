# 22 - 技能开关前端接入（GET/POST /api/skills）

日期：2026-10-17　|　范围：`runtime.skills.enabled` 与 `runtime.skills.tools_enabled`
从「只能手改 system.yaml」变为「前端弹窗勾选 → 保存 → 下一次运行生效」。

前置阅读：`docs/21-技能工具调用实现与真实链路验证.md`（开关控制的正是该链路）。

## 1. 结论

两个开关已接入前端「模型配置」弹窗，**前后端字段同名同义**（HTTP 层的 `enabled` /
`tools_enabled` 就是 system.yaml `runtime.skills` 下的两个子键，无别名、无转换）。
保存后**下一次运行生效，无需重启任何服务**；前端服务与 CLI 都不缓存配置。

| 断言 | 取证 |
| --- | --- |
| 前端勾选 → system.yaml 真实变化 | 真实 HTTP 验证：`POST /api/skills {"enabled":true,"tools_enabled":true}` 后文件两行变 true，且落盘行尾不被改写（CRLF=0） |
| 热更新（无需重启） | 同一验证中 POST 后立即 `load_config()` 读到 `True True`（`/api/run` 每次都在 start_run 里重新 load_config） |
| 字段命名一致 | POST body 即 `{enabled, tools_enabled}`；保存响应与 GET 返回同形；前端 JS 直接读写这两个名字 |
| 最小改动 | 后端 server.py 2 个函数 + 2 处路由；前端 3 个文件（html 2 个控件 / js 4 处 / css 1 段）；零新依赖 |

## 2. 三个设计问题的答案

### 2.1 配置读取与写回路径

```text
读取：GET /api/skills → load_skills_switch() → load_config() → config.runtime["skills"]
      （与「模型配置」同一读取口径、同样不带 profile；lean/strict 不覆盖 runtime.skills，
        且 default_profile=null ⇒ 读到的就是 system.yaml 原文值，与写回目标同一文件）

写回：POST /api/skills → save_skills_switch() → _rewrite_skills_switches()（行级替换）
      → config/system.yaml（保留注释与其余内容，仅改目标两行）
```

写回与 `save_llm_defaults` 同一模式（保注释、保格式的行级替换），多跟踪一层嵌套：
必须同时满足 `top=="runtime" 且 second=="skills"` 才替换——`llm.vision.enabled`、
`runtime.ui_probe.enabled`、`runtime.context_compression.enabled` 等同名键在其他段同样存在，
只按「4 空格缩进的 enabled」匹配会误改任意一个。

**行尾修复（本次连带发现并修复的既有缺陷）**：Windows 下 `Path.write_text` 默认把
`\n` 转成 `\r\n`，写回会整份改写配置文件的换行符（git 全文件 diff），与「保留格式」
承诺相悖。`save_skills_switch` 与既有的 `save_llm_defaults` 均已补 `newline="\n"`
（受控实验：`write_text('a\nb\n')` 落盘 `b'a\r\nb\r\n'`，显式 newline 后为 `b'a\nb\n'`）。

### 2.1.1 连带修复：filelock 并发打开竞争（全量回归暴露）

全量回归 319 项中 `test_concurrent_runs_isolated_two_instances` 偶发失败
（实测 13 轮 3 次 ≈ 23%），根因：`mas/filelock.py` 的 `open(lock_path, "a+b")`
在重试循环**之外**——Windows 上并发打开同一 `.lock` 文件偶发 `PermissionError`
（Errno 13）直接穿透，绕过模块自身「获取失败 → 重试 → 超时抛 FileLockTimeout」的语义。
修复：把 open 纳入既有重试循环（handle 懒打开、失败共用同一重试与超时路径，约 ±8 行）。
修复后 10/10 轮通过。与本次前端改动无关，属既有缺陷、验证过程中暴露后一并修复。

### 2.2 前端开关与后端字段映射

| 前端 | HTTP（/api/skills） | system.yaml | 语义 |
| --- | --- | --- | --- |
| `#cfg-skills-enabled` 勾选框 | `enabled`（bool） | `runtime.skills.enabled` | 技能系统总开关：文本注入 + 技能工具注册都依赖它 |
| `#cfg-skills-tools-enabled` 勾选框 | `tools_enabled`（bool） | `runtime.skills.tools_enabled` | 技能工具（function calling）注册；**依赖 enabled 双开才生效** |

- 联动规则（仅 UI 层）：`enabled` 关闭时 `tools_enabled` 勾选框置灰（值保留、不强制清零）；
- 校验（后端硬约束）：两个字段必须是 JSON 布尔，否则 400——不接受 `"yes"` / `1` 等伪装值。

### 2.3 生效方式（热更新边界）

| 对象 | 是否需重启 | 说明 |
| --- | --- | --- |
| 前端面板服务 | **不需要** | server.py 不缓存配置，GET 每次重新 load_config |
| 下一次流水线运行（面板 / CLI） | **不需要** | `/api/run` → `start_run()` 每次 `load_config()` 重读 system.yaml；CLI 同理 |
| 正在运行中的流水线 | 不受影响 | 其 config 在 run 启动时已构建，运行期间不重读——开关变更只作用于「之后启动」的运行 |

## 5. 边界与不做

- 只写这两个开关；`skills` 段的其余键（max_items / min_score / max_chars / tools_timeout_s）
  仍手改 yaml（无前端需求，不做）；
- 不做部分更新：POST 必须携带两个布尔字段（语义无歧义，避免「只改一个」的隐式默认）；
- `:has()` 选择器用于置灰样式（Chromium 105+ / Firefox 121+）；旧浏览器仅样式降级，功能不受影响；
- 目标键在 yaml 中缺失时保存报 400（不猜测插入位置），提示信息含缺失键名。
