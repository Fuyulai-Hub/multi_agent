# 输出预算与思考链治理（空正文根因 + 最小修复）

对象：`mas`（配置驱动多 Agent 系统）+ 端点 `api.chat.csu.edu.cn/v1`
现象：一轮运行没有任何代码产物，`implement` 节点 `status=fail` 且 `summary` 为空，面板上看不出原因。
结论：**不是上下文超限，是输出预算 `max_tokens` 被思考链占满，正文被截断为空字符串。**

---

## 1. 根因

### 1.1 现象链（run `20261014-004436-9236`，可复核）

| 环节 | 实测值 |
|---|---|
| `llm_traces.jsonl` 第 3 条（developer@implement 第 1 轮） | `tokens=17961`、`latency=221464ms`、`output_len=0`、`reasoning_len=12000`（= `TRACE_LIMIT` 截断值） |
| 第 5 条（第 2 轮） | `tokens=18642`、`output_len=0` |
| `events.jsonl` | `node_end(implement) status=fail`、summary 空；`review` reject → `rollback` → 第 2 轮同样空 → `verdict=fail` |
| `code/` 目录 | 0 文件 |
| 输入体积 | prompt 文件 7679 字节，头部自估 `tokens≈2295`；`context_window=262144` → **占比 0.7%** |

### 1.2 决定性实验（同一份 prompt 直接打端点，GLM）

| 实验 | 参数 | `finish_reason` | `completion_tokens` | 正文 | 思考链 |
|---|---|---|---|---|---|
| 复现线上失败 | `max_tokens=16000` | **length** | **16000（打满）** | **0 字符** | 60735 字符 |
| 小预算对照 | `max_tokens=300` | length | 300（打满） | 0 字符 | 1093 字符 |
| 参数语义 | `max_completion_tokens=300` | length | 300（打满） | 0 字符 | 1193 字符 |
| 关思考（智谱原生） | `thinking:{type:disabled}` + `max_tokens=300` | length | 300 | 0 字符 | 1279 字符（**参数被忽略**） |
| 降思考强度 | `reasoning_effort=low` + `max_tokens=300` | length | 300 | **704 字符** | 241 字符 |
| 根治对照 | `reasoning_effort=low` + `max_tokens=16000` + `json_object` | **stop** | 3929 | **12620 字符** | 155 字符，耗时 35s |

结论：`completion_tokens` 达到 `max_tokens` 上限时 `finish_reason=length`，而其中绝大部分是思考链 → **推理 token 计入 `max_tokens` 输出预算**，正文无剩余额度。

### 1.3 参数关系（只说实测，不替厂商背书）

- `max_tokens`：**含推理 token**（实测：思考链 60735 字符 ≈ 打满 16000 token，正文 0）。
- `max_completion_tokens`：本网关下与 `max_tokens` **表现完全一致**（同为 length/正文 0），即按同义参数处理，**同样计入推理 token**。是否严格等同 OpenAI 官方语义未验证（官方亦说明其包含推理 token，此处不展开引用）。
- `reasoning_effort`：本网关 GLM **生效**（low → 思考链 1073→241 字符，正文出现）。`medium` 实测与默认相当（1073 字符、正文 0），未起到避免截断的作用。
- `thinking:{type:disabled}`（智谱原生）：**被本网关忽略**，不可用。
- `usage` 明细：DeepSeek 返回 `completion_tokens_details.reasoning_tokens`（实测 40/43）；**GLM 不返回该明细** → 防御逻辑不能依赖 `reasoning_tokens`，必须以「空正文 + `finish_reason=length`」为触发条件。
- 流式（`stream=true` + `stream_options.include_usage`）：可用，正常回 `usage`，但**不增加总预算**，仍会 `length` 截断 —— 它只改善"提前感知"，不解决根因。

**不确定项**：
1. DeepSeek 是否支持 `reasoning_effort`：本次两次调用均返回 **HTTP 504**（网关 openresty 超时），与参数无关，因此支持度**无法判定**。
2. GLM 是否存在独立的"思考预算"参数：本网关未暴露，`thinking` 被忽略，未找到可用通道。
3. `medium` 是否被识别：只能说实测未降低思考量，无法区分"被忽略"还是"本就接近默认"。

## 2. 根治方案与取舍

| 方案 | 效果（实测/推断） | 取舍与副作用 |
|---|---|---|
| **降低 `reasoning_effort`（本次采用）** | 同任务 221s 空输出 → 35s 出 12620 字符正文 | 推理深度下降，复杂任务质量可能变差；需靠 review/测试节点兜底 |
| 提高 `max_tokens` | 16K 被 60K 字符思考吃光，单纯加预算不保证够 | 耗时与成本上升；更易撞网关超时（DeepSeek 已实测 504） |
| 按节点分配预算/思考强度 | 精准（implement 用 low，review 用默认） | 需配置矩阵与节点级映射，复杂度上升；本期只做全局单档 |
| 关闭思考 `thinking:disabled` | 本网关**无效** | 至少在本通道不可用 |
| 流式输出 | 可用，但**不增加预算** | 只提升可观测性，不能根治（常见误解） |
| 精简 prompt 减少思考量 | 有效（思考量与任务复杂度正相关） | 需裁剪契约/经验注入，可能丢约束；`blackboard.brief` 已按 900 字符截断 |
| 产物分批生成（多次调用各写一批文件） | 单次输出体积下降，最彻底 | 要改契约与落地逻辑，改动面大，本期未做 |

## 3. 代码改动（最小改动，5 处）

### 3.1 `mas/llm.py`

- `Generation` 新增字段（诊断用）：
  ```python
  finish_reason: str = ""      # stop | length（被输出预算截断）| ...
  prompt_tokens: int = 0
  completion_tokens: int = 0
  reasoning_tokens: int = 0    # usage.completion_tokens_details.reasoning_tokens（端点不返回则为 0）
  degraded: bool = False       # 本次结果来自"降低思考强度"的降级重发
  ```
  `to_dict()` 同步输出这 5 个键。
- `LLMClient.__init__` 新增配置读取：`reasoning_effort`（默认 `""`=不下发）、`empty_output_retry`（默认 1）、`downgrade_reasoning_effort`（默认 `"low"`）；新增常量 `TRUNCATED_FINISH = "length"`。
- `_generate_openai` 拆分为 `_build_payload` / `_request_generation` / `_parse_response`（原逻辑内嵌在 60 行函数里，行为不变），并新增降级循环与兜底：
  ```python
  # 改前：解析完直接返回，正文为空时 error 为空 → 上层静默 fail
  # 改后：
  while (not generation.text and not generation.tool_calls
         and generation.finish_reason == self.TRUNCATED_FINISH
         and not generation.error and attempts < self.empty_output_retry):
      retry_payload = dict(payload)
      retry_payload["reasoning_effort"] = self.downgrade_reasoning_effort
      fallback = self._request_generation(retry_payload, api_key, base_url)
      fallback.degraded = True
      generation = fallback
  if not generation.text and not generation.tool_calls and not generation.error:
      generation.error = self._empty_output_error(generation)
  ```
  注意 `not generation.tool_calls` 这一条件：function calling 的中间轮正文为空是正常行为，不能误判（修复首版已踩此坑，导致 e2e 用例失败）。
- `_parse_response` 读取 usage 明细；新增 `_empty_output_error()` 生成诊断串（含 `finish_reason`、`completion_tokens`、`reasoning_tokens`、`reasoning_chars`）。

### 3.2 `mas/agents/base.py`

```python
# 改前
if generation.data is None:
    result.status, result.error = "fail", "模型未返回可解析的 JSON"
    return result
# 改后：带上诊断信息并发 node_error 事件（原为静默失败，面板上只有"失败"没有原因）
if generation.data is None:
    result.status, result.error = "fail", (
        generation.error or f"模型未返回可解析的 JSON（finish_reason=...，正文 N 字符）")
    self.ctx.events.emit("node_error", ..., payload={"error": result.error})
    return result
```
`_trace_llm` 落盘新增 `finish_reason` / `prompt_tokens` / `completion_tokens` / `reasoning_tokens` / `degraded`。

### 3.3 `config/system.yaml`（`llm` 段新增，既有项默认值一律不动）

```yaml
reasoning_effort: ""              # 空=不下发（保持端点默认）；可填 low / medium / high
empty_output_retry: 1             # 正文为空且被截断时降级重发次数（0=关闭）

```

## 4. 防御逻辑

1. **读取 usage**：`completion_tokens_details.reasoning_tokens`（DeepSeek 实测有）→ 记入 `Generation.reasoning_tokens` 并落盘；端点不返回时记 0，**不估算**（避免假数据）。
2. **检测**：`正文为空 且 无 tool_calls 且 finish_reason == "length"` → 判定为"思考链吃满预算"。
3. **降级重发**：以 `reasoning_effort=low` 重发一次（次数 `empty_output_retry` 可配），结果标记 `degraded=True`。
4. **兜底告警**：重发仍为空 → `generation.error` 写入完整诊断 → `base.act()` 发 `node_error` 事件，面板可见原因（此前静默）。
5. **留痕**：`llm_traces.jsonl` 每次调用都带预算字段，便于事后统计哪类节点/模型最容易触发。

## 6. 无法从根本上消除的场景

1. **端点/模型不提供思考强度控制**：不认 `reasoning_effort`、不透传 `thinking` 时，只剩"加预算 / 换模型 / 缩小产出粒度"。
2. **端点不返回 `reasoning_tokens` 明细**（GLM 实测）：无法精确预分配预算，只能事后按 `finish_reason=length` 判定并重试。
3. **单次调用必须一次性吐出超大正文**：即使预算充足，也可能撞模型自身硬上限（非请求参数可控）；此时唯一解是把产物拆成多次调用分批落地（本期未做）。
4. **网关/上游超时**：实测 DeepSeek 504（openresty，约 5 分钟），表现为失败且与预算无关，重试仍可能超时。
5. **任务本身需要深度推理**：降思考强度与保推理质量此消彼长，只能按节点权衡，没有两全的配置。
6. **正文非空但被截断**：`finish_reason=length` 且 JSON 只剩半截 → `parse_json_block` 解析失败，同样需要重发；多次仍截断则只能缩小产出粒度。
