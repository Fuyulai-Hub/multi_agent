# 配置驱动的多 Agent 任务协作系统（MAS）

**个人项目** ｜ 2026.9 - 2026.10

- 五个角色 Agent（产品 / 研发 / 评审 / 测试 / 报告）串起需求评估到报告归档的交付流水线，节点、流转、门禁、回退全部 YAML 声明；Profile 深合并 + 节点裁剪后自动重接流转边，加一个评审环节或去掉审查环节都只改配置，调度代码不动；角色间仅经版本化黑板与消息总线通信，无直接调用。第三方依赖仅 PyYAML。

- 证据式验收门禁：门禁判据写成表达式，由 AST 白名单求值器在黑板快照上求值（拒绝赋值、导入、方法调用），判定用例通过率、功能 / 异常 / 边界三类覆盖率、缺陷闭环与需求歧义闭环；叠加语法树静态检查扫描代码与前端资产问题，经路径隔离、命令白名单、敏感环境变量剔除、资源限制四层沙箱约束真实执行，只认跑出来的证据，不认模型自述。

- 服务化后端：Redis Streams 承载运行队列与 Agent 消息，每个角色独立消费组实现扇出，未确认消息可被重新认领、失败按退避重投、超限转入死信队列，至少一次投递语义下靠运行摘要做幂等；独立 worker 消费，使数十分钟级长任务与 API 进程生命周期解耦。MySQL 建索引表支撑查询统计，实时写走覆盖更新、历史迁移只补缺口以免陈旧快照回滚计数；文件系统为证据层唯一真相源，库连接失败只降级不抛异常。

- 大模型接入：手写 SSE 流式客户端绕开网关对非流式请求的总时长上限，用逐级降低推理强度的降级阶梯，治理思考链吃满输出预算导致正文为空的问题。三级经验库按相关性、置信度、使用频次、新鲜度加权检索后注入 Prompt，运行结果反向修正经验置信度形成闭环。

## 说明：为什么删掉这些数字

| 原数字 | 删掉的原因 |
| --- | --- |
| Python 17,026 行 / 43 模块 | 读者无法判断这个规模是好是坏，行数也不代表质量 |
| 373 条自测用例 | 同上；测试价值看覆盖了哪些风险，不看条数 |
| 486 次真实调用 / 4 个模型 / 13 次降级 | 属于调试过程量，读者无从对标 |
| 387 次反馈调整、47 次运行 | 调参过程量，不如直接说「形成了闭环」 |
| 10 条门禁 / 18 条静态规则 / 3 条前端规则 | 数字带不出信息，改成列出「判定什么」更有说服力 |
| MySQL 六张表 | 表数量与设计好坏无关，改成说明「支撑什么查询」 |
| 权重 0.45 / 0.25 / 0.15 / 0.15 | 参数细节，面试被问到再展开即可 |

保留的数字只有两类：**角色数**（说明分工规模）与**环节数**（说明流程长度）。这两个读者能立刻理解。

## 面试时怎么展开这些被删掉的数字

- 被问「测试做得怎么样」：不报条数，说清测了哪几类风险——配置解析与裁剪、门禁表达式求值、经验检索与晋级、技能注入、任务取消、队列可靠性、前后端交付形态。
- 被问「调用量多大」：说清遇到过什么问题、怎么解决的（网关超时靠流式、思考链吃额度靠降级），比报次数有效。
- 被问「规则具体有哪些」：说文档缺失、类型注解缺失、可变默认值、裸 except、危险调用、意外外连依赖、命令白名单绕过、前端标签未闭合。
