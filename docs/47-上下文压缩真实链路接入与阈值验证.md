## 一、改造前的事实（为什么必须改）

上一轮盘点确认：压缩代码在，但真实执行史里**一次都没用过**。

| 机制 | 改造前状态 | 证据 |
|---|---|---|
| `compress.found_artifacts`（结构化压缩） | `enabled: false`，从未启用 | 全部 `events.jsonl` 中 `context_compressed` = **0** |
| `context.ContextManager.fit`（Codex 式三层） | `enabled: true`，但从未触发 | 峰值 prompt_tokens 75146，仅为阈值 178329 的 42%；`context_compacted` = **0** |
| `blackboard.brief`（感知段） | 实际生效，但多数是**裸硬截断** | 1023 份 prompt 中 354 份含 `...(截断, 共 N 字符)` |

**两个真实缺陷（不是配置问题，是代码问题）**：

1. **没有阈值**：`found_artifacts` 一旦 `enabled=true` 就对**所有**白名单产物无条件压缩，
   哪怕它只有 500 字符。这与「压缩是超限后的补救」的语义相反，会无谓丢掉本可完整保留的细节
   （如 `test_report` 的逐条用例明细）。
2. **改动了 `Perception.found`**：原实现把压缩结果直接当作 `Perception.found` 返回。
   而下游 Agent 会从 `found` 里取 `test_report.test_file`、`bug_reports.items`、`env_probe` 做逻辑判断——
   压缩 `bug_reports` 会**清空已关闭缺陷的 items**，`test_report` 压缩会丢 `test_file`。
   这与模块文档承诺的「只改进 Prompt 的内容」相矛盾，属于会改变流程行为的隐患。

## 二、改了哪三处（最小改动）

### 2.1 `mas/compress.py`：补上阈值语义

```python
original = _size(value)
if original <= per_item:
    # 未达阈值：原样透传（这是「按阈值触发」的核心——没超就不动）
    artifacts[name] = value
    untouched.append(name)
    continue
```

只加 6 行：**单产物不超过 `per_item_chars` 就完全不碰**。超阈值才走 L1（丢 samples/parameters）
→ 仍超再 L2（只留 id/title/rules/category）→ 最后按 `total_chars` 对低优先级产物继续裁剪。

### 2.2 `mas/agents/base.py`：压缩只进 Prompt，不进 `Perception.found`

```python
brief = self.ctx.blackboard.brief(sorted(found.keys()),
                                  max_chars_per_item=max_chars, data=result.artifacts)
return Perception(found=found, missing=missing, artifacts_brief=brief, bus_digest=digest)
```

`found` 用完整产物，压缩结果只作为 `brief()` 的 `data` 覆盖映射——**只影响进 Prompt 的文本**。
黑板数据、门禁求值（走 `blackboard.snapshot()`）、下游 Agent 的逻辑判断全部不受影响。

同时把事件 payload 补上实际生效的两个阈值（`per_item_chars` / `total_chars`），便于审计「为什么这次压了/没压」。

### 2.3 `config/system.yaml`：启用并让两个阈值对齐

```yaml
prompt_artifact_max_chars: 30000
context_compression:
  enabled: true
  per_item_chars: 30000        # = prompt_artifact_max_chars：恰在硬截断发生处接管
  total_chars: 60000           # 感知段总量预算
```

## 三、压缩阈值是怎么做的（两条线，缺一不压）

```
                        ┌─ 单产物 > per_item_chars（30000）？──否──→ 原样透传（一个字节都不动）
感知到的每个 artifact ──┤
                        └─ 是 ──→ L1 结构化压缩（保 FP 的 id/title/rules/acceptance，丢 samples/parameters）
                                          │
                                          ├─ 仍 > 30000 ──→ L2 深压（只留 id/title/rules/category）
                                          │
                                          ▼
                              压缩后感知段总量 > total_chars（60000）？
                                          └─ 是 ──→ 按优先级继续深压：test_report → review_report → bug_reports
                                                     （spec / solution_design 不参与，保需求不被牺牲）
```

**关键设计：`per_item_chars` 显式对齐 `prompt_artifact_max_chars`（都是 30000）。**
这不是巧合——`brief()` 在超过 `prompt_artifact_max_chars` 时会把 JSON **硬切断**（`payload[:max] + "...(截断)"`，
把 JSON 切坏、尾部 FP 整段消失）。把压缩阈值设在这里，等于**在硬截断即将发生的位置接管**：
在此之前完整透传，在此之后改用结构化压缩。压缩失败或产出更大时回退原值，仍由 `brief` 兜底。

与 `ContextManager`（另一套机制）的区别：那一套按 **token 预算**（窗口 262144 − max_tokens 64000 = 198144，
90% 即 178329）管理**整份请求体**，管的是「多轮工具历史堆积」。两者阈值口径不同、作用对象不同，互补而不重叠。

**关于验收结论（如实说明）**：四次跑完全程的运行（含压缩关闭的基线）**结论一致，都是 fail**，
且失败原因完全相同——`acceptance_gate.failed_criteria = [{"id": "回退次数耗尽"}]`，
即业务测试连续失败耗尽 3 次回退预算。这是 `miniledger_backend` 这个需求本身的难度
（历史同需求 10 次运行里 9 次 fail），**与压缩无关**：压缩关闭时同样 fail。

也就是说，本次验证**没有**证明「压缩能提高通过率」；它证明的是
**「压缩在真实链路上确实触发、确实大幅减小感知段，且不破坏交付质量（FP 不丢、JSON 不坏、节点照常推进）」**。

**关于 `verify-comp-01/02` 的失败（如实说明）**：这两次都停在 `product@intake` 的「隐藏用例生成」环节，
错误是 `hidden_file_not_object` / `hidden_case_missing:FP-01..FP-06`——模型输出的 JSON 结构不符合预期。
这**不是压缩造成的**，证据有两条：

1. 该节点的 `context_compressed` 是 `compressed=[]`（intake 感知段只有 5896 字符，未达阈值，一字未改）；
2. 逐行 diff 两次运行的 `intake#1` Prompt（29988 vs 29992 字符），差异只有 run_id 与经验命中次数，
   **没有一行是压缩导致的**。

该环节本身是 Qwen 在该需求上的不稳定点（同一需求下 `verify-comp-03/04/05` 三次都通过了这一步，
而 `verify-comp-01/02` 各失败一次），属于模型输出协议波动，与本次改动无关。

## 五、已知边界（没做 / 做不到）

1. **`ContextManager`（Codex 式三层）仍然一次没触发过。** 它的阈值是 token 级（178329），
   而真实 prompt 峰值只有 75146。要让它触发，需要把窗口调小或把 `compact_ratio` 大幅降低——
   那是另一个决定，本次未动。两套机制现在同时开启，互不干扰。
2. **只对白名单产物生效**：`requirement_spec` / `test_report` / `review_report` / `bug_reports`。
   `solution_design`（真实最大可达 5 万字符）**没有压缩策略**，超阈值时仍走 `brief()` 的硬截断。
   这是明确的缺口，若要补需新增策略并单独验证（它有 `implementation_plan` 等对下游有价值的明细）。
3. **压缩是全有或全无的字段裁剪**，不是摘要改写。L2 深压会丢 `description/inputs/outputs/acceptance`，
   只保 `id/title/rules/category`。是否影响实现质量，需要跨更多需求做定量对比，本次只验证了「不漏 FP、不切坏 JSON、节点通过」。
4. **`llm_summary` 配置项仍未接线**（读配置但代码里没有消费点），LLM 摘要仍为未实现状态。
5. **验证未证明「压缩提高通过率」。** 四次跑完全程的运行（含压缩关闭的基线）结论一致，
   都因「回退次数耗尽」而未通过验收——这是该需求本身的难度，与压缩无关。
   本次达成的是「压缩真实触发（31 次实际压缩）、大幅减小感知段（25%~54%）、且不破坏交付」
   （31/31 压缩块 JSON 可解析、FP 一个不少、0 次硬截断）。要证明收益需换更易通过的需求做 A/B，本次未做。
