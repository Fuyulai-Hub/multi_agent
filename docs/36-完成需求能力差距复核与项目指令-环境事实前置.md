# 完成需求能力：与 Codex 的差距复核 + 两处最小改动（docs/36）

## 0. 先给结论

**multi_agent 与 Codex 在"能不能把需求做完"上的差距，不在循环结构、并行工具、沙箱强度这些架构级差异上**——那些要么不该抄（引入 asyncio 牵动全同步假设），要么在 Python 单进程 + Windows 下做不到（landlock/seatbelt）。真正的差距集中在一句话：

> **约束没有在决策之前变得可见。**

具体是两个可判定的缺口（本次定位并修复）：

| 缺口 | 表现 | Codex 对应机制 | 代价 |
|---|---|---|---|
| 形态判错了没有纠正入口 | intake 判 `full_stack_spa` → 本机无浏览器证据通道 → 必然验收不通过，且改代码改不掉 | `AGENTS.md`（`core/src/agents_md.rs:42`） | 整条链路白跑，最后 `forced_fail` |
| 环境事实只在验收端可见 | `env_probe` 只有 test 节点感知，产品定形态、研发定选型时看不到 | world state（`core/src/session/mod.rs:4473`） | 「规划时不看约束，验收时才发现违反约束」 |

**量化背景**（`workspace/runs/*/run_summary.json`，48 次有结论的运行）：pass 20 / fail 28。失败归因里 **15 次是"回退次数耗尽"**（其中 test 节点 11 次），12 次是节点或门禁直接判失败。也就是说失败的主形态不是"跑挂了"，而是**"改了几轮还是过不了"**——正是约束未在决策前可见的典型症状。

## 2. 两个缺口的定位过程

### 2.1 缺口一：形态判错了没有纠正入口

完整链路（每一环都能在代码里对上行号）：

```
intent.py L1/L2 判 shape = full_stack_spa
  → config/system.yaml:99  ui_probe.enabled = false（默认关）
  → envprobe.py:71        browser_ui_ready = False
  → tester.py:595-607     _verification_gap 报 gap=1（如实判失败，不降级放行）
  → tester.py:436-439     result.status = fail
  → leader.py:531         回退到 optimize（研发改代码）
  → 改代码消除不了通道缺口 → 回退耗尽 → forced_fail
```

关键在最后两步：这是一个**改代码永远改不掉**的失败，但在本次改动之前，需求方没有任何手段告诉流水线"这个需求不该按 SPA 交付"——要么改 `intent.py` 的分类规则（改框架），要么去 `system.yaml` 里打开 `ui_probe` 并接好 Playwright MCP（改环境）。

历史实证：`workspace/runs/20261019-163912-b732` 的事件流里同时存在
`test_verification_gap`（形态 SPA、通道未接入）与 `test_ui_evidence_incomplete`；
另有一次真实 LLM 运行把「贪吃蛇小游戏」判成 `full_stack_spa`（`requirement_spec` 产物落盘可查）。

### 2.2 缺口二：环境事实只在验收端可见

`env_probe` 在 run 启动时就写成黑板产物（`mas/leader.py:427`，早于 intake 执行），
但消费方只有一个：

- `config/flow.yaml:59` —— 只有 `test` 节点的 `inputs` 含 `env_probe`；
- `config/collaboration.yaml` —— 感知名单里 `product: ["requirement_source"]`、`developer: [...]` 均不含它。

而 `perceive()` 取的是 `collaboration.perception_of(role)`（`mas/agents/base.py:569`），
所以**产品定形态、研发定选型的那一刻，模型看不到"浏览器通道不可用、node 是否可用"**。
Codex 的做法是把环境/git/沙箱等运行时事实作为 world state 拼进初始上下文
（`build_initial_context_with_world_state`，`session/mod.rs:4473`；压缩后的新窗口也用它重建——`compact.rs:92`），每个 turn 都可见。

## 3. 最小改动实现

三处代码 + 三处配置，共 **+93 / -5 行**（不含新增的模块与测试）：

| 文件 | 改动 |
|---|---|
| `mas/projectdocs.py` | **新增 226 行**：收集、上限、front-matter 解析、形态声明取值 |
| `mas/prompts.py` | +11/-1：`PromptBuilder` 增加 `project_docs` 项，插在感知段之前 |
| `mas/leader.py` | +21：解析输入后收集、注入、发布 `project_docs` 产物、落 `project_docs_loaded` 事件 |
| `mas/agents/product.py` | +18：项目指令声明的 `delivery_shape` 覆盖模型判定，来源记 `project_doc` |
| `config/flow.yaml` | +5/-2：`intake` / `solution` 的 inputs 加 `env_probe` |
| `config/collaboration.yaml` | +8/-2：`product` / `developer` 的感知名单加 `env_probe` |
| `config/system.yaml` | +6：`runtime.project_docs.{enabled, max_bytes}` |
| `tests/test_projectdocs.py` | **新增 283 行 / 19 个用例** |

### 3.1 项目指令文件（对标 AGENTS.md）

- **收集**：从需求文件所在目录向上逐级到项目根；同目录有 `AGENTS.override.md` 时覆盖 `AGENTS.md`；由外到内拼接（离需求越近越权威）。
- **上限**：32 KiB，按 UTF-8 字节累计，超限即停并标记 `truncated`（与 Codex `DEFAULT_PROJECT_DOC_MAX_BYTES` 同策略，不截断到半句话）。
- **起点为什么不是 cwd**：Codex 从 cwd 遍历；本系统需求常来自 `examples/requirements/` 等子目录，从 cwd 找会把无关目录的指令带进来。
- **可选 front-matter**（这是与 Codex 的有意差异）：与仓库内 `skills` 的 SKILL.md 同构，只认白名单键 `delivery_shape`；写了就由框架**确定性采纳**，不靠模型这次看懂。没写 front-matter 时退化为纯文本注入。
- **覆盖语义**：声明值合法即采纳，`delivery_shape_source` 记为 `project_doc`；与模型判定不一致时额外落 `intent_declared_by_project_doc` 事件（复盘时能查到"用户纠正了框架"）。非法值一律忽略——手误不该把流水线带进不可验证的形态。

### 3.2 环境事实前置

只改两处配置：`product`/`developer` 的感知名单与 `intake`/`solution` 的 inputs 加 `env_probe`。
`env_probe` 本身已在 intake 之前发布，无需改发布时机；产物体积在 `prompt_artifact_max_chars=10000` 预算内。

### 3.3 零影响保证

没有项目指令文件时，收集结果为空 → `PromptBuilder.project_docs_text` 为空串 → **Prompt 与改造前逐字节一致**（`test_prompt_unchanged_when_no_docs` 锁定）。环境事实前置会改变决策节点的输入（这是目的本身），但由 C 组基线对照证明它不改变离线全链路的结论与步数。

## 5. 这次改动解决什么、不解决什么

**解决**：需求方能声明形态（纠正误判）；决策节点能看到环境能力（规划阶段就避开不可验证的形态）。

**不解决**（如实说明，避免把"注入了约束"说成"模型一定遵守"）：

- 注入的是**文本与声明**，模型是否按它选型仍取决于模型本身；只有 front-matter 的 `delivery_shape` 是框架确定性执行的。
- 若需求本身确实需要浏览器 SPA 形态，本次改动不会让它变通过——它仍会按 docs/15 的诚实性原则如实报失败。改动提供的是**纠正权**与**提前可见性**，不是放宽验收。

## 6. 明确不做（附理由）

| Codex 机制 | 不做的原因 |
|---|---|
| 并行工具调用（`FuturesOrdered`） | 需引入 asyncio，牵动沙箱/文件锁/事件落盘的同步假设；耗时大头是单次 LLM 请求（实测 400s+），收益远小于成本 |
| 平台级沙箱（landlock/seatbelt/受限令牌） | Python 标准库无对应能力；且 Windows 上 Codex 默认也无沙箱 |
| LLM 摘要压缩 / 两阶段记忆提炼 | 每次压缩都要再调一次模型，在本项目 HPC 端点（300s 网关超时是实测失败模式）代价过高 |
| 完整人工审批（`AskForApproval`） | 与"全流程无人工干预"的批处理定位冲突 |
| 动态多 Agent 委派（spawn/wait） | 本系统是确定性流水线，可预测性与可观测性是其优势；要改也是节点内行为分化，不是抄动态派发 |
